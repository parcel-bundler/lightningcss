# PR #1308: Fix parsing of pseudo-elements and pseudo-classes after ::details-content
**Verdict:** approve with nits (drop the `.cargo/config.toml` hunk; optionally add element-backed pseudos to `valid_after_slotted`). **Confidence:** high.

Author: rorshopping. Fixes #1244. Built with `build-pr.sh --on-master 1308` (merges cleanly onto 574eee24).

## Summary
Models element-backed pseudo-elements (`::details-content`, `::picker()`) in the forked selectors parser: any pseudo-class/pseudo-element may follow them, they may follow `::part()`, and `::before`/`::after` accept `::marker` after them. The bug is real: on master `::details-content::before{color:red}` is a hard `InvalidState` error in strict mode (CLI panics), and with `--error-recovery` the rule is dropped, although Chrome 153 (and per the issue, Firefox and Safari) accept it. The PR is a near-literal port of upstream servo/stylo's design (same trait methods and state-flag names) and fixes it.

## Design
- **Upstream comparison (servo/stylo `selectors/parser.rs`, main).** Upstream has the same three trait methods (`valid_after_before_or_after`, `parses_as_element_backed`, `is_before_or_after`), renames `AFTER_PSEUDO_ELEMENT` to `AFTER_NON_ELEMENT_BACKED_PSEUDO`, adds `AFTER_BEFORE_OR_AFTER_PSEUDO`, and uses the same `allows_pseudos` condition (`DISALLOW_PSEUDOS || (AFTER_NON_ELEMENT_BACKED_PSEUDO && !AFTER_BEFORE_OR_AFTER_PSEUDO)`), the same `valid_after_before_or_after` check, and the same functional-pseudo-class gate (`AFTER_NON_ELEMENT_BACKED_PSEUDO | AFTER_SLOTTED`). Differences:
  1. Upstream folds element-backed pseudos into `AFTER_PART` (renamed `AFTER_PART_LIKE`); the PR adds a separate `AFTER_ELEMENT_BACKED_PSEUDO_ELEMENT` flag. Reasonable here: lightningcss derives `HAS_PART`/`HAS_PSEUDO` from parse state (upstream computes flags from components in the builder), so folding would set `HAS_PART` for `::details-content`. Parse behavior is the same.
  2. The PR clears `AFTER_BEFORE_OR_AFTER_PSEUDO` after a non-before/after pseudo, so `::before::marker::marker` is rejected; upstream keeps the flag and would accept it. Chrome 153 rejects it, so the deviation is correct (stricter, matches browser and spec note "pseudo-elements cannot be chained together unless explicitly allowed").
  3. Upstream's Gecko `valid_after_slotted` is "is tree-abiding", which includes all element-backed pseudos, so `::slotted(div)::details-content` parses in Firefox; Chrome 153 accepts it too. lightningcss's `valid_after_slotted` (src/selector.rs) is a hard-coded list without `DetailsContent`; both master and PR reject it. Pre-existing, but cheap to fix in this PR (Finding 2).
  4. Gecko marks view-transition pseudos as element-backed; the PR deliberately doesn't (css-view-transitions only allows `:only-child`). Chrome rejects `::view-transition-group(x)::before`, so the PR's choice matches browsers.
- **`::picker()` as element-backed.** Not stated in css-forms-1 text, but Gecko's `pseudo_elements.toml` has `is_element_backed = true` for `picker`, and Chrome accepts `::picker(select)::before`, `:lang(en)`, `::picker-icon` after it. OK.
- **HAS_PSEUDO claim.** On master a bare `::details-content` already set `AFTER_PSEUDO_ELEMENT` → `HAS_PSEUDO`, so the `:is()` lowering guard in `rules/mod.rs:750` behaves the same; the PR keeps that invariant via `has_pseudo_element` including the new flag. No behavior change there.
- General and in the reusable place (trait methods on `PseudoElement`, as upstream). No perf concern (constant work per pseudo-element).

## Spec
css-pseudo-4 §Element-backed pseudo-elements (https://drafts.csswg.org/css-pseudo-4/#element-like):
> All pseudo-classes and pseudo-elements are syntactically allowed after an element-backed pseudo-element (such as `x-button::part(label):hover` or `x-button::part(label)::before`), just as if the pseudo-element were a type selector; but some are disallowed from matching: The structural pseudo-classes, `:has()` pseudo-class, `:scope` pseudo-class, and `:host`/`:host()`/`:host-context()` pseudo-classes never match. `::part()` never matches.

§details-content: "It is an element-backed pseudo-element." Intro note: "pseudo-elements cannot be chained together unless explicitly allowed. For example, `::marker::before` is not allowed; but `::before::marker` is."

Browser deviation: Chrome rejects (at parse time) `::details-content:first-child`, `:empty`, `:has()`, `::part()`, `::slotted()` after it, whereas the spec says they're syntactically allowed but never match. The PR (like upstream) rejects `::part`/`::slotted` after it and passes structural pseudo-classes through as unknown; either way the rule never applies, so output meaning is preserved.

## Findings
1. **Should fix: drop the `.cargo/config.toml` hunk.** Master already added `-C link-arg=--allow-undefined` for wasm32 in 3822c49a ("fix wasm build", 2026-09-26). The PR merges cleanly, but the merged file then passes the flag twice (harmless for wasm-ld, but noise). This is unrelated to the selector fix and should not be in this PR in any case. The `src/selector.rs` blank-line rustfmt hunk is also already on master (no-op after merge); the `src/lib.rs` `image(alpha(...))` reformat is unrelated noise but harmless.
2. **Nit / optional: `::slotted(div)::details-content`.** Chrome 153 accepts; upstream Gecko accepts (tree-abiding ⇒ valid after slotted); master and PR both error in strict mode (`Invalid state`). Fix: add `PseudoElement::DetailsContent` (and arguably `PickerFunction`) to `valid_after_slotted` in src/selector.rs. Pre-existing, not a regression.
3. **Pre-existing, out of scope (not for this PR):**
   - `::details-content:has(div)` and `::part(foo):has(div)` serialize as `:has()` (argument lost) on both master and PR. Chrome rejects the selector anyway so no visible change alone, but the empty `:has()` is wrong output. Worth a separate issue.
   - Chrome rejects any user-action pseudo-class after `::before` (`::before:hover`), so `.x{color:red} .d::before:hover{color:red}` → `.x,.d:before:hover{color:red}` drops `.x` in Chrome. Same on master; the PR just makes more such chains parseable (`details::details-content::before:hover`). cases.mjs reported this as a "regression" in `--error-recovery` only because master dropped the rule entirely there. Not PR-caused.
   - Nested `&::before` inside `details::details-content{}` is lowered to `details::details-content:before` (with targets), although `&` can't represent pseudo-elements. Same output on master.
