# PR #1386: fix: emit @supports fallbacks for nested declarations
**Verdict:** request changes (small). **Confidence:** medium-high.

## Summary
Declarations that follow a nested rule are parsed into a `NestedDeclarationsRule`. Its `minify` lowers values in place (for example `--after: #ffedce`) and queues `@supports` overrides in `PropertyHandlerContext::supports`. On base, `CssRuleList::minify` never emits those overrides for `NestedDeclarations`. The PR adds `take_nested_supports_rules`, which drains the entries and emits `@supports (cond) { <NestedDeclarationsRule> }` right after the nested declarations. The bug from #1381 is real and the PR fixes it: on base the override is lost, or worse, it is attached to the **next sibling nested style rule**, which uses that rule's selector. Base example: `.foo{.bar{} --after:lab(..); .baz{}}` → `@supports(color:lab(0% 0 0)){.foo .baz{--after:lab(95% 4 18)}}`. In Chromium, base is not equivalent and the PR is equivalent.

The PR has two problems:
- **Incomplete fix.** It drains only the `supports` side channel. The same handler context also collects `ltr`/`rtl` (logical-property `:dir` fallbacks) and `dark` (`color-scheme` with `light-dark()` lowering). Those are still dropped, or leaked into the next sibling rule.
- **Newly exposed bug.** It brings a pre-existing bug to nested declarations: an `@supports` fallback is emitted for a declaration that a later declaration in the same block overrides.

## Spec
I could not fetch the spec. `drafts.csswg.org` does not resolve in this session (network allowlist), and no web-fetch agent type was available to me. So I have no quote for CSS Nesting 1 §"The Nested Declarations Rule" (https://drafts.csswg.org/css-nesting-1/#nested-declarations-rule).

Here is the behavior that matters, verified in Chromium (bundled build 1243) instead of the spec:
- Nested declarations apply in source order relative to sibling nested rules. A later nested-declarations block beats an earlier `& {}` rule of equal specificity (case "earlier nested rule same specificity overridden": equivalent).
- With a parent list `.a, #i`, nested declarations do **not** get `:is()` specificity. `div.a{color:blue}` still beats them for `.a` elements, and the flattened `.a,#i{…}` output is equivalent.
- `@supports` with bare declarations inside a style rule is wrapped as nested declarations. The PR's output shape matches what the parser already produces.

## Findings

1. **should fix: leak/loss of `ltr`/`rtl` and `dark` fallbacks from nested declarations (same mechanism, not handled).** `take_nested_supports_rules` drains only `self.supports`. `add_logical_rule`/`add_dark_rule` entries collected while minifying a `NestedDeclarationsRule` stay in the context. `get_additional_rules` then emits them for the next sibling `Style` rule (with that rule's selector), or they are discarded. This is pre-existing, but it is the same "entries stay in the handler context" bug the PR description says it fixes.
   - Logical: `.a{.b{color:red} margin-inline-start:10px; margin-inline-end:20px; .c{color:green}}` with `--targets 'chrome 60'`. Base and PR: `.a{}` gets no margins, and `.a .c:not(:lang(ar,…)){margin-left:10px;margin-right:20px}` plus the RTL variants are emitted for `.a .c`. Browser: NOT EQUIVALENT (28 diffs: `margin-left 10px -> 0px` on `div.a`). Without the following `.c` rule the margins are just dropped (12 diffs).
   - Dark: `.a{.b{color:red} color-scheme:light dark; color:light-dark(red,blue); .c{color:light-dark(green,yellow)}}` with `--targets 'chrome 100'`. Base and PR emit `@media (prefers-color-scheme:dark){.a .c{--lightningcss-light: ;--lightningcss-dark:initial}}` instead of targeting `.a`. Chromium with `prefers-color-scheme: dark` emulated: input `.a`=`rgb(0,0,255)`, output `.a`=`rgb(255,0,0)`. `equivalence.mjs` missed this because it doesn't emulate dark mode; I checked with a puppeteer script (`reviews/pr-1386/dark.mjs`).
   - Suggested fix:
     - Minimum: call `context.handler_context.reset()` after handling a `NestedDeclarations` rule, so nothing leaks into siblings.
     - Better: also emit the logical/dark rules as nested rules. `&:dir(ltr) { … }` / `&:dir(rtl) { … }` style rules, and `@media (prefers-color-scheme:dark) { <NestedDeclarationsRule> }`, mirroring `get_additional_rules`. Keep the order the `Style` branch uses: logical first, then supports.

2. **should fix / maintainer decision: fallbacks emitted for overridden declarations (pre-existing for plain rules, newly reached for nested declarations).** Input `.a{.b{color:red} --x:lab(60% 50 50); --x:blue; color:var(--x)}` with `--minify --targets 'chrome 110'`:
   - base: `.a .b{color:red}.a{--x:blue;color:var(--x)}` (equivalent)
   - PR: `….a{--x:blue;color:var(--x)}@supports (color:lab(0% 0 0)){.a{--x:lab(60% 50 50)}}`. Browser: NOT EQUIVALENT, the `.a` color becomes lab instead of blue.

   The same happens for unparsed shorthands. `border:var(--w) solid lab(…); border:3px solid blue` after a nested rule: the PR emits `@supports{…border:var(--w) solid lab(…)}`, which overrides the 3px border (32 diffs, height 22px→20px). For flat rules, base already does this: `.a{--x:lab(60% 50 50);--x:blue}` gives `.a{--x:blue}@supports(...){.a{--x:lab(…)}}`, NOT EQUIVALENT. So the root cause is in fallback collection (`add_conditional_fallbacks` / `add_unparsed_fallbacks` queue entries that a later declaration in the block overrides), not in this PR. Still, the PR turns correct base output into wrong output for these inputs. Options:
   - fix the root cause first: drop a queued supports entry when a later declaration of the same property in the same importance bucket supersedes it;
   - or accept the regression and file it separately.

3. **nit: tests.**
   - The PR's tests cover only custom properties with `lab()` and only pretty-printed `nesting_test` output (no `minify_test`).
   - No test covers:
     - a regular property after a nested rule (`border: var(--w) solid lab()`, unparsed);
     - `!important` (works: `@supports{.a{--x:lab(60% 50 50)!important}}`);
     - nested declarations inside `@media`/`@supports` within a style rule (both work);
     - multiple supports conditions (p3 + lab with `safari 14, chrome 100`; works, same order as flat rules);
     - keeping nesting (the nested-`@supports` print path).
   - Keeping nesting cannot be reached from the CLI: every browser that supports nesting also supports lab/p3/color-mix. It needs the `exclude: Features.Nesting` API path. A Rust test with `Features::Nesting` excluded would cover the nested-`@supports` serialization.

No API/AST changes. `take_nested_supports_rules` is `pub` on a `pub(crate)` type, so it is not public API. No generated files touched.

## Tooling feedback
- **equivalence.mjs: color-string false positives.** Computed colors are compared as strings, so `oklch(0.96 0.08 58)` vs `lab(95.1084 15.5897 27.2018)` (the same color re-expressed by Lightning CSS) counts as a diff. In the first run 40/115 outputs were "NOT EQUIVALENT", nearly all from this. Even `--minify` with no targets was flagged (`oklch(0.6 0.2 250)` → `oklch(60% .2 250)` on a custom property). Suggestions:
  - normalize colors before comparing (convert both to one space with a small tolerance);
  - treat a custom property's token-text change as a separate, lower-severity diff class, or allow ignoring it with a flag.

  Without this, any color-lowering PR review needs a hand-written lab-only rerun.
- **equivalence.mjs: no `prefers-color-scheme: dark`.** It never emulates dark mode, so `light-dark()`/`color-scheme` lowering bugs pass (F3 above). It should add a dark scheme to the matrix when the CSS mentions `light-dark`, `color-scheme` or `prefers-color-scheme`. The same probably applies to `prefers-reduced-motion`, `print`, etc.
- **cases.mjs:**
  - There is no summary that separates "regression" (base equivalent → PR not) from "fixed" (base not → PR equivalent) and "pre-existing". I had to scrape the text output with awk.
  - Base is browser-checked only when the output changed, so unchanged-but-broken cases don't show "pre-existing" explicitly.
  - Repeated sample lines across fixtures make the text output long. A `--summary` mode would help.
- **CLI gap:** the CLI has no `--include`/`--exclude` feature flags. "Keep nesting but lower colors" (`exclude: Features.Nesting`) can't be tested through `build-pr.sh` binaries, even though real users (bundlers) hit that path.
- **build-pr.sh:** worked (`PR_BIN`/`BASE_BIN` printed, worktree at `target/review/pr-1386/src`). It is quiet until it finishes, which is fine in the background. No problems.
- **Skill gaps:**
  - Step 2 depends on a "web-fetch agent" and on `drafts.csswg.org`. Neither was available here (no Agent tool in this subagent, and the host is blocked by the network allowlist). A local snapshot of the relevant specs, or a stated fallback, would help.
  - `css-pitfalls.md` should gain entries for:
    - (a) `PropertyHandlerContext` side channels (`supports`, `ltr`/`rtl`, `dark`): any rule type that minifies declarations must emit **all** of them and reset, or they leak into the next sibling;
    - (b) "fallbacks for overridden declarations": a queued `@supports` override can resurrect a value a later declaration replaced (`--x:lab(); --x:blue`).
  - The skill could also note that the oracle lacks dark mode, so color-scheme/light-dark work needs a manual check.
