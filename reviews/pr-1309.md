# PR #1309: Fix invalid selectors
**Verdict:** approve with nits (suggest porting two more upstream checks). **Confidence:** high.

Built with `build-pr.sh --on-master 1309` (merges cleanly): PR head 18f1cb6 on master 574eee24.
PR_BIN=target/review/pr-1309-on-574eee24/lightningcss, BASE_BIN=target/review/base-574eee24/lightningcss.

## Summary
`parse_has` in `selectors/parser.rs` now parses its `<relative-selector-list>` with `ParseErrorRecovery::DiscardList` (unforgiving) and sets `DISALLOW_PSEUDOS`. So `:has()`, `:has(::before)`, `:has(.x, ::before)` and `:has(.x, slot="s")` become parse errors (strict) / warning + dropped rule (`--error-recovery`), as in browsers. The bug is real: master turns invalid selectors into *different* ones, sometimes valid ones that change rendering:
- `.a:has(.x, slot="s")` -> `.a:has(.x)` (rule becomes valid; equivalence NOT EQUIV, 68 diffs)
- `.a:where(.b, :has(.x, ::before))` -> `.a:where(.b,:has(.x))` (the inner :has becomes valid; NOT EQUIV)
- `video:not(:has(::backdrop))` -> `video:not(:has())`, `a:has(::before)` -> `a:has(:before)`, `.a::part(x):has(.y)` -> `.a::part(x):has()`, `.a::before:has(.x)` -> `.a:before:has()` (invalid in, mangled invalid out).

## Design
- Matches upstream servo/stylo exactly for the core change. Upstream `parse_has` (stylo main, `selectors/parser.rs` ~L3452):
  ```rust
  if state.intersects(SelectorParsingState::DISALLOW_RELATIVE_SELECTOR | SelectorParsingState::AFTER_PSEUDO) {
      return Err(ParseError::custom(SelectorParseErrorKind::InvalidState));
  }
  let inner = SelectorList::parse_with_state(parser, input,
      state | SKIP_DEFAULT_NAMESPACE | DISALLOW_PSEUDOS | DISALLOW_RELATIVE_SELECTOR,
      ForgivingParsing::No, ParseRelative::ForHas)?;
  ```
  The PR has the `DISALLOW_PSEUDOS` + unforgiving part. It lacks:
  1. `DISALLOW_RELATIVE_SELECTOR`: nested `:has()` is still accepted (`.a:has(.x:has(i))` passes through on both builds; Chromium drops the rule; spec: ":has() is not valid within :has()").
  2. The up-front `AFTER_PSEUDO` check: `.a::before:has(:hover)` is still accepted (-> `.a:before:has(:hover)`; Chromium rejects). `::part(x):has(.y)` / `::before:has(.x)` now error only incidentally, with a misleading message ("Pseudo-elements like '::before' or '::after' can't be followed by selectors like Delim('.')") because the outer `AFTER_PSEUDO_ELEMENT` state leaks into the :has() argument.
  Both are a few lines in the same function; lightningcss has no `DISALLOW_RELATIVE_SELECTOR` flag yet (bit 8 is taken by `AFTER_WEBKIT_SCROLLBAR`, so a new bit is needed). The flag also needs to propagate through `:is()/:where()` so `:has(:is(:has(c)))` becomes `:has(:is())` like Chromium (forgiving drop). Upstream also adds `SKIP_DEFAULT_NAMESPACE` (minor, untested here).
- Fits philosophy: strict error on known invalid syntax; error recovery drops the rule with a warning, like a browser (browser drops the whole rule for an invalid selector). Unknown pseudo-classes (`:has(.x, :foo)`) still pass through, consistent with existing policy.
- `is_and_where_error_recovery()` hook is not overridden anywhere in `src/`, so hard-coding `DiscardList` for :has loses nothing.

## #1239 and :is()/:where()
Not a bug for :is/:where. Spec (selectors-4 §16.1, https://drafts.csswg.org/selectors-4/#parse-as-a-forgiving-selector-list): "Remove all failure items from selector list, and all items that are invalid selectors, then return a <selector-list> representing the remaining items in selector list. (This might be empty.)" Chromium 153 CSSOM: `a:is(::before){}` serializes as `a:is() { color: red; }`, `b:where(::before, .x)` as `b:where(.x)` — exactly master's output. cases.mjs: ok/equivalent on all configs. Upstream stylo keeps invalid items verbatim (`Selector::new_invalid`) in forgiving lists, a serialization-fidelity choice, not a behavior difference. So the PR closing #1239 is right: the only real bug in it is :has (unforgiving).

## Spec
https://drafts.csswg.org/selectors-4/#relational: ":has() ... taking a <relative-selector-list> as an argument. ... The :has() pseudo-class cannot be nested; :has() is not valid within :has(). Also, unless explicitly defined as a :has-allowed pseudo-element, pseudo-elements are not valid selectors within :has(). (This specification does not define any :has-allowed pseudo-elements, but other specifications may do so.)"
§16.1: "<forgiving-selector-list> is used in :is() and :where() only." / "intentionally used only in :is() and :where(), not in any other selector that takes a selector argument."
Chromium 153 agrees: `a:has(.x, ::before)`, `a:has()`, `a:has(:before)`, `a:has(b:has(c))`, `::before:has(a)`, `::part(x):has(a)`, `a:has(::-webkit-scrollbar)`, `a:has(::slotted(b))` all dropped; `a:has(:is(b:has(c)))` -> `a:has(:is())`.

## Findings
1. should fix (cheap, same function): port upstream's `DISALLOW_RELATIVE_SELECTOR` (nested :has) and `AFTER_PSEUDO` early return. Repros: `.a:has(.x:has(i)){color:red}` base/PR `.a:has(.x:has(i)){color:red}`, Chromium drops rule. `.a::before:has(:hover){color:red}` base/PR `.a:before:has(:hover){color:red}`, Chromium drops rule. Pre-existing, not regressions.
2. nit: `SelectorError::InvalidState` gives users "Invalid state" for `:has(::before)`; a dedicated error message (e.g. "pseudo-elements are not allowed inside :has()") would be friendlier. Node tests assert the string 'Invalid state', so changing it later would touch those.
3. Follow-up, separate (not this PR): `parse_nth_pseudo_class` `of S` uses `IgnoreInvalidSelector` (forgiving); upstream uses `ForgivingParsing::No`. `li:nth-child(2 of ::before)` -> `li:nth-child(2 of )` (invalid output) on both builds; `li:nth-child(2 of .a, ::before)` -> `li:nth-child(2 of .a)`. Note Chromium 153 accepts and preserves `:nth-child(2 of .a, ::before)`, so the right fix needs checking; `2 of .a, :foo` is dropped by Chromium (unforgiving).

No regressions found. All PR-blocked inputs are rejected by Chromium too, incl. newly erroring `:has(::part(x))`, `:has(::slotted(x))`, `:has(::view-transition-group(x))`, `:has(::highlight(x))`, `:has(::-webkit-scrollbar)` (no spec defines any :has-allowed pseudo-element).
