## Summary

The bug is real. When a declaration's value is unparsed (usually because of `var()`), the handler calls `UnparsedProperty::get_prefixed()` and pushes the result. An authored `-webkit-X: v; X: v` pair then becomes `-webkit-X: v; -webkit-X: v; X: v`, and it grows again on every re-minify. For parsed values the handlers already accumulate prefix bits. Issue #969 (mask-image) is the open report. Repro on master, `--minify --targets 'chrome 90'`:

```
.a{-webkit-mask-image:var(--i);mask-image:var(--i)}
→ .a{-webkit-mask-image:var(--i);-webkit-mask-image:var(--i);mask-image:var(--i)}
```

The bug matters on real CSS. #1334 removes 28 duplicate `-webkit-text-decoration-color: … !important` lines from Bootstrap's `.link-*` utilities (−2,808 B, −1.2% with older targets).

All three PRs use the same mechanism: compare with `dest.last_mut()` only, and if it is the same unparsed property (modulo prefix) with identical tokens, OR the prefix bits into it. The maintainer asked for exactly this shape on #1339. It's O(1) per declaration, so there's no quadratic risk.

- **#1339** inlines it in `MaskHandler` for `mask-image` only.
- **#1295** adds a reusable helper `UnparsedProperty::merge_prefixes_into_last(&self, &mut [Property]) -> bool` (custom.rs). It uses it in `MaskHandler` for *all* mask properties, and also in `PropertyHandlerContext::add_conditional_property` so the generated `@supports (color: lab())` fallback blocks are deduplicated too.
- **#1334** inlines the same check a third time in `TextDecorationHandler` (text-decoration*/text-emphasis*). It doesn't touch the `@supports` fallbacks.

## Design

**One shared place.** The same bug exists at every `get_prefixed` push site on master. Repro with `-webkit-P: var(--x); P: var(--x)` and `--targets 'chrome 20' --targets 'safari 5' --targets 'firefox 10'`:

| handler (file:line on master) | duplicated? | covered by |
|---|---|---|
| transition (`transition.rs:234`) | yes | none |
| animation (`animation.rs:875`) | yes | none |
| transform (`transform.rs:1781`) | yes | none |
| mask-image / mask / mask-* (`masking.rs:707`) | yes | #1295 (all mask-*), #1339 (mask-image only) |
| text-decoration*, text-emphasis* (`text.rs:1196,1202`) | yes | #1334 |
| border-radius (`border_radius.rs:202`), border-image (`border_image.rs:458`) | same push pattern; with these targets no extra prefix was added, so not observed | none |
| prefix_handler / fallback handler | no (index replacement) | n/a |

The maintainer prefers fixes that automatically cover future properties (calibration #1416). The right shape is #1295's helper, renamed to something like `push_unparsed(dest, unparsed)`, on `DeclarationList` or `UnparsedProperty`. It should be called at every site that pushes a `get_prefixed` result, plus the `@supports` path in `context.rs` (which #1295 already does). That is roughly 8 one-line call-site changes. Two alternatives:
- (a) A single O(n) post-pass over `handler.decls` at the end of `DeclarationBlock::minify` (after `finalize`; the `custom_properties` indices are already cleared). It covers future handlers with no call-site discipline.
- (b) A `get_prefixed_into(dest, …)` that does get-prefix + merge + push together.

I'd go with the helper at the call sites, because it keeps the adjacency semantics exactly where the handler has flushed its own buffered longhands. Shared fallback paths keep the generated `@supports` blocks in sync.

**#1295 is a strict superset of #1339.** In my cases file, every mask-image case that #1339 changes, #1295 changes to the identical main-rule output. #1295 also removes the duplicate inside the generated `@supports (color: lab())` block, which #1339 leaves:

```
in:  .a{-webkit-mask-image:linear-gradient(lab(56% 94 98),lab(51% 70 -115)),var(--f);mask-image:…same…}   --minify --targets 'chrome 90'
1339: …@supports (color:lab(0% 0 0)){.a{-webkit-mask-image:…;-webkit-mask-image:…;mask-image:…}}
1295: …@supports (color:lab(0% 0 0)){.a{-webkit-mask-image:…;mask-image:…}}
```

#1334 has the same `@supports` gap (its description admits it). With `text-decoration: underline lab(56% 94 98) var(--s)` and Safari 14, the `@supports` block still has `-webkit-text-decoration` twice.

**Recommended path:** land one PR, #1295 extended to all handlers with the guard from finding 1. Port #1334's and #1339's tests into it (they're good boundary tests: importance, intervening longhands, different values, rule/`@media` boundaries). Then close #1339 and #1334, or have SyMind rebase #1334 onto the helper if it lands first.

Project philosophy: fine. Declarations stay `Unparsed` because they contain `var()`; no new token storage, no hacks, no flags needed.

## Spec

- Invalid substitution, css-values-5 ([Overview.bs](https://raw.githubusercontent.com/w3c/csswg-drafts/main/css-values-5/Overview.bs), §Invalid Substitution): "When property replacement results in a property's value containing the guaranteed-invalid value, this makes the declaration invalid at computed-value time. … the computed value is … either the property's inherited value or its initial value … as if the property's value had been specified as the 'unset' keyword."

  So a declaration containing `var()` is always valid at parse time and never falls back to an earlier declaration. Removing an *identical adjacent* duplicate of the same property is therefore cascade-neutral.
- Merging a prefixed and an unprefixed declaration is a different case. It is only neutral if the declaration that comes **last** among properties sharing longhands stays last, or if the two properties treat the substituted value identically. The merged property serializes in prefix order (`-webkit-`, …, unprefixed). The compat spec's legacy alias list (`-webkit-mask-image` → `mask-image`) would make the mask-image case neutral, but I couldn't fetch compat.spec.whatwg.org (proxy 403), so that is unquoted.

## Findings

1. **Should fix (all three; not observable in Chromium): the merge can reorder an authored `X: v; -webkit-X: v` pair.** When the earlier output declaration already carries the unprefixed bit and the later one is prefix-only, merging moves the winner from `-webkit-X` to `X`. Examples:
   - #1334, `--minify` without targets: `.a{text-emphasis:filled var(--m);-webkit-text-emphasis:filled var(--m)}` → `-webkit-text-emphasis…;text-emphasis…`. Master keeps the order.
   - #1339/#1295, `--minify` without targets: `mask-image:var(--i);-webkit-mask-image:var(--i)` → `-webkit-mask-image:var(--i);mask-image:var(--i)`.
   - With targets, the authored trailing `-webkit-X` is absorbed into `-webkit-X; X`. Master: `-webkit-td v; td v; -webkit-td v`. PR: `-webkit-td v; td v`.

   This only matters where the prefixed and unprefixed properties accept different values after substitution. Chromium's `CSS.supports('-webkit-text-decoration','underline 3px')` is false and `CSS.supports('text-decoration','underline 3px')` is true. Even so, with `--t:3px`, both orders compute `text-decoration-line: underline; thickness: 3px` in Chromium (probe), and every case was browser-equivalent. So I found no observable difference; Safari (separate `-webkit-text-decoration` shorthand) is unverified.

   Suggested guard in the shared helper: don't merge when the previous declaration has `VendorPrefix::None` and the new one doesn't (`!(prev.contains(None) && !new.contains(None))`). This keeps master's behavior for the unusual "unprefixed then prefixed" order and still fixes the common `-webkit-X; X` and `X` + auto-prefix cases. It costs bytes only in that unusual order.
2. **Should fix (#1334, #1339): duplicates remain in the generated `@supports` color fallback blocks** (repros above). #1295 handles this in `context.rs`.
3. **Nit (#1334, and by construction the helper): a merged multi-prefix declaration loses its authored prefix when the block is minified a second time.** This happens when same-selector rules merge. `.a{-webkit-text-decoration:underline var(--c);text-decoration:underline var(--c)} .a{--c:red}` with `--minify --targets 'chrome 90'`:
   - master: `.a{-webkit-text-decoration:…;text-decoration:…;--c:red}`
   - #1334: `.a{text-decoration:underline var(--c);--c:red}`

   The cause: the second `get_prefixed` pass sees `webkit|none`, which includes `None`, so it recomputes the prefixes from targets. Chrome 90 doesn't need `-webkit-`, so this matches how parsed values are already treated (master turns `-webkit-text-decoration:underline red;text-decoration:underline red` into `text-decoration:underline red` for chrome 90). Not a correctness bug for the targets given. But it contradicts #1334's own test comment "Explicit prefixes are retained even if the targets do not require them", which only holds for a single, unmerged rule.
4. **Rebase (#1295):** its new `test_svg` expectation fails on current master only because master's lab→sRGB conversion changed since the PR's base. Expected `#ff0f0e, #7773ff`, master now gives `#ff0b0c, #766eff`. The code is fine; the expected hex needs updating. #1334's and #1339's tests pass on master.
5. **Nit (#1339):** the PR description still describes the removed backward scan.
