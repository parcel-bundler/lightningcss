# PR #1250: Don't deduplicate `font-family: monospace, monospace`
**Verdict:** approve with nits. **Confidence:** high.

## Summary
`FontHandler::flush` dedupes every `font-family` list, so `monospace, monospace` (the normalize.css idiom) becomes a lone `monospace`. This happens with and without `--minify`, and in the `font` shorthand too. A lone generic `monospace` makes the browser use its smaller "fixed" default font size. The PR keeps two entries when every entry is generic `monospace` (`truncate(2)`) and dedupes everything else as before. Fixes #1221. The bug is real in current browsers: in Chrome 153, `font-family:monospace` gives 13px, while `monospace,monospace` gives 16px. That contradicts the earlier comment on the issue that only ancient browsers are affected.

## Design
- **General rule:** No spec text governs this. It is long-standing UA behavior: there is a separate default size for the `monospace` generic, Chrome's "fixed font size" and Gecko's `font.size.monospace.*`. Probe on Chrome 153:

  | font-family | font-size |
  |---|---|
  | `monospace` | 13px |
  | `MONOSPACE` | 13px |
  | `monospace; font-size: medium` | 13px |
  | `monospace,monospace` | 16px |
  | `monospace,monospace,monospace` | 16px |
  | `monospace,ui-monospace` | 16px |
  | `ui-monospace` | 16px |
  | `ui-monospace,ui-monospace` | 16px |
  | `serif` | 16px |

  So the only list whose dedupe changes rendering is an all-`monospace` list, which collapses to a single `monospace`. The PR's condition matches exactly that set. Other duplicates leave ≥2 entries or a non-monospace generic, so deduping them stays safe.
- **Placement:** `FontHandler::flush` is the only place that dedupes. It serves both `font-family` and `font` (shorthand parse, and longhands combined into `font`), so the fix applies everywhere at once. There is no copy-paste and no better shared type.
- **Complexity:** One extra O(n) `iter().all()` per flushed family list. Negligible.
- **Philosophy:** Not a hack for old browsers. Current Chromium shows the behavior, and normalize.css still ships the idiom.

## Spec
CSS Fonts 4 (https://drafts.csswg.org/css-fonts-4/) does not define a per-generic default size. A grep of the ED for `monospace` near `size` finds only the WPT test name `rem-in-monospace.html`, so no quote can be given. The reporter says the same. The behavior is de facto UA behavior, verified in Chromium only.

   - `font: 1em monospace, monospace`, to cover the shorthand;

No blocking issues.

## Edge cases checked
22 cases × 3 configs (`--minify`; `--targets 'chrome 60'`; `--minify --targets 'safari 12' --targets 'chrome 90'`). Each case had an HTML fixture with no ancestor absolute font-size. Results: 36 fixed, 18 still-broken, 12 ok, 0 regressions.

| case | result |
|---|---|
| `monospace,monospace`; with `font-size:1em` / `2em`; uppercase `MONOSPACE,Monospace`; `!important`; inside `@media`; nested `&{}`; adjacent rules merged; `font-size:smaller` on a child; `font:1em monospace,monospace`; longhands combined into `font`; `font-family:monospace;font-family:monospace,monospace` | **fixed** in all configs (base drops to 13px-derived sizes, 52–104 diffs) |
| `monospace,monospace,monospace` → `monospace,monospace` | still-broken, but only in the computed `font-family` string (oracle artifact). Font sizes are equal. |
| neighbors: `Menlo,Menlo,monospace`, `monospace,monospace,serif`, `serif,serif`, `system-ui,monospace,monospace`, `ui-monospace,ui-monospace` | unchanged from base. "still-broken" is only the computed `font-family` string from the pre-existing dedupe, with no rendering difference. |
| `monospace,"monospace"`, lone `monospace`, `--f:monospace,monospace;font-family:var(--f)`, `monospace,monospace;font-family:monospace` | ok, unchanged |

Every non-equivalence in the PR outputs is the `font-family` computed string only. No other properties differ.
