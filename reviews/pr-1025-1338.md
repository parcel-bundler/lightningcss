# PRs #1338 and #1025: shorter quoting for strings and url()

- **#1338** "fix: choose shorter quotes for minified URLs" (SyMind). **Verdict:** approve on correctness, but needs a maintainer decision because it overlaps #1025. **Confidence:** high.
- **#1025** "Add custom serialize_string function producing shorter representation" (mina86). **Verdict:** request changes (blocking correctness bug). **Confidence:** high.

Builds: #1338 merged onto master 574eee2 (`target/review/pr-1338-on-574eee24`). #1025 does **not** merge onto current master (conflict in `src/printer.rs` with #1354's UTF-16 column change; trivial). It was built on its own base 4a1b083 (`target/review/pr-1025`). Neither PR has CI check runs.

## Summary

Both PRs serialize a string with single quotes when it contains more `"` than `'`, and keep double quotes on ties. That's the same rule in both.
- **#1338** applies it only to `url()` under `--minify`, with a small single-quote writer in `values/url.rs`. Its output is correct in every test I ran.
- **#1025** adds `crate::serialize::string`, replacing `cssparser::serialize_string` at every lightningcss call site: url, image-set, `@import`, font-family, `@font-face format()`, quoted animation/keyframes names, CSS-module `from`, attribute selector values and `CSSString`. It applies in both minified and pretty output. It also drops the space after a hex escape unless the next byte is a hex digit, and that part is wrong: when the next character is a literal U+0020 space, the space is lost on re-parse. This changes URLs, font family names and **which elements attribute selectors match**.

Neither PR fixes a correctness bug. The benefit is bytes in strings with many `"` (mainly SVG data URIs with double-quoted attributes). The whole size corpus shows **0 bytes change** for both PRs, with and without targets.

## Design

- **Is there a general rule?** Yes: CSSOM always uses `"`, but any string token may use either quote. The general place is one crate-level string serializer, which is #1025's design. #1338 fixes only `url()`. It misses font-family, `@import`, attribute values, image-set `type()` and others, which #1025 covers.
- **Coverage of #1025.** It still misses `Token::String` in `properties/custom.rs:853` (unparsed values, including `content`, the most string-heavy property) and `selectors/parser.rs:3257`. On the PR build, `content:'say "hi"'` still outputs `"say \"hi\""`.
- **Supersede?** A fixed #1025 subsumes #1338: `Url::to_css`'s quoted branch would call the shared serializer and pick the same quote. The two PRs conflict in `values/url.rs`. Recommendation:
  - Ask #1025 to fix the space bug, drop `cssparser-macros = "*"` (a plain `match` works) and rebase. Then take #1025 and close #1338 as superseded, crediting its tests.
  - #1338's round-trip and source-map tests are worth carrying over.
  - If the maintainer prefers a minimal, correct change now, #1338 can merge as-is, and #1025 then rebases onto it and removes `serialize_single_quoted_string`.
- **Philosophy.** No concerns. Quote choice in non-minified output (#1025) is a visible output change, though harmless. Reusing `cssparser::CssStringWriter` for everything except quotes (#1338) is safe, because cssparser's `hex_escape` *always* writes a terminating space (`cssparser-0.37 src/serializer.rs:162-179`). That makes the slice boundaries in `serialize_single_quoted_string` irrelevant.

## Spec

CSS Syntax 3, [§4.3.7 Consume an escaped code point](https://drafts.csswg.org/css-syntax-3/#consume-escaped-code-point):
> Consume as many hex digits as possible, but no more than 5. … If the next input code point is whitespace, consume it as well.

So after `\1`, one following whitespace code point is always eaten. A literal space after a hex escape therefore needs a terminator space before it (`\1  b`). Inside a string serialized by either PR, U+0009/000A/000C/000D are themselves hex-escaped, so U+0020 is the only raw whitespace that can follow.

CSSOM [serialize a string](https://drafts.csswg.org/cssom-1/#serialize-a-string):
> Note: "'" (U+0027) is not escaped because strings are always serialized with '"' (U+0022).

That governs CSSOM serialization only. The syntax accepts either quote, and Chromium parses both identically (all equivalence runs below).

## Findings

1. **#1025, blocking: a literal space after an escaped control character is lost.** `hex_escape` emits the terminator only when the next byte is a hex digit.

   | input | base | #1025 |
   |---|---|---|
   | `background-image:url('x y\1  z.png')` (`--minify`) | `url("x y\1  z.png")` | `url("x y\1 z.png")` |
   | `font-family:"x\1  y",serif` | `"x\1  y"` | `"x\1 y"` |
   | `[title="\1  b"]` | `[title=\1 \ b]` | `[title="\1 b"]` |

   - Chromium: the computed `background-image` and `font-family` differ (cases.mjs: regression in both `--minify` and `--targets 'chrome 80'`).
   - Chromium, attribute selector: with `title="\x01 b"`, `matches('[title="\\1  b"]')` is `true` and `matches('[title="\\1 b"]')` is `false` (probe.mjs). So the selector stops matching.
   - The same bug hits `\a` (a newline) followed by a space, and any other control character.
   - Exhaustive check: 4096 strings (`""` + every 4-char combination of `" ' \x01 space a g \ \n`) in `url()` and `font-family`. #1025 gives 1452 computed-style differences, *all* of them an escape followed by a space. #1338 and both bases give 0.
   - **Fix:** `next.map_or(false, |b| b.is_ascii_hexdigit() || *b == b' ')`, plus tests for `"\x01 b"` and `"\n b"`. I didn't prototype it (shared build budget), but it follows directly from the spec text above and the fact that other whitespace is escaped.
2. **#1025, blocking for release: `cssparser-macros = "*"` in `Cargo.toml`.** crates.io rejects wildcard dependency versions at publish. `match_byte!` gains nothing on a 6-arm match. Use a plain `match` and drop the dependency.
3. **#1025, should fix: rebase.** It conflicts with master in `src/printer.rs` (from #1354). The PR's only test is a 7-row unit test in `src/serialize.rs`, with no integration tests in `src/lib.rs`. It needs `minify_test`s for url, font-family, attribute selectors and `@import`, including the escape-then-space case.
4. **#1025, nit.** Remove the `unsafe { from_utf8_unchecked }` in `hex_escape`: the buffer is ASCII, so `std::str::from_utf8(..).unwrap()`, or writing chars directly, costs nothing measurable. Also, `crate::serialize::identifier`/`name` are pure re-exports. The rename touches 10 files for no behavior change, which is fine as an indirection point but enlarges the diff.
5. **#1338, nit.** The single-quote path is url-only and minify-only. That's by design, but a later generalization (#1025) makes `serialize_single_quoted_string` redundant.
6. **Pre-existing, out of scope (both bases).** Not caused by either PR. Neither PR needs to fix them.
   - `.a{--x:'say "hi"'}` minifies to `--x:"say \"hi\""`, and Chromium reports a different computed `--x` (the custom property's token text is observable).
   - `font-family` strings with leading or trailing spaces lose them (`"é "` → `é`). This showed up in a font-family fuzz on the base build.

## Tests & performance

- #1338: `cargo test --lib --all-features url` (4 tests including `test_url_quote_roundtrip`, 2,744 combos) pass.
- #1025: `cargo test --lib --all-features` passes (125 tests). No existing expectation changed, because no existing test has a string with more `"` than `'` or a control character.
- `scripts/size-check.sh`, both PRs vs their bases, with no targets and with chrome 80 / safari 13 / firefox 78: **0 bytes and no timing change on every corpus file** (synthetic, react-spectrum S2, Radix, Bootstrap, Bulma, Primer, Pico, animate.css, Open Props, Font Awesome, normalize). Real-world SVG data URIs in these packages already use single-quoted attributes or percent-encoding.
- Perf: #1338 adds one byte-count pass, only when the quoted form may win. #1025 adds one counting pass per serialized string. Both are negligible, and neither was benchmarked separately (CLI timings unchanged in size-check).

## Not verified

- Firefox and WebKit parsing of the outputs (Chromium only). Single-quoted strings and escape terminators are basic tokenizer behavior, so this is low risk.
- The proposed #1025 space fix was not built.
- `yarn test` / WPT baseline were not run (no binding changes).
- Dependency placeholders: with #1025 they still serialize with double quotes, since a placeholder hash contains no quotes. #1338's `test_url_quoting_dependencies` covers its own path.
