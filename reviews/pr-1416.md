# PR #1416: fix: preserve units of zero lengths in values that also accept numbers
**Verdict:** approve with nits. **Confidence:** high (Chromium-verified; spec text not quoted, see "Not verified").

Head `f07ab9f` (fork `giuliowaitforitdavide/lightningcss`, opened by devongovett), base `4a1b083`. Builds: `target/review/pr-1416/lightningcss` and `target/review/base-4a1b083/lightningcss`.

## Summary
The printer flag `in_calc` becomes `preserve_zero_units`, and a scoped helper `Printer::with_zero_units` is added. It is turned on when printing the length branch of `LengthOrNumber` (border-image-outset, mask-border-outset, -webkit-mask-box-image-outset, tab-size), `BorderImageSideWidth` (border-image-width, mask-border-width, -webkit-mask-box-image-width) and `LineHeight` (line-height and the `/lh` part of `font`). It is also on for `@property` `initial-value` when the syntax contains a `<number>` or `<integer>` component, but only for lengths at the top level of the syntax (not inside functions). The bug is real, and it is worse than the PR description says. On base, `0px` → `0` changes the type from length to number. Animations and transitions between the two are discrete. For tab-size, border-image-outset/width and mask outset, the static computed value changes too (Chromium reports `0` instead of `0px`; the oracle flags the base output as NOT EQUIVALENT even without animation). With `<number> | <length>`, `<integer> | <length>`, `<length-percentage> | <number>` and `<number># | <length>#` syntaxes, the base build changes the `@property` initial value from a length to a number. The PR fixes every case I found, and all PR outputs are browser-equivalent.

## Spec
- I could not fetch drafts.csswg.org or drafts.css-houdini.org: DNS fails in this sandbox (not on the allowlist), and no web-fetch agent was available to me. **No spec quotes.** From memory and unverified: css-values-4 §6.1 notes that when `0` could parse as either `<number>` or `<length>` (e.g. `line-height`), it parses as a `<number>`.
- Secondary source, local `mdn-data/css/properties.json` (derived from the specs):
  - `line-height: normal | <number> | <length> | <percentage>`; animation type `numberOrLength`; computed: absolute length, or as specified.
  - `border-image-outset: [ <length> | <number> ]{1,4}`; animation type `byComputedValueType`; computed: as specified, relative lengths made absolute. `border-image-width` (`<length-percentage> | <number> | auto`) is the same.
  - `mask-border-outset` / `mask-border-width`: same grammars.
  - `tab-size: <integer> | <length>`; computed: "specified integer or absolute length".
  - These are the only properties in mdn-data whose grammar includes both `<number>` and `<length>`. The PR covers all of them.
- Browser evidence that `@property` components match **in order** (Chromium): with `syntax:'<length>|<number>'`, `initial-value:0` gives the same computed `--p` as `0px`, so the `0` matched `<length>`. With `'<number>|<length>'`, `0` and `0px` differ (base NOT EQUIVALENT). `'<angle>|<length>'` with `0` is equivalent to `0px`: `<angle>` does not take a unitless zero, so it is correct that the PR doesn't preserve the unit there.

## Findings
1. **nit: `@property` preservation ignores component order, so it over-preserves.** `SyntaxString::accepts_unitless_zero_as_number` returns true whenever *any* component is `<number>`/`<integer>`. Since components match in order (see above), preserving the unit is unnecessary when the length component comes first, or when a multi-value list can't match a single `<number>`.
   - `@property --p{syntax:'<length> | <number>';initial-value:0}`: base `initial-value:0` (equivalent). PR `initial-value:0px` (equivalent, +2 bytes). The PR enshrines this in a test, and the test comment even says "Components are matched in order, so a unitless zero is parsed as a <length> here".
   - `syntax:'<number> | <length>+';initial-value:0px 0px`: base `0 0` (equivalent, since two values can't match `<number>`). PR `0px 0px`.
   - The cost is only bytes in rare `@property` rules (0 bytes changed on ~510 KB of real CSS; see below). Optional fix: preserve only when a `<number>`/`<integer>` component comes before the first component that accepts a length. The current over-approximation is safe.
2. **nit: a new test enshrines a pre-existing CSSOM difference.** The new test `syntax:'<number> | <transform-list>'; initial-value: translate(0px, 0px)` → `translate(0)` is labeled "Lengths nested in other values are not ambiguous". That is true for the unit question. But Chromium's computed value of the registered property changes from `translate(0px, 0px)` to `translate(0px)`: the oracle reports NOT EQUIVALENT on **both** base and PR (unchanged output). The cause is the existing transform minification (dropping the second argument), not this PR. Consider dropping this case from the test, or using a value whose minified form round-trips, so the test doesn't look like an approval of that behavior. Low severity: the rendering is identical.
3. **nit: test coverage.** All new tests are `minify_test`. There is no pretty-printed (non-minify) case and no targets case, though the CLI shows the same behavior there (`font: 12px / 0px serif`, `border-image-outset: 0px 0 0em 1px`). There is also no `@keyframes` test for line-height/tab-size; the transition test is a source-level stand-in. Optional.

No blocking issues. Public API and the AST shape are unchanged: `in_calc` was `pub(crate)`, the hand-written `ToCss` impls replace derives of the same trait, and the new helpers are `pub(crate)`. The changed expectations (`calc(1px - 2px)` → `0px` for border-image-outset/width, tab-size and line-height) are justified: on base, `calc(1px - 2px)` → `0` makes tab-size/border-image-outset NOT EQUIVALENT in Chromium, and the PR's output is equivalent. `font-size` correctly keeps `0`.

The remaining rows were unchanged and equivalent:
- `var()` and custom property neighbors (`--x:0px`, `line-height:var(--y,0px)`).
- `margin`/`width`/`letter-spacing`/`perspective`/`transform`/`text-indent`/`box-shadow` with `0px`.
- `flex: 1 1 0px`, `flex:0px`, `flex-basis:0px`, `flex:2 0px` (already handled by `Flex::to_css`), plus a flex keyframe.
- `stroke-width`/`stroke-dashoffset`/`stroke-dasharray` 0px, static and in keyframes. Chromium treats unitless SVG lengths as px and interpolates them smoothly, so they are not affected.
- `@property` with `<angle>|<length>` (correctly still `0`), `<length>` only (still `0`), `<number>|<time>` `0s`, and `<number>|<length-percentage>` `calc(0px + 0%)` → `0%`.
- `rotate` / `skew` with zero angles.

Sibling completeness: every property in mdn-data whose grammar includes both `<number>` and `<length>` is covered. I grepped `src/properties` and `src/values` for enums with a `Number`/`Integer` variant. The others are `animation-iteration-count`, grid line integers, the `z-index`-like position integer, and gradient/percentage number-or-percentage; none of them has a length alternative.

## Not verified
- Spec text: drafts.csswg.org and drafts.css-houdini.org are unreachable from this sandbox, so no verbatim quotes. The grammar and animation-type facts come from mdn-data and Chromium behavior.
- Firefox and Safari behavior: Chromium only. In particular, I did not check whether Firefox/WebKit match `@property` syntax components in order (this matters only for finding 1, which is a size nit).
- Transition interpolation is not observed by the oracle (it finishes CSSTransitions). The equivalent `@keyframes` cases were used instead.
- `yarn test:wpt:baseline` was skipped: no `wpt/fixtures.json`, and generating it needs a WPT checkout. CI's WPT regression job passed.
- Old-target behavior (e.g. `-webkit-mask-box-image` in old Safari with `0px`): `0px` is valid wherever `0` is, so the risk is low, but this is unverified.

## Tooling feedback
- **`scripts/equivalence.mjs` cannot see transition bugs.** `snapshot()` calls `finish()` on every `CSSTransition`. Discrete-vs-smooth transition interpolation, the exact motivating bug of this PR (a `0px` → `20px` transition on `:hover`), always reports "equivalent" on base. I had to rewrite the case as `@keyframes`. Suggestion: seek transitions to the same sampled fractions as animations instead of finishing them, or add a `--transitions` mode.
- **`/* args: */` in `scripts/cases.mjs` is appended to every `--config`**, so a case with `--targets 'safari 5'` ran as `--targets 'safari 12' --targets 'safari 5'` (a union of targets). There is no way to override the config's targets per case. Suggestion: document this, or let per-case `args` replace `--targets` from the config.
- **Pre-existing failures make `cases.mjs` exit 1.** Unchanged outputs that are NOT EQUIVALENT on both builds (the transform-list registered property, the mask-border prefix fallback) set exit 1 even though the PR caused no regression. A `--regressions-only` exit mode (fail only when base is equivalent and the PR is not) would make the exit code usable for reviews.
- **False positive with prefix fallbacks:** when the input uses a property Chromium supports only prefixed (`mask-border`), the added `-webkit-mask-box-image` fallback "changes" computed styles and is flagged NOT EQUIVALENT. The oracle could classify differences in properties that only the output declares (vendor-prefixed fallbacks) separately.
- **Output volume:** 44 cases × 3 configs produced ~1000 lines. I had to `awk` out the per-case/per-config status. A compact `--summary` table (case | config | changed | base | PR) would help, and it maps directly onto the report's table.
- **`scripts/build-pr.sh`** worked without problems (cached, fast). Minor: it builds in `target/review/cargo`, while the review instructions say to run tests in `target/review/cargo-test`, so the crate gets compiled twice.
- **Skill gaps:**
  - Step 2 assumes drafts.csswg.org is reachable and that a web-fetch agent exists. Neither was true here. The skill should name a fallback (e.g. mdn-data or `@webref/css` in node_modules) and say the report must mark spec claims as unquoted.
  - The skill could also tell reviewers to check CI check runs and to tell infrastructure failures (CodSpeed "Unsupported system") apart from real ones.
  - The pitfalls entry for zero units could list the full set of affected properties (line-height, tab-size, border-image-outset/width, mask-border-outset/width and their -webkit-mask-box-image aliases, `@property` syntaxes with `<number>`/`<integer>`) and note that matching `@property` syntax components in order makes `<length>|<number>` safe to shorten.
