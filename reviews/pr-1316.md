# PR #1316: fix(supports): keep the vendor prefix on a feature query inside and/or
**Verdict:** request changes (small, one-line addition in the same block). **Confidence:** high.

## Summary
The `@supports` parser merges `Declaration` operands with the same unprefixed property and value into one multi-prefix `Declaration` (printed as `((-webkit-x:v) or (x:v))`). On master the merge pass shadows `property_id` with the unprefixed id, so any prefixed operand after the first is stored stripped (`-webkit-box-orient` -> `box-orient`, `-moz-appearance` -> `appearance`) and merges add `None` instead of the real prefix. The PR keeps the unprefixed id as the match key only. Bug #710 is real and the PR fixes it (base vs PR, browser-checked). But the merge also runs inside `and` lists, and because a multi-prefix `Declaration` means *any* prefix, merging there turns `and` into `or`. That pre-existing bug is still present with the PR (and its shape changes), and the fix is a guard on the very lines the PR edits.

## Design
- Root cause of #710 correctly identified; the key/value split is the right minimal fix.
- The merge semantics: `SupportsCondition::Declaration` with prefix set P serializes as an `or` of the prefixed forms (`to_css`, supports.rs ~385-410). Merging is therefore only meaning-preserving inside an `or` list (by the spec, `or` is true iff any term is true; merging duplicates is idempotent). Inside `and`, it is only valid when prefixes are identical (pure dedup). `not` takes a single `<supports-in-parens>`, so no merge happens directly under it; nested `or` lists inside `not` still merge correctly.
- Better fix: merge only when `expected_type == Some(2)` (or). Prototype (scratchpad/r1316/or-only.diff), applied on top of the PR:
  ```rust
  if let (Some(2), SupportsCondition::Declaration { property_id, value }) = (expected_type, &condition) {
    let (property_id, value) = (property_id.clone(), value.clone());
  ```
  (a `match` with a guard avoids the clones in a real patch). `test_supports_rule`, `test_merge_supports`, `targets::supports_scope_correctly` all pass with it — no existing test relies on merging in `and`.
- In scope? It is a distinct pre-existing bug (merge since the feature landed), but: same 20 lines, same root mechanism (the merge pass changing what a query means), and the PR newly changes output for the `and` shapes (e.g. `(appearance:none) and (-webkit-appearance:none)`: master `(appearance:none)`, PR `((-webkit-appearance:none) or (appearance:none))` — in Safari < 15.4, which has only `-webkit-appearance`, the original is false, master's output false by accident, the PR's true). Asking for the one-line guard here is reasonable; alternatively merge and file a follow-up — maintainer call, but I recommend asking.
- Nit (pre-existing): a single-prefix `Declaration` always prints extra parens `((-webkit-box-orient:vertical))` — valid, not minimal; `to_css` could add the inner parens only when more than one prefix is set. Not required here.

## Spec
css-conditional-3 (Overview.bs, lines 361-364, 427-448):
> `<supports-condition> = not <supports-in-parens> | <supports-in-parens> [ and <supports-in-parens> ]* | <supports-in-parens> [ or <supports-in-parens> ]*`
> and: "The result is true if all of the <supports-in-parens> child terms are true"
> or: "The result is false if all of the <supports-in-parens> child terms are false"

Chromium: `CSS.supports('(-webkit-appearance:none) and (-moz-appearance:none)')` => false; `CSS.supports('((-webkit-appearance:none) or (-moz-appearance:none))')` => true. `-webkit-backdrop-filter` unsupported, `box-orient` unsupported, `-moz-appearance` unsupported in Chromium.

## Findings
1. **should fix (pre-existing, same code): merge inside `and` turns it into `or`.**
   `@supports (-webkit-appearance:none) and (-moz-appearance:none){.a{color:red}}` `--minify`
   - master: `@supports ((-webkit-appearance:none) or (appearance:none))` — NOT EQUIV in Chromium (rule applies; original doesn't)
   - PR: `@supports ((-webkit-appearance:none) or (-moz-appearance:none))` — NOT EQUIV
   - PR + or-only guard: `@supports ((-webkit-appearance:none)) and ((-moz-appearance:none))` — equiv
   Same for `(backdrop-filter:blur(1px)) and (-webkit-backdrop-filter:blur(1px))` (PR: `or`, Chrome applies a block that should never apply), `(appearance:none) and (-moz-appearance:none)`, and `not ((-webkit-appearance:none) and (-moz-appearance:none))` (inverts in Chrome). Triage note's claim verified.
2. **nit (pre-existing):** redundant double parens for single-prefix declarations.
3. **test gap:** add an `and`-merge case and an `or` case where the prefixed operand comes after a non-matching operand (the author's own `(not selector(::-webkit-scrollbar)) or (-moz-appearance:none)` row).
