# PR #1380: fix: reject min-/max- prefixed media features in a boolean context
**Verdict:** needs maintainer decision (approve-able as is, but there's a simpler alternative that matches browsers more closely). **Confidence:** high on behavior (CLI and Chromium evidence), medium on spec wording (drafts.csswg.org couldn't be reached from this session; see "Not verified").

## Summary
`MediaFeatureName::parse` strips `min-`/`max-` from known features and returns the prefix as a legacy operator. `parse_name_first` threw that operator away when no `:` or comparison followed, so `(min-width)` became `(width)`. The bug (#1366) is real. Base `ab14f90`: `@media (min-width){.a{color:red}}` → `@media (width){.a{color:red}}`. The equivalence check reports this as NOT EQUIVALENT (4182 diffs): Chromium 153 never matches the input but always matches the output. The PR now returns `InvalidMediaQuery` in that case. In strict mode the whole stylesheet fails to parse. With `--error-recovery`, the code warns and keeps the condition verbatim as `MediaCondition::Unknown` tokens. I found no wrong output from the PR: across 93 runs, every PR output was browser-equivalent.

## Spec
- MQ4 §2.4.4 (https://drafts.csswg.org/mediaqueries-4/#mq-min-max), as quoted in #1366 and the PR: "Attempting to evaluate a min/max prefixed media feature in a boolean context is invalid and a syntax error." I could not fetch the Editor's Draft myself: drafts.csswg.org fails DNS in this session, and the session can't read w3c/csswg-drafts on GitHub.
- MQ4 grammar, from memory and not re-fetched: `<media-in-parens> = ( <media-condition> ) | ( <media-feature> ) | <general-enclosed>`, with `<general-enclosed> = [ <function-token> <any-value>? ) ] | [ ( <any-value>? ) ]`, which evaluates to *unknown*. So when `(min-width)` fails as `<media-feature>`, it can still match `<general-enclosed>`.
- **Chromium 153 does exactly that.** It treats `(min-width)` like an unknown feature such as `(min-foo)`, not as a query-wide syntax error (`not all`). Puppeteer, `matchMedia(q)` → `[media, matches]` at 800x600:
  - `(min-width)` → `["(min-width)", false]`. A real syntax error serializes as `not all`: `1px` → `["not all", false]`, `(width) and` → `["not all", false]`.
  - `(min-width) or (width)` → `["(min-width) or (width)", true]`, the same as `(min-foo) or (width)` → `true`.
  - `(min-width), print` → `false`; `(min-width), screen` → `true`. Sibling queries in the list survive.
  - `not (min-width)` → `false` (unknown, not `not all` negated).
  - `(min-width) or (min-width: 1px)` → `true`; `(MIN-WIDTH)`, `(min-resolution)`, `(min-color)`, `(min-aspect-ratio)` and `(-webkit-min-device-pixel-ratio)` all keep their text and → `false`.
  - CSSOM: `@media (min-width), print {}` keeps its rule, with `mediaText` `"(min-width), print"`.
- `@container` in Chromium also treats `(min-width)` as unknown. There, an unknown `or` branch makes the whole query fail. With `.c{container-type:inline-size;width:100px}`, `(min-width) or (width > 0px)` does not apply, `(width) or (width > 0px)` does, and `(min-foo) or (width > 0px)` does not apply either.
- The issue, the PR description and the maintainer comment (kdy1) all describe the result as "syntax error → `not all`". That is not how Chromium evaluates it, for example with `or`. The PR is unaffected, because it preserves the original text and the browser decides.

## Findings
1. **Should fix, or maintainer decision: strict mode now hard-fails on input that browsers treat exactly like an unknown feature, while lightningcss accepts genuinely unknown features.**
   - Input: `@media (min-foo){…}` and `@media (min-width){…}`. In Chromium both are unknown and never match.
   - Base: `(min-foo)` passes through; `(min-width)` → `(width)` (wrong).
   - PR: `(min-foo)` passes through; `(min-width)` → `Error { kind: InvalidMediaQuery }`, so the whole `StyleSheet::parse` fails. The same applies to `@import "b.css" (min-width);`, `@custom-media --m (min-width);` and `@container (min-width)`.
   - With the npm package's default (`errorRecovery: false`), any stylesheet containing this typo now fails to build, including third-party CSS. Before, it built with wrong output. There is precedent for the error: `(min-scan: interlace)` and `(min-width: hi)` already error. So the PR is consistent with the existing "known feature, wrong usage" policy, and it is a defensible choice.
   - Alternative fix: in the `Err(..) if legacy_op.is_some()` arm, return `QueryFeature::Boolean { name: MediaFeatureName::Unknown(Ident(original_ident)) }`, optionally with a warning. `MediaFeatureName::parse` would need to hand back the original ident, or the caller can re-read it from the parser state. That is what browsers do and how `(min-foo)` is already handled. It also avoids finding 2. The maintainer should choose between the two.
2. **Should fix (low frequency): in error-recovery mode the whole condition becomes opaque tokens, so sibling features in the same condition are no longer lowered or minified.**
   - Input: `@media (min-width) or (width > 100px){.a{color:red}} @media (min-width) or (resolution >= 2dppx){.c{color:red}}`, run with `--minify --error-recovery --targets 'safari 12'`.
   - Base: `@media (width) or (not (max-width:100px)){…}@media (width) or (-webkit-min-device-pixel-ratio:2),(width) or (min-resolution:2dppx){…}`. It is lowered, but `(width)` is wrong.
   - PR: `@media (min-width) or (width > 100px){…}@media (min-width) or (resolution >= 2dppx){…}`. It is not lowered at all; compare `(min-foo) or (width > 100px)`, which is still lowered to `(min-foo) or (not (max-width:100px))`.
   - Modern Chromium: equivalent. Safari 12 has no range syntax, so in that browser the `(width > 100px)` branch can no longer match. This is reasoned from compat data, not checked in a browser.
   - Top-level comma lists are fine: `(min-width), (width > 100px)` still lowers the second query. Fixing finding 1 the alternative way fixes this as well.
3. **Nit: test gaps.**
   - No `error_recovery_test` asserts the recovered output (`@media (min-width)` preserved, plus one warning). That recovered output is the behavior the PR description advertises.
   - Also untested: a comma list (`(min-width), print`), the case-insensitive spelling (`(MIN-WIDTH)`), `@custom-media` and `@import` media lists. I checked all of these manually and they behave consistently.
   - The `-webkit-min-device-pixel-ratio` test is fine; Chromium also treats that one as unknown.
4. **Nit: PR description accuracy.** "browsers treat [it] as inert" is true for a lone `(min-width)`. As the Spec section shows, though, Chromium evaluates it as *unknown*, not as a `not all` syntax error. The description could say so, since the difference matters for finding 1.

Not the PR's fault: the Rust CLI panics (`StyleSheet::parse(..).unwrap()`, `src/main.rs:196`, and `:189` with `--bundle`) on any parse error, including the existing `(max-width:)`. That makes the strict-mode result look like a crash in the CLI.

## Tooling feedback
- **`scripts/build-pr.sh` race under parallel reviews.**
  - My first run failed with `fatal: shallow file has changed since we read it`, because concurrent `git fetch --depth=100` runs share `.git/shallow`; it still exited 0 through the `eval` subshell. A retry worked.
  - The script also uses `FETCH_HEAD` for the merge base, which another review's fetch can overwrite between the two commands. Combined with `git fetch … master || true`, a failed master fetch can leave `FETCH_HEAD` pointing at the PR head (or another PR's head), making the base wrong.
  - Suggested fixes: fetch master into a named ref (`refs/review/master`), take a `flock` around fetches, and don't swallow fetch errors.
  - Here the base came out correct: `ab14f90` matches the PR's base sha.
- **`scripts/equivalence.mjs` viewport false negative.**
  - `autoMatrix` always picks `1280x800,500x800,320x900` for any `@media`, regardless of the breakpoints in the CSS. Base output `@media (width) or (width>100px)` for the input `(min-width) or (width > 100px)` was reported "equivalent", but it is wrong for widths ≤ 100px.
  - Confirmed: with `--viewports 80x800,1280x800`, the same comparison is NOT EQUIVALENT (2533 diffs).
  - Suggestion: extract the lengths in media/container queries and add viewports at, just below and just above each breakpoint (plus a very small width).
- **`scripts/cases.mjs`.**
  - A strict-mode parse error prints the full Rust panic backtrace, because the CLI `unwrap()`s the parse result. That buries the actual error, and the "ERROR" count mixes intended rejections with crashes.
  - Consider a `--expect-error` per-case marker, or reporting just the `Error { kind … }` line.
  - The default configs don't include `--error-recovery`, which matters for any parser-strictness PR.
  - No `--html` per-config option for container fixtures was needed, but container cases depend on the generated DOM containing `.c`; a `/* html: */` fixture would have been more targeted.
- **Skill gaps.**
  - The skill tells reviewers to use the web-fetch agent for drafts.csswg.org, but no Agent tool was available in this session, and the plain WebFetch tool's DNS lookup for drafts.csswg.org failed. The skill should name a fallback, such as a vendored spec snapshot or an allowed mirror.
  - The skill has no step for "probe browser CSSOM/`matchMedia` directly" (the decisive evidence here). A small helper script (`scripts/probe.mjs` taking JS expressions) would help.
  - The skill says nothing about strict vs error-recovery mode; parser PRs need both configs.
