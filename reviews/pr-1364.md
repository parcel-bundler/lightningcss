## Summary
`Filter::is_compatible` and `FilterList::is_compatible` returned `true` unconditionally, so `FallbackHandler` (`define_fallbacks!` in `prefix_handler.rs`) always overwrote an earlier `filter`/`backdrop-filter` with a later one, even when the later value uses a color or length unit the targets lack. The bug is real: `.a{filter:blur(1px);filter:drop-shadow(0 0 2px oklch(25% .05 30))}` with `--targets 'chrome 90'` gives `.a{filter:drop-shadow(0 0 2px oklch(25% .05 30))}` on master, so Chrome 90 (oklch since 111) gets no filter. The PR checks `blur()`'s length and `drop-shadow()`'s color/offsets/blur, and requires all filters in a list to be compatible; the earlier declaration is then kept, exactly as `color`, `text-shadow`, `fill` etc. already behave.

## Design
- **Right place, mirrors existing code.** `Filter::DropShadow` is checked field-for-field like `TextShadow`/`BoxShadow::is_compatible`; `FilterList` uses `all()`. Other filter functions hold numbers/percentages/angles/url, none of which have target-gated syntax, so `_ => true` is correct.
- **Completes FallbackHandler.** `Filter` and `BackdropFilter` were the only `define_fallbacks!` properties whose value type had a trivially-true `IsCompatible` (checked all `fn is_compatible(&self, _browsers` impls: the rest are keyword types or `Position`, none in FallbackHandler). No sibling left behind.
- **No rule-merging side effect.** The triage note suspected rule merging; `StyleRule::is_compatible` (`rules/style.rs:117`) only checks selectors, so declaration-value compat doesn't feed rule merging.
- Complexity: O(filters) per declaration, only when targets are set. Philosophy: fine.

## Spec
Filter Effects 1 (https://drafts.csswg.org/filter-effects-1/, fetched):
`blur() = blur( <length>? )`; `drop-shadow() = drop-shadow( [ <color>? && <length>{2,3} ] )`. `backdrop-filter` uses the same `<filter-value-list>` (Filter Effects 2). A UA that doesn't support a component (e.g. `oklch()`, `cqw`) treats the declaration as invalid and the earlier declaration wins by normal cascade, so dropping the earlier one changes behavior in those UAs. Compat: OklabColors Chrome 111; ContainerQueryLengthUnits Chrome 105; LhUnit Chrome 109; dynamic viewport units Chrome 108.

## Findings
1. **Nit (tests):** the tests only cover the oklch color case. Add one with an unsupported length unit (e.g. `blur(1px); blur(1cqw)` or `drop-shadow(1lh 1lh 2px red)`) and a mixed list (`grayscale(1)` then `grayscale(1) drop-shadow(... oklch ...)`) to cover the `Blur` arm and the `all()` in `FilterList`. All three behave correctly in my runs.
2. **Nit / pre-existing, not from this PR:** after an incompatible value is pushed, a third compatible declaration replaces the incompatible one but the earliest fallback stays: `filter:blur(1px);filter:drop-shadow(...oklch...);filter:blur(3px)` → PR `filter:blur(1px);filter:blur(3px)` (base `filter:blur(3px)`). Equivalent, slightly larger; `color:red;color:oklch(..);color:blue` → `color:red;color:#00f` already does the same on master, so it's the shared FallbackHandler design. Not worth blocking.
3. **Bonus fix observed:** `.a{color:red}.a{filter:blur(1px)}.a{filter:drop-shadow(0 0 2px oklch(...))}` with chrome 90: base `.a{color:red;filter:drop-shadow(0 0 2px lab(...))}` (no filter in Chrome 90 — no lab support), PR `...filter:drop-shadow(0 0 2px #361713);filter:drop-shadow(0 0 2px lab(...))`. Correct in Chrome 90.
