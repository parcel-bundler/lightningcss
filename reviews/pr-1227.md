# PR #1227: Fix logical property shorthands with calc(var()) not being converted (#927)
**Verdict:** request changes. **Confidence:** high.

## Summary
Lowers unparsed `margin-block`/`margin-inline` (and padding/scroll-margin/scroll-padding/inset-block/inset-inline, which share `side_handler!`) and unparsed `inset` to longhands/physical properties when targets lack support. #927 is real: master leaves `margin-block: calc(var(--s) * 0)` untouched for `chrome 80`, which old browsers drop. The PR fixes that single-value case, but (1) the "single value" test only excludes a token list that is exactly one bare `var()`, so multi-value shorthands are copied whole into each longhand (invalid at computed-value time), and (2) the new code in the `_` arm also catches unparsed **physical** `top`/`bottom`/`left`/`right`, turning `left: calc(...)` into all four sides. (2) changes real Bootstrap, Font Awesome and Radix output.

## Design
- The check `!matches!(tokens, [Var(_)] | [])` is the wrong predicate. What's needed is "exactly one top-level component value (ignoring whitespace) that is not itself a substitution function (`Var`, `Env`; arguably `attr()` functions)". Anything else must keep the shorthand. Put it in one helper (e.g. a `TokenList` method in `src/properties/custom.rs`) instead of three copy-pasted `let is_single_value = ...` lines, so other handlers that may want to split unparsed shorthands (border, size, border-radius already do per-property versions) can reuse it.
- The `_` arm matches `PropertyId::$top | $bottom | $left | $right | $shorthand`. The expansion must be restricted to `PropertyId::$shorthand`; as written, for `InsetHandler` (shorthand category Logical) every unparsed `top/left/...` gets expanded to 4 sides.
- Fits philosophy otherwise (no token storage added; it reuses `UnparsedProperty::with_property_id`). No perf concern (O(1) per declaration).

## Spec
- css-logical-1 (Overview.bs) for `margin-block` etc.: "The first value represents the start edge ..., and the second value represents the end edge .... If only one value is given, it applies to both the start and end edges." So `margin-block: 10px var(--x)` sets two different values; it cannot be copied to each longhand.
- css-variables-1 §guaranteed-invalid / substitution: a property whose substituted value doesn't match its grammar is "invalid at computed-value time" (behaves as `unset` → `margin-top: 0`). `margin-top: 10px 20px` is such a case.

## Findings
1. **Blocking: physical inset longhands expanded to all four sides.** With targets lacking `inset` (chrome < 87, safari < 14.1):
   - input `.a{left:calc(var(--a) * 2)}`, `--minify --targets 'chrome 80'`
   - base: `.a{left:calc(var(--a) * 2)}`
   - PR: `.a{top:calc(var(--a) * 2);bottom:calc(var(--a) * 2);left:calc(var(--a) * 2);right:calc(var(--a) * 2)}`
   - browser: NOT equivalent (element moved/stretched). Same for `top`.
   - Real world (`--targets 'chrome 80' --targets 'safari 13'`): Bootstrap tooltip/popover arrows (`top: calc(-1 * var(--bs-tooltip-arrow-height))` gains left/right/bottom), Font Awesome `.fa-li` (`left: calc(-1 * var(--fa-li-width, 2em))` gains top/bottom/right), Radix slider, Primer, Bulma, react-spectrum S2 all change.
   - Fix: only expand when `val.property_id == PropertyId::$shorthand`.
2. **Blocking: multi-value shorthands copied into each longhand** (the triage suspicion, confirmed).
   - `.a{margin-block:10px var(--x)}`, chrome 80 → PR `margin-block-start:10px var(--x);margin-block-end:10px var(--x)`; chrome 60 → `margin-top:10px var(--x);margin-bottom:10px var(--x)`. Base kept `margin-block:10px var(--x)`. Browser: NOT equivalent (both margins become 0 instead of 10px/20px).
   - Same for `margin-block: var(--a) var(--b)`, `margin-inline: 10px var(--x)`, `padding-block: calc(var(--x)) 3px`, `inset: var(--a) var(--b)` (→ `top: var(--a) var(--b)` x4), `inset: calc(var(--a)) 1px 2px 3px`.
   - Fix: helper as described in Design; only split when the list is one non-substitution component.
3. Should fix: tests only cover the happy path; add the cases above (two values, physical `top`/`left` with old targets) as negative tests.
4. Nit: the same 8-line block is duplicated three times.
5. Pre-existing (not caused by PR): `margin-inline-start:2px; margin-inline:calc(var(--s) * 3)` for chrome 60 reorders the `:lang()`-based start rules after the shorthand, so the later shorthand loses (still-broken on both builds).

## Edge cases checked
21 cases x 4 configs (`--minify`, `--minify --targets 'chrome 80'`, `--targets 'chrome 60'`, `--minify --targets 'chrome 90'`), base = master 574eee2, PR merged onto it.

| case | config | result |
|---|---|---|
| #927 `margin-block: calc(var(--s) * 3)` | chrome 80 / 60 | changed, equivalent (split into longhands/physical: the intended fix) |
| #927 `inset-inline: calc(var(--s) * 2.5)` | chrome 80 / 60 | changed, equivalent |
| `margin-block: 10px var(--x)` / `var(--a) var(--b)` | chrome 80, 60 | **regression** |
| `margin-inline: 10px var(--x)` | chrome 80, 60 | **regression** |
| `padding-block: calc(var(--x)) 3px` | chrome 80, 60 | **regression** |
| `inset: var(--a) var(--b)` / `inset: calc(var(--a)) 1px 2px 3px` | chrome 80, 60 | **regression** |
| `top: calc(var(--a) * 2)` / `left: calc(var(--a) * 2)` | chrome 80, 60 | **regression** |
| bare `var(--a, 3px)` | all | ok (kept) |
| `!important`, override ordering, rtl fixture, env(), scroll-padding-block, invalid trailing ident | all | ok/changed-equivalent |
| `margin-inline-start` then `margin-inline` calc | chrome 60 | still-broken (pre-existing) |

16 regressions in total; none with `--minify` alone or chrome 90 (no lowering there). Note the #927 cases cannot come out "fixed" in the oracle, since modern Chromium supports `margin-block`; the fix only matters in old browsers.
