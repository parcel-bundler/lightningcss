# PR #696: minify selectors (dedupe selectors in a list)
**Verdict:** request changes (or close; see Design). **Confidence:** high on measurements, medium on the recommendation.

## Summary
Adds `SelectorList::minify` (selectors/parser.rs) that serializes every selector with `to_css_string()`, inserts into a `HashSet<String>`, and removes repeats; called unconditionally at the top of `StyleRule::minify`. Fixes #240 (`h1,h2,h3,h1,h3{}` -> `h1,h2,h3{}`). Semantically safe (identical selectors in one rule have identical specificity; order within a list is irrelevant), and no browser-check regressions. But: duplicates never occur in the real-world corpus (input or output), the check costs ~5% of total instructions on real CSS, and the duplicates Lightning CSS itself produces (rule merging, `:is()` unwrapping) are not covered.

## Design
- **Does it happen in real code? (maintainer's question on #240)** No evidence. postcss walk of every rule in the pinned real-world corpus (react-spectrum S2, Radix Themes, Bootstrap, Bulma, Primer, Pico, animate.css, Open Props, Font Awesome, normalize) plus the synthetic corpus: 0 rules with a duplicate selector in input (of ~24k rules, ~1.3k multi-selector rules). Same count on master's `--minify` output, with and without old targets: 0. size-check: 0 bytes changed on all 16 files in both configs.
- **Merge-created duplicates are NOT covered.** `StyleRule::minify` runs per rule before `merge_style_rules` (`rules/mod.rs` ~1080) extends `last_style_rule.selectors` with the next rule's selectors:
  - `.a,.b{color:red}.a{color:red}` -> base and PR both `.a,.b,.a{color:red}`
  - `.a{color:red}.b{color:red}.a{color:red}` -> both `.a,.b,.a{color:red}`
- **Print-time duplicates are NOT covered.** Single-item `:is()` is unwrapped during serialization, after dedup: `.x :is(.a),.x .a{color:red}` -> both `.x .a,.x .a{color:red}` (even without targets). Nested lists are untouched: `:is(.a,.a)` stays.
- **Cost design.** `to_css_string()` allocates a String per selector, and lightningcss's `PseudoClass`/`PseudoElement` `cssparser::ToCss` impls each allocate a further String + `Printer`. `Selector` already derives `Hash + Eq` (selectors/parser.rs:713), so a `HashSet<&Selector>` (or a pairwise compare for small lists) works without serialization, and an early return for `len() < 2` skips the ~90-99% of rules with one selector. Structural equality misses only a few equal-but-differently-represented pairs; the string approach has no collision risk found (prefixes and case-sensitive idents serialize distinctly), so either is safe.
- **Better place, if wanted at all:** dedupe when lists are combined, i.e. in `merge_style_rules` (only the incoming selectors need checking against the existing list), which is where Lightning CSS itself creates duplicates. Plus an `is_empty/len<2` guard if the per-rule pass stays.
- Upstream servo/stylo `selectors/parser.rs` has no dedup/minify (checked: no `dedup`/`HashSet`/`fn minify`); not applicable, it is a style engine.
- Public API: adds `pub fn minify` on `parcel_selectors::SelectorList` (new public method in the published selectors crate; additive).

## Spec
Selector lists: a rule matches if any selector in the list matches; specificity is per matching selector (Selectors 4, unquoted here; not fetched). Removing an exact duplicate cannot change matching or specificity. Browser checks agree (below).

## Findings
1. **should fix (perf): hot-path cost with no measured benefit.** callgrind instruction counts, `--minify`, single process:
   | input | base Ir | PR Ir | delta | StyleRule::minify incl. base -> PR |
   |---|---|---|---|---|
   | real5.css (Bootstrap+Bulma+Primer+Pico+Radix concatenated, 3.0 MB) | 718.0M | 754.8M | **+5.1%** | 130.8M -> 167.2M (+28%) |
   | selheavy.css (synthetic, 30k rules, 1-20 complex selectors each, 6.1 MB) | 2305.5M | 2811.5M | **+21.9%** | 92.3M -> 591.9M (6.4x) |
   Wall-clock was too noisy to use (load avg ~13 on 4 cores from parallel reviews). Not quadratic (hash set + reverse `remove`, O(n*d) for d duplicates).
2. **should fix: incomplete.** Merge-created and `:is()`-unwrap duplicates remain (repros above), which are the only duplicates Lightning CSS can realistically be fed or produce.
3. **nit:** fold + Vec of indices + reverse `remove` is convoluted; `retain` with a seen set is simpler.
