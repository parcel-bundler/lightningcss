# PR #1287: fix: preserve light-dark in custom properties
**Verdict:** needs maintainer decision. **Confidence:** medium (behavior browser-verified in modern Chromium; old-browser behavior and the policy question are not mine to settle).

## Summary
Fixes #821 (open since 2024, 9 upvotes): the `light-dark()` polyfill in a custom property is resolved where the property is *declared*, so a descendant with a different `color-scheme` gets the wrong color. The first version dropped the polyfill for custom properties; you called that breaking. This version (head 1e107cd) keeps the polyfill and adds, after each such rule, `@supports (color: light-dark(#000, #fff)) { <same selector> { --x: light-dark(…) } }`. Browsers with native support then use real `light-dark()`, which resolves where the value is used, and older ones keep today's output. It also bundles three related fixes:
- `@property` `initial-value` keeps native `light-dark()`;
- `@supports (--x: …)` and `var()`/`attr()` fallbacks no longer count as proof that a feature is supported;
- stale conditional fallbacks are removed when a custom property is redeclared.

The bug is real. With `--targets 'chrome 90'`, the base output is not equivalent to the input in Chromium for the #821 pattern; the PR output is (see table).

## Design
- **The policy question is the main issue, not correctness.** Modern browsers now get native semantics: the custom property resolves at the place it is used. Wherever that differs from the polyfill, the polyfill was the one disagreeing with the CSS as written. So this matches the authored CSS. Old browsers are unchanged. It is still a visible behavior change in modern browsers for anyone whose output relied on the declare-site resolution, which is your concern from the thread. You also suggested an alternative: a separate opt-out flag for `light-dark()` in custom properties. That has zero size cost but leaves the bug in place by default.
- **Size cost is inherent to the approach.** Every rule that sets a custom property with `light-dark()` gets its own `@supports` block, placed right after the rule to keep its position in the cascade. In atomic CSS these blocks never merge. Moving or grouping them would change the cascade order, so there is no cheap way to shrink this.
- **The reusable place is reasonable.** The logic sits in `TokenList::get_light_dark_fallbacks` and `DeclarationHandler::add_conditional_fallbacks`, next to the existing LAB/P3 fallbacks for custom properties. `Printer::with_feature_disabled` is a small helper that is also reused in `container.rs`.
- **`TargetsWithSupportsScope::enter_supports` now also removes features from `include`.** Without this, `include: LightDark` would also lower `light-dark()` inside `@supports (color: light-dark(…))`. I think that is right, but it is a semantic change for every feature that can be forced on with `include`.
- **The side fixes are correct, but separable.** I checked each one in a browser (below). They could go in on their own even if the main approach is rejected.

## Spec
css-color-5 (Bikeshed source, `css-color-5/Overview.bs`):
> For the color form, this function computes to the computed value of the first color, if the element color scheme is 'light', or to the computed value of the second color, if the element color scheme is 'dark'.

An unregistered custom property holds unresolved tokens, so native `light-dark()` resolves on the element that uses the value. The polyfill's `var(--lightningcss-light, …)` is substituted where the property is declared, which causes #821.

Chrome 153 accepts `@property --t{syntax:"<color>";initial-value:light-dark(#fff,#000)}`. The base output's `initial-value: var(--lightningcss-light,#fff) var(--lightningcss-dark,#000)` makes Chrome drop the whole `@property` rule, checked with probe.mjs: `cs('--u')` is `""`.

## Findings
1. **Should decide (policy and size):** with `--minify --targets 'chrome 100' --targets 'safari 15'`, react-spectrum S2 grows from 104,550 to 112,591 B (+7.7%), and gzipped from 19,574 to 20,466 B (+4.6%). The growth comes from 81 separate `@supports (color:light-dark(#000, #fff)){.x{--…:light-dark(…)}}` blocks. Every other corpus entry is unchanged, because none of them uses `light-dark()` in custom properties (Bulma has one occurrence, with no size change). `size-check.sh` runs without targets and shows 0 change everywhere, because the polyfill is inactive there. S2 is exactly the "design tokens on the color-scheme element" user who already works with the polyfill and now pays bytes.
2. **Should fix / note (pre-existing):** the fix silently does not apply to declarations that come after a nested rule. `.a{.b{color:red} --c:light-dark(red,blue)}` with chrome 100 gives `.a .b{color:red}.a{--c:var(--lightningcss-light,red)var(--lightningcss-dark,#00f)}`, with no `@supports` override. The same happens with `&:hover`. This is the existing "`@supports` fallbacks dropped for nested declarations" bug. The base drops the LAB fallback for `--c:lab(…)` the same way. It is covered by #1386, so #821 stays broken for that shape until #1386 lands.
3. **Nit:** the `light-dark()` fallback list is built from `get_features()` and `get_necessary_fallbacks()` in a second pass over the tokens of every custom property, but only when `LightDark` is compiled. CLI time on the corpus did not change measurably.
4. **Nit:** `remove_conditional_property` is a linear scan of the rule's `supports` entries for each redeclaration. That is fine in practice: it is per rule and per redeclared name, not quadratic over a stylesheet.

## Edge cases checked
26 cases × 4 configs (`--minify --targets 'chrome 90'`, `--targets 'chrome 100'`, `--minify --targets 'chrome 123'`, `--minify --targets 'safari 15' --targets 'chrome 90'`). No regressions: 21 fixed, 18 changed (both equivalent), 21 ok, 44 still-broken. Every still-broken run differs only in the serialized string of a custom property (`blue`→`#00f` inside a custom property). That difference is pre-existing and identical at `chrome 123`, where nothing is lowered; no real computed color differs. Cases file: `scratchpad/r1287/cases.css`, output in `cases.out`.

| case | config | result |
|---|---|---|
| #821 reporter (`:root` tokens, `p{color-scheme:dark}`) | chrome 90 / 100 / safari 15 | real colors fixed (base had 96 diffs; the PR has only the 24 custom-property-string diffs that also show at chrome 123) |
| `:root{color-scheme:light dark; --bg:light-dark()}` (design-system pattern) | all lowering configs | fixed in the dark-media render (base not equiv), PR equiv |
| `html[data-theme=dark]` toggle, tokens on `:root` | all lowering | fixed |
| nested `color-scheme` island | all lowering | fixed |
| `@property` initial-value `light-dark()` | all lowering | fixed (base drops the `@property` rule) |
| registered `<color>` property set to `light-dark()` | all lowering | fixed |
| `@supports (--x: light-dark())` / `var(--t, light-dark())` condition | all lowering | changed: the inner `light-dark()` is now polyfilled for old browsers (correct, because the condition proves nothing) |

## Tests & performance
- `cargo test --lib` in the PR worktree: all passed. The new tests cover the #821 shape, `var()` inside `light-dark()`, redeclarations, LAB fallbacks, the `exclude` flag, the `@supports` conditions and `@property`.
- No existing expectations were changed.
- `size-check.sh`: 0 change on every entry (no targets). With chrome 100 + safari 15 targets: S2 +7.7% raw / +4.6% gz; all other entries are byte-identical.
- CLI time on the corpus is unchanged within noise.
- Behavior was verified with `scripts/cases.mjs` (Chromium 153) and `probe.mjs` for `@property`.
- CI: no check runs are reported on head 1e107cd. The PR is 26 commits behind master; I built against its merge base 91bfa3f, not merged onto master.

## Not verified

- The stored repro `target/triage/repros/821/821-repro.mjs`: I did not run it through the node binding. Its two key checks (the PR emits `--background:light-dark(`; chrome 123 targets are untouched) match the CLI output above.
