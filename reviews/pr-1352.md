# PR #1352: fix: preserve legacy placeholder pseudo-classes
**Verdict:** approve (one optional test nit). **Confidence:** high.

## Summary
Removes the two parse-table entries added by #929 (v1.29.3) that mapped `:-moz-placeholder` and `:-ms-input-placeholder` to `PseudoClass::PlaceholderShown(Moz/Ms)`. After the PR they parse as unknown vendor-prefixed pseudo-classes and round-trip as written. The bug is real and worse than #1351 states: on master these legacy names are **renamed even without targets** (`.a:-ms-input-placeholder` -> `.a:-ms-placeholder-shown`, a selector no browser ever supported), and the standard autoprefixer `::placeholder` fallback pair (`:-moz-placeholder` rule + `:-ms-input-placeholder` rule) gets merged as prefix-equivalents into an **unprefixed `:placeholder-shown`** rule, which in every modern browser styles the whole input instead of the placeholder text. Bulma (in our real-world corpus) hits this with default options.

Merged cleanly onto master 574eee2 (`build-pr.sh --on-master`).

## Design
- The ambiguity is inherent: MDN BCD lists `:-moz-placeholder` (Fx 4-50) and `:-ms-input-placeholder` (IE 10+) as `alternative_name`s of `:placeholder-shown`, which is what #929 relied on, but in practice (autoprefixer's `placeholder.js` "-moz- old"/"-ms- old", Bulma, Bootstrap 4) they are emitted as `::placeholder` fallbacks, and in those browsers they styled the placeholder text. Neither `:placeholder-shown` nor `::placeholder` is a meaning-preserving target, so keeping them opaque is the only safe choice (CLAUDE.md: "when unsure whether a transform preserves meaning, it must not be applied").
- Fix is in the right place (the parse table); no new machinery. Not a `selectors/` crate change, so upstream stylo comparison is not relevant (Firefox has dropped both names anyway).
- Philosophy: these are non-standard names that now pass through as custom pseudo-classes, same as other unknown `-vendor-` pseudo-classes. No old-browser hack added.
- Remaining pre-existing gap (not introduced here, not required for this PR): prefixing `:placeholder-shown` for Firefox <51 / IE 10-11 targets still prints `:-moz-placeholder-shown` / `:-ms-placeholder-shown` (`write_prefixed!` in `selector.rs`, `PseudoClassPlaceholderShown` prefix data), names that never existed. Before #929 the parser accepted those same bogus names. Options for a follow-up: print autoprefixer's legacy names on output only, or drop the prefix data for this feature. Given "limit hacks for very old browsers", low priority.

## Spec
Selectors 4 defines only `:placeholder-shown` (https://drafts.csswg.org/selectors-4/#placeholder) and CSS Pseudo 4 `::placeholder`; the legacy names are non-standard, so behaviour is decided by browser data. BCD (`node_modules/@mdn/browser-compat-data`): `:placeholder-shown` firefox `alternative_name: ":-moz-placeholder"` 4-50 (removed 51), ie `alternative_name: ":-ms-input-placeholder"` from 10. Chromium: `CSS.supports('selector(:-ms-input-placeholder)')` and `(:-moz-placeholder)` => false (probe.mjs), so in modern browsers any rule containing them is dropped.

## Findings
1. nit: The PR's tests cover only the `:is()` list case with chrome 111. The most common real-world trigger is the autoprefixer pair with no targets, `.a:-moz-placeholder{color:red}.a:-ms-input-placeholder{color:red}`: master -> `.a:-moz-placeholder-shown{color:red}.a:placeholder-shown{color:red}`, PR -> unchanged. Worth a `minify_test` so the merge path is pinned too.
