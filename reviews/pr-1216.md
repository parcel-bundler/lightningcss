# PR #1216: fix: error on `composes:` references to undefined classes
**Verdict:** request changes (plus a policy call on errorRecovery). **Confidence:** high on the findings, medium on what the right errorRecovery behavior is.

## Summary
Adds `PrinterErrorKind::MissingComposesName { name, specifier }`. `CssModule` records every same-file and bundler-resolved (`Specifier::SourceIndex`) `composes` name in `pending_composes`; `StyleSheet::to_css` checks them against `exports_by_source_index` after all rules are printed, so forward references keep working. Fixes #1215 (`composes: historychevron` against `.historyChevron` silently exports a hashed name with no rule). The bug is real: base df63db2 exports `historyChevronOpen.composes = [{local, "…_historychevron"}]` with no matching class. Matches postcss-modules-scope, which throws `referenced class name "x" in composes not found`.

Doesn't merge cleanly onto current master: conflict in `src/css_modules.rs` with 987e1bf (#1355, IndexMap exports). Built and tested against its merge base (df63db2) instead.

## Design
- **Where "defined" comes from is wrong for empty rules.** The check uses the printed exports, but exports are only added when a rule is printed, and `minify()` (which the CLI, `transform()` and `bundle()` always run) drops empty style rules. So `.b {}` is never exported, and `.a { composes: b }` now **fails the build** even though `.b` is declared in the source. postcss-modules-scope accepts it (it registers every local class from `walkRules` selectors, empty or not). Base also doesn't export `b` for an empty rule (pre-existing gap), but there it was harmless for `composes`; the PR turns it into a hard error. Fix direction: collect declared local class names before minification (e.g. during parse or in a pass over the unminified rules), or keep exports for removed empty rules; then validate against that set.
- **Strict vs errorRecovery.** Per CLAUDE.md, strict mode errors on definitely invalid input; errorRecovery should warn and keep the output as it was. An undefined `composes` target is definitely invalid CSS Modules (the reference implementation throws), so an error in strict mode fits. But the PR errors in errorRecovery mode too (`--error-recovery` still panics with MissingComposesName). This is new territory: no printer error currently honours errorRecovery, and `PrinterOptions` has no flag. It is feasible though: `StyleSheet` keeps its `ParserOptions` (`error_recovery`, `warnings` Arc), and napi reads warnings after `to_css`, so `validate_composes` could push a warning instead of returning `Err` when `self.options.error_recovery` is set. That needs a warning kind (warnings are `Error<ParserError>`), i.e. a new `ParserError` variant or a different warning type. Maintainer decision whether to require it here.
- **Breaking change.** Builds with a dangling `composes` (including the empty-rule false positive above) now fail in all modes. The PR description says so; it needs a release-note callout. API: new variant on the public `PrinterErrorKind` (not `#[non_exhaustive]`), so exhaustive Rust matches break; there is precedent for adding variants in minor releases. JS errors get a new `data.type: "MissingComposesName"` with `name`/`specifier`.
- Generality: covers same-file and bundled cross-file references; unresolved `from "./x.css"` (non-bundle) is out of scope, reasonably. `from global` is untouched (correct).
- Complexity is fine: one Vec push per composes name, linear validation. Nit: it allocates the specifier string (`to_string_lossy().into_owned()`) for every cross-file reference up front; storing the source index and formatting only on error would avoid that.

## Spec
No CSS spec; CSS Modules semantics come from the reference implementation. postcss-modules-scope `src/index.js` (master): in `walkRules`, for each `composes` class: `else if (hasOwnProperty.call(exports, className)) {...} else { throw decl.error(\`referenced class name "${className}" in ${decl.prop} not found\`) }`, where `exports` holds every localized class from every rule's selector (empty rules included). Note postcss-modules-scope only sees rules *before* the current one (no forward refs); the PR is more lenient, which is fine.

## Findings
1. **Blocking: false error when the composed class only has an empty rule.**
   `.a { composes: b; color: red; } .b {}` (also `.b{}` before `.a`, and `@media print { .b {} }`)
   - base: builds; exports `a.composes=[…_b]` (no `b` export).
   - PR: `MissingComposesName { name: "b", specifier: None }`, with and without `--minify`, and with `--error-recovery`.
   - postcss-modules-scope: accepts.
   Fix: validate against declared names collected before minify.
2. **Policy (needs maintainer decision): no errorRecovery downgrade.** `--error-recovery` still fails on `issue.css`. Under the project policy this should be a warning with output unchanged. See Design for a feasible route.
3. **Should fix: rebase** onto master (conflict with #1355 in `css_modules.rs`).
4. Minor false negatives (not blocking): any name in the exports map passes, so `composes: fade` passes when `fade` is a `@keyframes` name, or merely referenced by `animation-name` (since `reference()` inserts an export). Existing `exports` mixes classes with other symbols.
5. Nit: eager specifier string allocation per cross-file composes.

## Edge cases checked (PR binary, CLI `--css-modules=x.json`, plain / `--minify` / `--error-recovery`)
| case | base | PR |
|---|---|---|
| #1215 repro (`historychevron`) | silent dangling export | error (all 3 modes) |
| `composes: b c`, only `.b` | silent | error on `c` |
| forward ref `.a{composes:b} .b{color:blue}` | ok | ok |
| `.b {}` empty, after/before, in `@media` | ok (no b export) | **error (false positive)** |
| `.b` only in `:global(.b)` | silent dangling | error (matches postcss) |
| `.b` only in `.parent .b`, `div:not(.b)`, `@media print` | ok | ok |
| `.b{colr:blue}` (invalid decl kept) | ok | ok |
| `.b,.c` merged rule; duplicate `.b` rules removed | ok | ok |
| mutual `composes` (`.a{composes:b}.b{composes:a}`) | ok | ok |
| `from global`, `from './nope.css'` (no bundler) | ok | ok (unchanged) |
| `composes: fade` with `@keyframes fade` | silent | ok (false negative) |
Error location matches `Printer::error` convention (0-based line), consistent with `InvalidComposesNesting`.

## Tests & performance
- `cargo test --all-features --lib css_modules` and `--lib bundler` in the PR worktree: all pass. The PR rewrites the existing bundler expectation (`composes: x from './b.css'` where b.css has no `.x`) from silent output to an error; justified by #1215 / postcss behavior.
- Gaps: no test for empty-rule targets, no errorRecovery test, no JS-level test of the error shape.
- No perf concern (linear); no minify/lowering change, so size-check not run.
