# PR #1390: fix: parse nested math functions with var() in linear time
**Verdict:** approve with nits (atan2 follow-up recommended). **Confidence:** high.

Author: sarankumar1325. Fixes #1389. Base 4a1b083 (master is 4 commits ahead, none touch `src/values/calc.rs`; merges cleanly). No CI check runs reported on head f5e498e (fork PR, workflows probably not approved yet).

## Summary
`Calc::parse_value` tries `Self::parse` on a nested math function; on failure (e.g. a `var()` inside) it falls through to `V::parse`, and every `V::parse` (`Length`, `DimensionPercentage`, `Angle`, `Time`, `Percentage`, `CSSNumber`) begins with `Calc::<V>::parse` on the same tokens, so each level is parsed twice: 2^depth. The PR peeks the token and, if it is one of the 21 math function names `parse_with` handles, returns the error instead of falling through. Bug confirmed: base takes 1354 ms at depth 18 (`calc(… var(--x) - 1px)`), PR takes 5 ms; depth 200 takes 12 ms on the PR. Output is byte-identical on all edge cases and on the size corpus.

## Design
- **Right place, general.** The fix is in `Calc::parse_value`, the one shared point, so it covers every `Calc<V>` and every math function (calc/min/max/clamp/round/rem/mod/trig/pow/log/sqrt/exp/hypot/abs/sign). Measured fixed for length, percentage, angle, number, `min()` and trig nesting (table below).
- **Semantics preserved.** The skipped fallback could only matter if some `V::parse` accepted a math function that `Calc<V>::parse` rejected. I checked all `V::parse` impls: each starts with `Calc::<V>::parse` and then only accepts a dimension/number/percentage token. `DimensionPercentage` falls back to `D::parse` and `Percentage::parse`, which are narrower `Calc` types and accept a subset. 0 output changes in 83 runs.
- **Nit: duplicated name list.** `is_math_function_name` has to stay in sync with the `match_ignore_ascii_case!` in `parse_with` (it does now, all 21 names). It's a small maintenance hazard. A cleaner option is for `parse_with` to report "not a math function" itself, e.g. split it into peek-name + dispatch so both use one match. Not blocking.
- **Remaining exponential path (separate mechanism, pre-existing): `atan2()`.** `parse_atan2` tries `Calc<Length>`, `Calc<Percentage>`, `Calc<Angle>`, `Calc<Time>` and then `Calc<CSSNumber>` in turn, and each try re-parses nested arguments from scratch. Nested `atan2` is still exponential on the PR, even for *valid* input:
  - `rotate: atan2(atan2(…1deg…, 1deg), 1deg)`: d=10 54 ms, d=12 387 ms, d=14 1793 ms (about 2x per level; base is about 5x per level, 2845 ms at d=10).
  - With `var()` innermost: d=8 450 ms, d=10 8116 ms, d=12 >20 s timeout (175 bytes). Base already timed out at d=8.

  This is the same DoS class as #1389 (tiny input stalls the process). The fix is different though: parse the arguments once in a type-agnostic way, or pick the type from the first leaf token. I'd file it as a follow-up rather than block this PR.
- **Related pre-existing bug on the touched line.** `parse_value` calls `Self::parse`, i.e. `parse_with(input, &|_| None)`, so nested math loses `parse_ident`. In relative colors, `rgb(from red calc(calc(r) - 10) g b)` fails to parse and is kept as written, while `calc((r) - 10)` resolves to `#f50000`. Chromium accepts the nested form (`CSS.supports` → true). With safari 12 targets the color isn't lowered, so it shows as "still-broken". Passing `parse_ident` (`Self::parse_with(input, parse_ident)`) would likely fix it. That's out of scope here, but cheap if the author wants it; it needs tests.
- Philosophy: no change to parse strictness, error recovery or output.

## Spec
css-values-4 (https://drafts.csswg.org/css-values-4/#calc-syntax): "`<calc-value> = <number> | <dimension> | <percentage> | <calc-keyword> | ( <calc-sum> )`" with math functions nestable as values. "In some contexts, additional `<calc-keyword>` values can be defined to be valid. (For example, in relative color syntax, appropriate channel keywords are allowed.)" This supports the relative-color note above. No spec question is at stake for the PR itself; it is a performance fix with identical output.

## Findings
1. **should fix (follow-up, not this PR):** nested `atan2()` is still exponential; numbers above. Suggest a separate issue.
2. **nit:** `is_math_function_name` duplicates the name list in `parse_with`.
3. **nit:** the test builds `value` and `expected` with two identical loops; one string would do. It also has no explicit timing assertion: on master it just runs forever (2^40), which acts as a hang rather than a failure. That's acceptable.
4. **optional:** pass `parse_ident` into the nested parse (relative colors with nested math). Pre-existing, separate.
