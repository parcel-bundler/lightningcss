# PR #1379: Fix error recovery for name-only container queries
**Verdict:** approve (PR is still marked draft). **Confidence:** high.

## Summary
With `errorRecovery`, `@container name { … }` (valid, name-only) emitted a spurious `EndOfInput` warning and printed an empty `ContainerCondition::Unknown`, producing `@container name  {` (double space; minified `@container sc {`). Cause: `ContainerCondition::parse_with_options` (src/rules/container.rs:326) never returns `Err` in recovery mode (it warns and returns `Unknown(TokenList)`), so the `name.is_some() && input.is_exhausted()` fallback in the `"container"` prelude (src/parser.rs) was unreachable. The PR moves that check before the condition parse. It is the fix suggested in #1370 (by sokra, from the Next.js/Turbopack report vercel/next.js#98261). Bug reproduced on master 574eee24; fixed by the PR.

## Design
- Right place and minimal: the name-only branch is the only alternative that depended on the condition parse failing. Other recovering parsers (`MediaCondition::parse_with_flags`) have no such fallback after them (`MediaQuery::parse_with_options` decides by media type / `and` beforehand), so there is no sibling instance of this pattern.
- `input.is_exhausted()` skips whitespace and comments, so `@container sc /* c */ {` is covered.
- `ContainerName::parse` already rejects `none|and|not|or`, so `@container not (…)` still goes to the condition path.
- Strict-mode behavior is unchanged (previously: condition parse fails, then fallback; now: fallback first). Errors for invalid preludes are identical (same messages and locations, checked below).
- Fits philosophy: recovery output now equals strict output for valid input; invalid preludes still warn and are preserved as written.
- Nit (not worth a comment): `input.try_parse(...)?` in the else branch no longer needs `try_parse`; harmless.

## Spec
css-conditional-5 (https://drafts.csswg.org/css-conditional-5/#container-rule), fetched:
```
<container-query-list> = <container-condition>#
<container-condition> = [ <container-name>? <container-query>? ]!
```
Name-only is valid. (Aside, out of scope: the ED now has a comma-separated `<container-query-list>`; lightningcss treats `@container a, b {}` as invalid — strict error; recovery keeps it as tokens `@container a , b{`. Pre-existing, unchanged by this PR.)

## Findings
None blocking. No should-fix.
- Pre-existing, unchanged: recovery output for `@container {}` is `@container  {` (empty Unknown printed with extra space). Invalid anyway; not this PR's concern.
