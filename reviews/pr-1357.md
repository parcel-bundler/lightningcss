# PR #1357: fix: deserialize null as None in visitor results
**Verdict:** approve with nits. **Confidence:** high.

## Summary
Fixes the 1.30.2 visitor regression (#1065, #1081 closed as its duplicate). Since #1062 buffered values go through serde-content, whose `Deserializer::deserialize_option` calls `visit_some` for `Value::Unit`; a JS `null` (napi `ValueType::Null => visit_unit`) or JSON `null` therefore fails on every `Option` field (`var()` `fallback`/`from`, anonymous `@layer` name, `@container` name...). The PR rewrites `Unit` to `Option(None)` recursively before deserializing in the three places that buffer a `serde_content::Value`: `Property` (`src/properties/mod.rs`), `CssRule` (`src/rules/mod.rs`) and napi `ValueOrVec` (which also covers `TokensOrRaw`). Bug confirmed on master (574eee2), fixed by the PR merged onto master (clean merge, built as 2665ca7).

## Design
- **Coverage is complete.** `grep serde_content` finds exactly these buffering points (plus `TokensOrRaw`, which delegates to `ValueOrVec`). Every other napi return path deserializes straight from the napi deserializer, whose `deserialize_option` already maps null/undefined to `None`. Untagged enums go through serde's own private `Content`, which handles `Unit` correctly.
- **Semantics vs. pre-#1062 behaviour.** serde's `ContentDeserializer::deserialize_option` (serde 1.0.228 `private/de.rs:1289`) does `Content::Unit => visitor.visit_unit()`, and `OptionVisitor::visit_unit` returns `None`; `Unit` stays `Unit` for `deserialize_unit`/unit structs. The PR instead erases `Unit` everywhere, so a `null` for a unit-typed value would now fail (`deserialize_unit` requires `Value::Unit`). I found no such type in the serialized AST: no `()` fields, no `Option<Option<_>>`; the only unit struct, `DefaultAtRule`, is never constructed (`DefaultAtRuleParser` always errors); untagged enums don't serialize unit variants as null. So no behaviour difference today, but it is a latent trap.
- **The truly general fix** is one line in serde-content (`deserialize_option`: `Value::Unit => visitor.visit_unit()`, matching serde). serde-content 0.1.2 (Jan 2025) is the latest release; I could not read its issue tracker from this session. Without forking/patching the crate, normalizing the `Value` is the pragmatic place, and the PR does it at the three entry points instead of per-type. Reasonable.
- **Duplicated helper** in `napi/src/transformer.rs` (crate can't reach `lightningcss::serialization`). Nit: could be a `#[doc(hidden)] pub` fn under the `nodejs` feature, but that adds public surface; duplication of 10 lines is acceptable.
- **Complexity/perf.** Each nesting level re-walks its subtree (napi `ValueOrVec` → `CssRule` → nested `CssRule` → `Property`), i.e. O(depth × size) — but master already rebuilds the `serde_content::Value` at each of those levels, so the order is unchanged and the walk moves values (no clone). Measured: no difference (below).
- Philosophy: n/a (no CSS syntax change). No public API / AST shape change.

## Findings
1. **nit** — Unit erasure is broader than serde's semantics (see Design). Suggest a comment noting that unit-typed values would break, or an upstream serde-content fix later so the walk can be dropped.
2. **nit** — duplicated `null_to_none` in napi.
3. **Out of scope, pre-existing (not caused by this PR):**
   - #1188: serde-content `coerce_numbers` rejects integral values ≥ 65536 for `f32` fields: `.a{border-radius:65536px}` or Open Props' `--radius-round:1e5px` with any identity Declaration/Rule/StyleSheet visitor → `expected a 32-bit floating point, found 65536i64` on both base and PR (65535 works). So the PR's "all 15 stylesheets deserialize" holds for serde_json, but Open Props still fails via the JS visitor path.
   - Round-trip fidelity: percentage tokens lose `int_value` (not serialized), so `calc(100% - var(--w))` → `calc(100.0% - var(--w))` after an identity StyleSheet visitor. Same in 1.30.1 (checked with `scripts/repro.mjs --versions 1.30.1`).
   - Rule visitor cost grows super-linearly with nesting depth on master: 200 trees × depth 30 with `Rule(r){return r}`-style visitor took 66 s on base (depth 8: ~1 s). Unrelated to the PR.
