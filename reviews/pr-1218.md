# PR #1218: feat: Added support for container-type: anchored and @container anchored()
**Verdict:** request changes (plus a maintainer decision on a draft flag). **Confidence:** high.

## Summary
Adds `anchored` to `container-type` (now a bitflags type, which also makes valid combinations like `size scroll-state` parse), and `@container anchored(<anchored-query>)` with a typed `fallback:` feature built on new `TryTactic` (bitflags) / `PositionTryFallback` types in `rules/position_try.rs`. The bug in #1176 is real: master and 1.33.0 error in strict mode with `Unexpected token Function("anchored")`, which is what fails `vite build` (Vite's lightningcss minifier spreads `css.lightningcss` and doesn't set `errorRecovery`). With `errorRecovery` on master, the rule passes through verbatim with a warning (verified with CLI and with npm 1.33.0 via the stored repro), so the Vite failure is strict-mode only; `css: { lightningcss: { errorRecovery: true } }` is a working workaround today. The PR merges cleanly onto master 574eee2 and its tests pass, but storing `<try-tactic>` as bitflags reorders the keywords, and the spec says the order is significant: real anchored queries silently stop matching.

## Design
- **`TryTactic` must be an ordered list, not bitflags.** css-anchor-position-1: "If multiple keywords are given, the transformations are composed in order", and css-anchor-position-2 for the `fallback` feature: "The order of <try-tactic>s is significant ... the order must match". Bitflags canonicalize order, so the type is wrong for both this feature and a future `position-try-fallbacks` property (which master doesn't parse yet; the maintainer asked to reuse "the same types as position-try-fallbacks", and these types will be what that property gets, so getting them right matters beyond this PR). Suggest `SmallVec<[TryTacticKeyword; 2]>` (or a fixed array) rejecting duplicates, serialized in source order; the JSON AST would then be an ordered array, which it already looks like.
- **Grammar strictness:** `[<dashed-ident> || <try-tactic>]` means the tactic keywords are one contiguous component. The parser's loop accepts `flip-block --x flip-inline` and rewrites it to valid `--x flip-block flip-inline` (Chrome rejects `position-try-fallbacks: flip-block --x flip-inline`). Parse name, then tactic list, then name (if not yet seen).
- **`container-type` bitflags:** fine and matches the grammar `normal | [ [ size | inline-size ] || scroll-state || anchored ]`; order there is not significant (Chrome itself canonicalizes to `inline-size scroll-state anchored`, same order as the PR). Invalid combos (`size inline-size`, `anchored anchored`) fall back to unparsed as before.
- **AST change:** `ContainerType` goes from `"inline-size"` to `["inline-size"]` (`"normal"` stays a string). Calibration said the AST change is fine for #1176, but note this is a shape change for existing values (not only an added union case) that JS visitors reading `container-type` will see. Call it out in the changelog.
- **Not covered:** `<position-area-query>` (`anchored(fallback: top)`, `bottom any`) and `<general-enclosed>` inside `anchored()` still hard-error in strict mode. Acceptable as documented gaps, but they keep the same Vite failure for those inputs.
- **Draft flag (maintainer decision).** Spec status: css-anchor-position-2 FPWD 21 Oct 2025, Work Status "exploring" (ED). Support (BCD in repo): Chrome/Edge 143 only, Firefox/Safari no, marked experimental. Open CSSWG issues still propose changing matching semantics: w3c/csswg-drafts#14350 (match explicit areas instead of the tactic that produced them) and #14351 (match the current position, not only fallbacks); #13092 (`<anchored-feature>` undefined) is open too. Per the calibration ("single-browser features: an early draft goes behind a flag") this fits a `ParserFlags` draft flag. Counterpoint: `scroll-state()` / `container-type: scroll-state` has identical status (conditional-5 exploring, Chrome-only since 133) and is unflagged, so either way is consistent with *some* precedent. Note a flag alone doesn't fix default Vite builds; users would need `css.lightningcss.drafts.<flag>` or `errorRecovery`. A more general fix for the strict-mode failure would be treating unknown functions in container/media conditions as `<general-enclosed>` (currently `@container foo(x)` and `@media foo(x)` also hard-error, while `(min-foo: 1px)` passes) — separate change, flagged in the #1176 triage.

## Spec
- css-anchor-position-2 (https://drafts.csswg.org/css-anchor-position-2/#container-rule-anchored): `<query-in-parens> = ... | anchored( <anchored-query> )`; `<anchored-query> = not <anchored-in-parens> | <anchored-in-parens> [ [ and <anchored-in-parens> ]* | [ or <anchored-in-parens> ]* ] | <anchored-feature>`; `<anchored-in-parens> = ( <anchored-query> ) | ( <anchored-feature> ) | <general-enclosed>`.
- `fallback` descriptor: `Value: none | [ [<dashed-ident> || <try-tactic>] | <position-area-query> ]`. "The order of <try-tactic>s is significant. For instance `flip-start flip-block` is not the same as `flip-block flip-start`. Hence, the order must match for '@container/fallback' queries."
- css-anchor-position-1 (https://drafts.csswg.org/css-anchor-position-1/#typedef-position-try-fallbacks-try-tactic): `<try-tactic> = flip-block || flip-inline || flip-start || flip-x || flip-y`; "If multiple keywords are given, the transformations are composed in order to produce a single position option."
- `container-type` (anchor-position-2): `normal | [ [ size | inline-size ] || scroll-state || anchored ]`.
- Chromium 153: CSSOM keeps `anchored(fallback: flip-start flip-block)` and `position-try-fallbacks: flip-start flip-block` in source order; with an anchor fixture where `flip-start flip-block` is the applied fallback, `@container anchored(fallback: flip-start flip-block)` matches and `anchored(fallback: flip-block flip-start)` doesn't (probe.mjs, computed color).

## Findings
1. **Blocking: try-tactic order is lost, queries stop matching.**
   Input (fixture: anchor at top of viewport, `.pop{position-area:top;position-try-fallbacks:flip-start flip-block;container-type:anchored}`):
   `@container anchored(fallback: flip-start flip-block){.c{color:green}} @container anchored(fallback: flip-block flip-start){.c{background-color:red}}`
   - master `--error-recovery`: kept verbatim, equivalent (green applies).
   - PR (any mode): `@container anchored(fallback:flip-block flip-start){.c{color:green;background-color:red}}` — reordered, then the two rules merge; in Chrome the green style no longer applies. NOT EQUIV.
   - Even commuting tactics break, since matching is exact: `position-try-fallbacks:flip-inline flip-block` + `anchored(fallback: flip-inline flip-block)` → PR emits `flip-block flip-inline`, no longer matches. NOT EQUIV.
   - The PR's tests enshrine this: `flip-start flip-block` → `flip-block flip-start`, `flip-y flip-x` → `flip-x flip-y`.
   Fix: ordered list type for `<try-tactic>`, serialize in source order; fix the tests.
2. **Should fix: invalid fallback value repaired into a valid, matching one.** `anchored(fallback: flip-block --x flip-inline)` (invalid: tactic keywords split) → PR emits `anchored(fallback:--x flip-block flip-inline)`. With `position-try-fallbacks:--x flip-block flip-inline` applied, Chrome doesn't match the original (master error-recovery output) but matches the PR output (red applied). Also strict mode should error on it. Fix: parse `<dashed-ident>?` / contiguous tactics / `<dashed-ident>?`.
3. **Decision: draft flag** (see Design). Recommend behind a `ParserFlags` draft flag per calibration, with the `drafts` option exposed in JS/`node/index.d.ts`, unless the maintainer prefers consistency with unflagged `scroll-state()`.
4. **Nit/call out:** `ContainerType` JSON shape change (string → array) for existing values. `<position-area-query>` and `<general-enclosed>` inside `anchored()` still hard-error in strict mode (documented in a doc comment only).
