# PR #1321: Add ::scroll-marker, ::scroll-marker-group and ::scroll-button()
**Verdict:** request changes. **Confidence:** high.

Author: oddharsh. Closes #1177, part of #1184. Head 5b7e370, base c6a0c3c (22 commits behind master 8823beb; merges cleanly per `git merge-tree`). No CI check runs on the head commit.

## Summary
Adds typed `ScrollMarker`, `ScrollMarkerGroup` and `ScrollButton { direction: ScrollButtonDirection }` pseudo-elements, only when `ParserFlags::SCROLL_NAVIGATION_CONTROLS` is set (the existing draft flag from #1185). It adds an `AFTER_SCROLL_MARKER` parse state so `::scroll-marker:target-current/-before/-after` is accepted, and regenerates compat data via `build-prefixes.js` (Chrome 135, no Firefox or Safari). With the flag off nothing changes (verified). The bug is real but small: on master these selectors produce an "unrecognized pseudo-element" warning and pass through unchanged, both with and without the flag. The maintainer said on #1177 that this is an early Chrome-only draft, so keeping it behind the flag is right. Note that the flag does not remove the warning for Next.js/Turbopack users unless they turn the flag on.

The blocking problem is that once the flag is on, valid spec CSS that master passes through becomes an error: `::scroll-button(*):disabled` / `:enabled`.

## Design
- Good: fully parsed (typed direction enum, canonical serialization), behind the draft flag, compat generated by the script rather than hand-edited, and an additive AST change.
- Incomplete special case: the after-pseudo-element exception is keyed to `::scroll-marker` only (`is_scroll_marker` + `is_valid_after_scroll_marker` + a new state bit). The same spec section allows `:disabled` on `::scroll-button()`, and Chromium accepts `:enabled` too. Each future pseudo-element exception would need another bit and another trait method, following the `AFTER_WEBKIT_SCROLLBAR` precedent. A more reusable shape is one hook on `parcel_selectors::parser::PseudoElement`, e.g. `fn is_valid_pseudo_class_after(&self, pc: &<Self::Impl as SelectorImpl>::NonTSPseudoClass) -> bool`, defaulting to `pc.is_user_action_state()`, with the compound-selector loop remembering the last pseudo-element. At minimum, `ScrollButton` needs its own allowance for `:disabled`/`:enabled`. It must not simply reuse the scroll-marker allowance, because Chromium rejects `::scroll-button(*):target-current`.
- `::column` (multicol-2, used as `::column::scroll-marker`, Chrome 135) is not added. It still passes through as unknown, which is fine for now but worth noting for #1184.

## Spec
css-overflow-5 ED (https://drafts.csswg.org/css-overflow-5/), fetched 2026-11-22:
- §3.2: "The ::scroll-button( '*' | <scroll-button-direction> ) pseudo-elements are generated on scroll containers…". The direction keywords are up, down, left, right, block-start, block-end, inline-start, inline-end, prev, next. The PR's enum matches exactly.
- §3.2: "**The :disabled pseudo-class can apply to ::scroll-button().** It matches a given button when their originating element can't be scrolled in their associated direction."
- §3.1.7: ":target-current … :target-before and :target-after pseudo-classes for use with scroll marker elements." This supports the PR's scroll-marker exception.
- §3.3.2: `:focus`, `:focus-visible` and `:active` match on the pseudo-elements, and `:focus-within` on `::scroll-marker-group`. These are user-action states and already allowed.
- Chromium 153 (`CSS.supports('selector(…)')`): `::scroll-button(*):disabled` true, `::scroll-button(*):enabled` true, `::scroll-button(*):not(:disabled)` true, `::scroll-marker:target-current` true, `::scroll-marker-group:target-current` false, `::scroll-button(*):target-current` false, `::scroll-button(sideways)` false, `::scroll-button(right left)` false, `::column::scroll-marker` true.
- Support (mdn-bcd 8.0.7): all three are Chrome/Edge 135, Opera 120, Samsung 29 and WebView 135, marked experimental, with no Firefox or Safari support. So the draft flag is appropriate.

## Findings
1. **Blocking: `::scroll-button():disabled` / `:enabled` become errors with the flag on.** Input `.c::scroll-button(*):disabled{opacity:.5}` with `--scroll-navigation-controls`:
   - base: passes through unchanged;
   - PR (strict): error "Invalid pseudo class after pseudo element, only user action pseudo classes…";
   - PR `--error-recovery`: warning, and **the rule is dropped**, whereas Chromium keeps and applies it.

   This is the standard carousel pattern for disabled prev/next buttons. `:enabled` and `:not(:disabled)` are affected too. cases.mjs classifies 6 runs as regressions (strict) and 3 as changed (rule dropped under recovery). Fix: see Design. Add tests for `:disabled`/`:enabled` after `::scroll-button()`, plus an error test that `::scroll-button(*):target-current` is still rejected.
2. **Should fix: `node/ast.d.ts` not regenerated.** The new `scroll-marker` / `scroll-marker-group` / `scroll-button` kinds and `ScrollButtonDirection` appear in the jsonschema output (`cargo run --example schema --features jsonschema`: 7 matches in `node/ast.json`), but `node/ast.d.ts` has none. Master now enforces this in CI (#1407, `yarn build-ast && git diff --exit-code node/ast.d.ts`), so after a rebase CI will fail until `yarn build-ast` is run.
3. **Note (Chromium bug, maintainer call): canonical lowercasing changes rendering in Chrome.** The PR serializes `::SCROLL-BUTTON(BLOCK-START)` as `::scroll-button(block-start)`. That is spec-correct, since keywords are ASCII case-insensitive. But Chromium 153 appears to treat an uppercase argument as `*`: with a 100px scroller and buttons `height:50px; display:block`, `document.body.scrollHeight` is 300 for `(BLOCK-START)` (four buttons) and 150 for `(block-start)` (one button). The oracle reported NOT EQUIV (80 diffs) for that case. Real authors essentially never write the uppercase form, and the spec is the source of truth, so I'd leave it as is. Optionally file a Chromium bug.
4. **Note: rule merging without targets.** Without targets, `.a::scroll-marker{color:red}.b{color:red}` now minifies to `.a::scroll-marker,.b{color:red}`, which Firefox/Safari would drop entirely. With targets the compat data correctly blocks the merge (safari 18, firefox 140 and chrome 130 stay unmerged; chrome 140 merges). Master behaves the same way for `::checkmark` and `:target-current`, so this is consistent with the existing no-targets policy and not specific to this PR.
5. Nit: "Closes #1177" covers the selectors, but #1177 also lists the `scroll-marker-group` property, which still passes through as an unparsed property (no warning). It also only helps users who turn the flag on.
