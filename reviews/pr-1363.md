# PR #1363: fix: keep caret, caret-color and caret-shape in source order
**Verdict:** request changes (small, one-line follow-up). **Confidence:** high on the code behavior, medium on real-world impact (no browser ships the `caret` shorthand yet).

## Summary
`FallbackHandler` (src/properties/prefix_handler.rs, `define_fallbacks!`) keeps one output index per property and writes a later declaration back at that index. `caret` and `caret-color` have separate slots, so `caret-color:red;caret:auto;caret-color:blue` became `caret-color:#00f;caret:auto` (the shorthand now resets the color to auto). The PR clears the opposite slot whenever `caret` / `caret-color` / `caret-shape` is seen (parsed or unparsed), so the later declaration is appended in source order. The bug is real per the spec and the PR fixes the four cases it lists. It misses `caret-animation`, the third longhand, which Lightning CSS doesn't type.

## Design
- Placement is reasonable. The bug is in `FallbackHandler`'s slot write-back, and `caret` is the only shorthand/longhand pair among its slots (Color, TextShadow, Filter, BackdropFilter, Fill, Stroke, CaretColor, Caret). A generic "shorthand resets longhands" mechanism isn't warranted for one pair.
- Cost: one extra `match` per property reaching `FallbackHandler`. That's negligible, and size-check showed no change.
- Keeping the earlier, now-dead declaration (`caret-color:red` before `caret:auto`) is correct, not just simpler: no browser supports `caret` (Chromium 153 `CSS.supports('caret','auto')` is false), so that earlier longhand is the fallback in every real browser today.
- **Gap (should fix):** the spec's `caret` is `<'caret-color'> || <'caret-animation'> || <'caret-shape'>`. `caret-animation` isn't in `properties/mod.rs`, so it parses as `Property::Custom(Unknown)` and never hits the PR's match. This is exactly the case #1365's `is_unknown_longhand(name, prefix)` helper (custom.rs) is for, also used by #1209-style handlers. Suggested addition to the PR's first match:
  `Property::Custom(val) if is_unknown_longhand(&val.name, "caret-") => self.caret = None,`
  This only clears the slot. The handler still returns false and the declaration is pushed by the normal path. If #1365 hasn't landed, inline `matches!(&val.name, CustomPropertyName::Unknown(n) if n.starts_with("caret-"))`, and whichever PR lands second switches to the helper. I prototyped the inline version in the PR worktree: `.foo{caret:red;caret-animation:manual;caret:green}` → `.foo{caret:red;caret-animation:manual;caret:green}`. `test_ui` passes with the extra test. Without it, the PR outputs `caret:green;caret-animation:manual`, so `manual` wins instead of the shorthand's reset to `auto`.
- Separate pre-existing gap (not this PR): Lightning's `Caret` type lacks the `caret-animation` component, so `caret: block manual` passes through untyped. A follow-up issue could cover typing `caret-animation`, which would also make the Custom branch unnecessary.

## Spec
css-ui-4 ED (https://drafts.csswg.org/css-ui-4/#propdef-caret): "Value: <'caret-color'> || <'caret-animation'> || <'caret-shape'>" … "This property is a shorthand for setting caret-color, caret-animation, and caret-shape in one declaration. Omitted values are set to their initial values."
Browser: Chromium 153 supports `caret-color`, `caret-shape` and `caret-animation` but not the `caret` shorthand (`CSS.supports('caret','red')`, `('caret','auto')` and `('caret','red manual')` are all false).

## Findings
1. **Should fix: `caret-animation` is still reordered.** Input `.a{caret:red;caret-animation:manual;caret:green}`. Base and PR both output `.a{caret:green;caret-animation:manual}`. Per the spec the result should be `caret-animation:auto` (reset by the last `caret`), but the output gives `manual`. Fix: the one-line `is_unknown_longhand` arm above. The browser check can't observe this because Chromium lacks `caret`.
2. Nit: the comment could mention that the earlier declaration is deliberately kept as a fallback for browsers without `caret`.
