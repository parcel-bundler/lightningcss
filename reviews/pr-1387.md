# PR #1387: Keep position, direction and unicode-bidi in source order before var() values
**Verdict:** approve with nits. **Confidence:** high.

Author: mkantautas. Fixes #1225. Base ab14f90; 10 commits behind master, none touching `src/declaration.rs` or `src/properties/position.rs`; merges cleanly. No CI check runs are reported on the head commit (7f1b4b4), probably because workflows haven't been approved for a first-time contributor.

## Summary
`PositionHandler` buffered `position` until `finalize` but let an unparsed `position` (var()/env()/CSS-wide keyword) go straight to the output, so `position:static;position:var(--x,static)` came out reversed and the fallback won. `DeclarationHandler` did the same for `direction`/`unicode-bidi`, which it holds as `Option`s because `all` does not reset them. The PR makes `PositionHandler` flush before an unparsed `position` (the same as `DisplayHandler`/`OverflowHandler`). It also turns the `direction`/`unicode-bidi` fields into `DeclarationList`s that keep parsed and unparsed declarations in source order and survive `all`. The bug is real and reproduces on base in Chromium (below). The PR also fixes two related bugs it didn't advertise: a CSS-wide keyword was reordered too (`direction:ltr;direction:inherit` → `direction:inherit;direction:ltr` on base), and `all` silently dropped an unparsed `direction`/`unicode-bidi` that came before it.

## Design
- **Generality:** I checked every non-prefixed property in mdn-data with a simple initial value (362 properties) as `p: <initial>; p: var(--x, <initial>)` under `--minify`, with and without old targets (`safari 8`, `chrome 40`). On base, only `direction`, `position` and `unicode-bidi` reorder; on the PR, none do. That matches the issue's audit, and every other `PropertyHandler` (or the `shorthand_handler!` macro) already has an `Unparsed` arm. So the fix is complete.
- **Placement:** Position uses the established flush-before-unparsed pattern, which is right. For direction/unicode-bidi, a list rather than "flush and push to `decls`" is needed, because `decls` is wiped by `all` and these two must survive it. That is justified, not over-engineering.
- **Nit (complexity):** on a parsed value, `retain(|d| matches!(d, Unparsed))` scans the list. With many unparsed values interleaved it is quadratic: one rule with N× `direction:var(--aI);direction:rtl` takes 15/32/85/392/3111 ms at N=2.5k/5k/10k/20k/40k on the PR, against ~30–130 ms on base. That input is pathological, not realistic, so it doesn't block. A parsed declaration overrides every earlier declaration of the property in the same importance bucket, whatever they are (an earlier `var()` is overridden at cascade time; an invalid unparsed value is ignored anyway). So `clear()` followed by `push` is correct, O(1), and drops the dead declarations as well. With that change, `rtl;var(--x);ltr` → `direction:ltr` instead of `direction:var(--x);direction:ltr`, and the test expectation would need updating. Not prototyped/built.
- **Philosophy:** no parsing changes, no new syntax, no flags needed.

## Spec
css-cascade-5 §all (https://drafts.csswg.org/css-cascade-5/#all-shorthand), fetched today: "The all property is a shorthand that resets all CSS properties except direction and unicode-bidi. It only accepts the CSS-wide keywords. It does not reset custom properties." So `direction:var(--x); all:revert-layer` must keep the `direction` declaration, which base drops. Declarations with var() are valid at parse time and win in the cascade by order (css-variables-1; not quoted, the fetch failed to extract).

## Findings
1. **nit:** quadratic `retain` in `handle_all` on pathological input (numbers above); suggest `self.direction.clear()` / `self.unicode_bidi.clear()` before the push for parsed values.
2. **nit (size, consistent with existing handlers):** `position:static;position:var(--x);position:relative` now keeps the dead `position:static` (base: `position:var(--x);position:relative`; PR: `position:static;position:var(--x);position:relative`). `DisplayHandler` behaves the same (`display:block;display:var(--x);display:flex` is kept whole on base), so this is acceptable. Zero effect on any corpus.
