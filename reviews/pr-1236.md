# PR #1236: Fix nondeterministic dedup caused by stale StyleRuleKey
**Verdict:** approve with nits (one should-fix: quadratic slowdown on CSS-modules bundles; fix it in this PR or in a follow-up). **Confidence:** high on correctness and on the nondeterminism fix; medium on how much the perf finding matters in practice.

## Summary
In `CssRuleList::minify`, the dedup map is `HashMap<StyleRuleKey, usize>`. Each key stores its hash once, when the rule is inserted, but `Eq` reads the rule as it is *now* (`list[index]`). When `merge_style_rules` later changes the rule, or the cascade loop `rules.pop()`s it and reuses its index, the stored hash and the live content no longer match. The PR replaces the map with `StyleRulesTracker`: `hash -> SmallVec<idx>` buckets plus an `idx -> hash` map. It rehashes a rule after each merge (`refresh`), drops the popped index (`drop_at`), and checks every candidate against the live rule with `is_duplicate`, so a cross-file CSS-modules candidate no longer hides a same-file one.

The bug is real and worse than the title says. On current master it **silently drops live rules**, nondeterministically per process, because `AHasher::default()` gets random keys per process. I reproduced this (below). The PR fixes it on both its own base and on current master.

**Still applies?** The PR is 40 commits behind master (`mergeable_state: behind`, base `df63db2`). `git merge-tree origin/master refs/review/pr-1236` merges with **no conflicts**. I built and tested the merged tree (`refs/review/pr-1236-on-master` = 7104b2c, built at `target/review/ref-7104b2c`). Commit 93b9e66 (importance in `hash_key`/`is_duplicate`, #1347) is already on master, and the PR's design depends only on those two functions, so the two changes compose correctly. The merged build passes the #1347 probe, which the PR's own base still fails.

## Findings

1. **should fix: CSS-modules cross-file duplicates make dedup quadratic.**
   - **Cause:** in the base code, `style_rules.remove(&key)` drops a cross-file candidate from the map even when it isn't removed, so each bucket holds one entry. In the PR, a non-removable candidate stays in its bucket. Every later identical rule from another file adds an entry, and `find_duplicate` scans the whole bucket, calling `is_duplicate` on each entry.
   - **Input:** N module files, each `body{margin:0} .k{color:red}`, imported from one entry, run with `--bundle --css-modules --minify`. Median of 3 runs, master vs PR merged onto master; output identical:

     | files | master | PR |
     |---|---|---|
     | 1500 | 31 ms | 100 ms |
     | 3000 | 55 ms | 377 ms |
     | 6000 | 100 ms | 1856 ms |
     | 12000 | 228 ms | 7720 ms |

     Master grows linearly; the PR grows quadratically.
   - **Second variant:** the cross-file rules are adjacent (each file only `body{margin:0}`). They merge into one `body,body,…` rule (pre-existing behavior), and `refresh` rehashes the growing selector list on every merge: 12000 files take 457 ms on master and 2676 ms with the PR. Master is already superlinear here.
   - **Suggested fix:** when `context.css_modules` is set, fold `source_index` into the bucket key. Then a bucket only holds same-file candidates, and the `is_removable` predicate (and the scan) go away. Alternatively, when a non-removable duplicate is found, replace it in the bucket with the new rule (the base behavior), and accept missing the PR's `test_css_module_dedup_skips_cross_file_candidate` scenario, which base already handles; see 3.
   - **Non-CSS-modules builds:** I found no unbounded growth. Buckets can hold mutually-duplicate entries after a `refresh`, but `find` stops at the first match.

2. **nit: `refresh` costs some time on merge-heavy input.**
   - On a 2.5 MB random merge-heavy stylesheet (`rand_big.css`, 60k small rules over 400 selectors), the merged-on-master build takes 266 ms vs 252 ms on master (+5.5%, interleaved medians of 15 runs; the machine is shared, so this is near noise).
   - bootstrap.css (281 KB) and bulma.css (763 KB) show no difference (22 ms vs 22 ms for bulma).
   - The PR's own hyperfine numbers (±1.6%) agree.
   - It is acceptable, but `refresh` could skip rehashing in the sel_eq branch when the property-id list didn't change.

3. **nit: test-quality notes.** I reasoned about each test from base CLI outputs; I did not run the tests on base.
   - `test_dedup_finds_duplicate_after_merge_collapses_longhands` and `test_dedup_finds_duplicate_after_cascading_merge` fail on base. Base outputs `.a{border-radius:16px}.x{color:red}.a{border-radius:16px}`.
   - `test_dedup_after_merge_preserves_merged_declarations`, `test_cascade_pop_clears_orphaned_style_rules_entry` and `test_css_module_dedup_skips_cross_file_candidate` **pass on base too**: the CLI gives identical output on base, PR, master and merged. They guard the new design, not a base bug, which the PR description states for two of them.
   - **Missing:** a regression test for the most serious symptom, *dropping a live rule*. The rule-drop repro below (from issue #1235 comments) depends on the hash seed, so a plain `minify_test` won't fail reliably on base.
     - An input with ~100 independent copies of the pattern in separate nested lists would fail on base with near certainty: 85–92 of 100 processes in my runs. A test that asserts the expected output (or that every `[aria-hidden]` rule survives) would catch it.
     - Alternatively, a unit test that minifies the 5-rule repro under a seeded hasher would do.

4. **nit: code.**
   - `untrack` and `drop_at` are identical.
   - `bucket_for: HashMap<usize, u64>` uses the default SipHash. Indices are dense, so a `Vec<Option<u64>>` (or storing the hash beside the rule) would be simpler and faster.
   - `rules.iter_mut().enumerate().next_back()` could be `let last_idx = rules.len() - 1` plus `last_mut()`.
   - An optional improvement, not required: when `refresh` moves a rule into a bucket that already holds an earlier duplicate, the earlier one could be marked `Ignored`. Neither base nor the PR does this today.

There are no public API changes. `StyleRuleKey` was `pub(crate)`, and the AST is unaffected. The new `unreachable!()` sits on a slot that was just pushed in the `CssRule::Style` arm, so it is safe. `cargo fmt --check` is clean on the merged tree.

## Tooling feedback
- **cases.mjs, `/* args: */` handling:** a case's args are *appended* to every `--config` rather than replacing it. The output shows `[--minify --minify --targets 'safari 12']` and `[--targets 'chrome 80' --minify --targets 'safari 12']`, so the configs in a case with args collapse into duplicates or conflicting `--targets`. Either replace the config, or document the appending and dedupe the runs.
- **cases.mjs / equivalence.mjs, false positive:** both report NOT EQUIVALENT when output lowered for old Safari uses `:lang(a,b,…)`, which Chromium 153 doesn't support. A known-artifact list, or a note in the summary when the targets aren't Chromium, would help. Worth a pitfalls entry: "logical-property lowering with `--targets safari` → false NOT EQUIVALENT in Chromium".
- **equivalence.mjs output:** it prints the full transformed CSS to stdout before the verdict, even with `--transformed`. On large inputs this floods the output (44 KB for four 15 KB inputs). A `--quiet` flag, or printing only the verdict and diffs, would help.
- **cases.mjs, nondeterminism:** neither tool can detect nondeterminism, because each runs the CLI once. A `--repeat N` option that flags differing outputs across processes would have found this bug class directly. I had to hand-roll loops.
- **build-pr.sh:**
  - It worked. A first build of two trees took more than 10 minutes on the shared machine, so the skill could suggest `run_in_background`.
  - It always uses the *merge base* as BASE. For stale PRs (this one is 40 commits behind), an option to also build "PR merged onto current master" would save the manual `git merge-tree` + `commit-tree` + `build-pr.sh <ref> origin/master` steps I used.
  - The CLI needs absolute paths with `--bundle`: a relative entry path panics with ResolverError NotFound. This is pre-existing, not in the scripts, but it confuses CSS-modules checks.
- **Skill gaps:**
  - The skill tells reviewers to fetch spec text via a web-fetch agent, but drafts.csswg.org was not on this session's network allowlist, and no Agent tool was available to me.
  - It has no guidance on nondeterminism or hash-seed bugs: run many processes, amplify with independent copies, and make sure the copies use *distinct* selectors. My first amplified fixture repeated identical nested selectors, so every copy hashed the same and it never triggered.
  - It has no guidance on CSS-modules bundle scaling or `--bundle` perf fixtures.

## Re-review (2026-11-24, head 4341a40, merged onto master 4eee08cb)
**Verdict:** merge. The head was rebased: 4cad72f is the old f768a22 content, and 4341a40 is new.

Our posted points:
1. **Quadratic with CSS modules: fully addressed.** `StyleRulesTracker::key` XORs `(source_index+1)*golden` into the hash when `css_modules` is on, so cross-file duplicates land in separate buckets. Cachegrind instruction counts match master (cssmk 3k/6k/12k: 130/257/514M on master vs 129/257/512M on the PR). The earlier head took 7.7 s against master's 228 ms at 12k.
2. **Bookkeeping, and measuring the precomputed hash: addressed in substance.**
   - The design changed to a "pending last rule". A rule is keyed only when the next dedup-eligible rule is pushed, because `merge_style_rules` only mutates the tail. A keyed rule that a cascade pop re-exposes is un-keyed and made pending again. So indexed rules are immutable, and no rehash happens on merges.
   - The author did not benchmark rehash-on-lookup. That alternative would not have fixed the bug on its own: hashbrown places entries by their insert-time hash, and h2-tag probing makes the misses seed-dependent.
   - Measured overhead: +0.5% instructions on bulma, +1.2% on bootstrap, ~0 elsewhere.
3. **Reliable failing test: addressed.** `test_dedup_does_not_remove_rule_pushed_at_popped_index` fails on every master run: master drops `.d{border-top-right-radius:8px}`.

Evidence (details in queue/review-1236.json; cases in r1236/cases.css, output in r1236/cases-out.txt):
- **cases.mjs `--repeat 20` (35 cases, 10 new):** PR output is deterministic everywhere, and every PR output is browser-equivalent except the known `:lang()` safari oracle artifact.
- **Rule loss:**

  - flat_drop: 5/300 vs 0/300.

- **Pre-existing:** adjacent `.cN{margin:0}` runs are quadratic on master as well (5.2G instructions at 20k). This is a follow-up, not caused by this PR.
