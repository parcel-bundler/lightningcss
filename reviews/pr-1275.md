# PR #1275: fix: restore declarations for incompatible selectors after rule merge
**Verdict:** approve with nits. **Confidence:** high.

## Summary
When a selector list must be split for targets (an unsupported selector such as `:has()` / `:focus-visible`, and `:is()` wrapping not possible), `CssRuleList::minify` keeps the compatible selectors in `style`, then `merge_style_rules` may merge it into the previous rule with identical selectors, which *drains* `style.declarations` (first branch of `merge_style_rules`, `src/rules/mod.rs` ~1046). The incompatible-selector clones are created afterwards from `style.clone()`, so they are empty and dropped by `!rule.is_empty()`. The bug is real (#1260): master (574eee24) `--minify --targets 'chrome 104'` on `.a:last-child{border-bottom:none}.a:last-child,.a:has(+ .b){display:flex}` gives `.a:last-child{border-bottom:none;display:flex}`; with `chrome 85`, `.a:hover{color:blue}.a:hover,.a:focus-visible{color:red}` gives `.a:hover{color:red}`. The PR snapshots `style.declarations` before the merge (only when `incompatible` is non-empty) and assigns it to each clone. PR output: `...;display:flex}.a:has(+.b){display:flex}` and `.a:hover{color:red}.a:focus-visible{color:red}`.

## Design
- Root cause correctly identified; the fix is local to the one place that builds incompatible-selector rules, which is the right place (no other code path clones `style` after a merge; nested rules disable merging, and the other two `merge_style_rules` branches drain selectors, not declarations).
- Only costs a declaration clone on the rare split path (incompatible non-empty), so no hot-path impact. Size-check: zero change on all corpora with and without targets.
- Simpler alternative (nit, not required): build `incompatible_rules` (clone + its `get_supports_rules`/`get_additional_rules`) *before* the merge attempt instead of snapshot-then-overwrite. That removes the extra snapshot clone (currently decls are cloned up to 3x per selector: snapshot, `style.clone()`, then `saved.clone()`) and makes the clones independent of merge side effects: `merge_style_rules` re-runs `last_style_rule.declarations.minify(..., &mut context.handler_context)`, so the handler context the clones' logical/`@supports` rules are read from after the merge can include state from re-minifying the previous rule's declarations. No observable bug found from this in testing (lab/@supports and logical-property cases were equivalent), so this is a robustness suggestion. The `incompatible` vector is consumed by that block anyway, and `context.handler_context.reset()` would stay after the main rule's supports/logical retrieval.
- Philosophy: no concerns (no new syntax, no hacks).

## Spec
Not a spec question: a minifier must not drop rules. Selector lists are non-forgiving (selectors-4 §"Selector lists": an invalid selector invalidates the whole list), which is why the split exists; `:has()` per https://drafts.csswg.org/selectors-4/#relational. (Not re-quoted; the issue does not hinge on spec wording.)

## Findings
1. **nit** Snapshot-then-overwrite clones declarations more than needed; hoisting clone construction above the merge is cleaner (see Design).
2. **nit (tests)** The test only covers pretty output with a non-conflicting property. Worth adding the issue's second shape, where the merged rule overrides a value of the previous rule (`.a:hover{color:blue}.a:hover,.a:focus-visible{color:red}` for chrome 85 → `.a:hover{color:red}.a:focus-visible{color:red}`), and/or a minified/`!important` variant.

No blocking findings.
