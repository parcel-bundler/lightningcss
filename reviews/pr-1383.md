# PR #1383: fix: parse nested light-dark() in custom properties once
**Verdict:** request changes (small: generalize to the sibling `rgb()`/`hsl()` path). **Confidence:** medium-high.

Author: BartWaardenburg. Fixes #1382. Head 5426acd, base 4a1b083 (master is 8823beb; `src/properties/custom.rs` is unchanged since 4a1b083, so the diff still applies as-is).

## Summary
In `TokenList::parse_into`, a function token is first tried as `UnresolvedColor::parse` inside `try_parse`; when that fails *after* fully parsing its argument token lists, the generic `Function` path parses the same arguments again, so each nesting level doubles the work. The PR adds `parse_light_dark`, which parses `light-dark()` arguments once and returns `UnresolvedColor::LightDark` (comma present) or a generic `Function` (no comma), propagating argument errors. It also passes `depth + 1` instead of resetting depth to 0. The bug is real and the light-dark fix works: `.a{--x:light-dark(`x22 `var(--a))`x22`}` 2.25 s → 0.014 s; x125/x250/x499 base >10 s (timeout) → 0.01–0.02 s. Output is byte-identical on all edge cases.

## Design
- **Not general.** The root cause is the "try `UnresolvedColor::parse`, then re-parse as a generic function" pattern, and it is shared by the `rgb()`/`hsl()` branches: they parse the `/ alpha` part with `TokenList::parse(input, options, 0)`, and an error inside the alpha makes the generic path parse it all again. The PR leaves that path exponential: `.a{--x:` + `rgb(0 0 0 / `x22 + `var(--a) ]` + `)`x22 `}` takes 7.1 s on base and 7.9 s on the PR (n=20: 1.5 s). The triage record for #1382 already flagged this.
- **Reusable place:** fix it once in `UnresolvedColor::parse` / its call site rather than special-casing `light-dark` before the generic `try_parse`. Concretely: pass `depth` into `UnresolvedColor::parse` (use `depth + 1` for all nested `TokenList::parse` calls), and distinguish "not this form" (fall back to the generic function, input reset) from "error inside an argument token list" (propagate, since the generic path hits the same tokens). For `rgb`/`hsl`, everything after the `/` is a single `TokenList::parse` that consumes the rest of the block, so any error there is fatal for the generic path too. That would cover light-dark, rgb and hsl and any future unresolved-color form. The PR's `parse_light_dark` is effectively this for one branch; moving the same idea into `UnresolvedColor::parse` (e.g. returning `Result<Option<Self>, _>` or parsing the alpha outside `try_parse`) is a small change.
- **Depth guard:** `rgb`/`hsl` still reset depth to 0, so the 500-level guard is bypassed there: `rgb(0 0 0 / `x20000 `1` `)`x20000 overflows the stack on both builds. The PR closes this for light-dark only.
- Complexity is minimal (one 25-line helper); fits the philosophy (still parsed into typed `UnresolvedColor`/`Function`, no change to strictness).
- No public API / AST change (`UnresolvedColor::parse` is private; the AST variants are unchanged).

## Spec
css-color-5 ED (https://drafts.csswg.org/css-color-5/#light-dark):
> `light-dark() = <light-dark-color> | <light-dark-image>`
> `<light-dark-color> = light-dark(<color>, <color>)`
> `<light-dark-image> = light-dark( [ <image> | none ] , [ <image> | none ] )`

Not decisive here: the PR changes only parse time, not which inputs become `LightDark` (same as base: any comma-separated token lists). Pre-existing: the image form inside a custom property is treated as `UnresolvedColor::LightDark` and lowered with `--lightningcss-light/dark` variables for old targets, same on both builds.

## Findings
1. **Should fix (incomplete fix, same bug class): `rgb()`/`hsl()` alpha path stays exponential.** Input `.a{--x:rgb(0 0 0 / rgb(0 0 0 / … var(--a) ] ))}` (22 levels): base 7.1 s, PR 7.9 s, both end with "Unexpected token CloseSquareBracket". Same for `hsl(0 0% 0% / …`. Suggested fix: as in Design (propagate alpha errors, pass depth). Per the calibration log, the maintainer prefers the fix in the shared place over a per-function special case.
2. **Should fix (same root): depth reset in `rgb`/`hsl`** (`TokenList::parse(input, options, 0)`) bypasses the 500-level nesting guard; 20000 levels → stack overflow on base and PR.
3. **Behavior change, acceptable:** >500 nested `light-dark()` now errors with `MaximumNestingDepth` (base: parsed, e.g. `light-dark(red,`x3000 `var(--a))` 1.3 s on base, error in 0.46 s on PR). Consistent with `var()`, `env()` and generic functions (`foo(`x600 already errors on base). I'd keep `depth + 1`.
4. **Out of scope, pre-existing:** `CssColor::parse` recursion has no depth guard: `color: light-dark(red,`x20000 `blue)` and the same in a custom property overflow the stack on both builds (try_parse_color_token runs first, so the TokenList guard never fires). Worth a separate issue (#1297 family).
5. Nit: test comment wording fine; the test's depth-40 case would hang on base (2^40), which is the intended regression check. Could add an `rgb(… / …)` case once generalized.
