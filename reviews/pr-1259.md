# PR #1259: fix: preserve `backdrop-filter` when webkit fallback is present
**Verdict:** request changes (incomplete fix; the parsed-value part is good). **Confidence:** high.

Author: fireairforce. Fixes #695 (21 upvotes, 17 comments; also next.js#78302, utoo#3090). Base ec16529, 30 commits behind master; `src/properties/prefix_handler.rs` is unchanged on master since then, so the base comparison still holds. CI: test, test-js and test-wasm all pass.

## Summary
`FallbackHandler` (the `define_fallbacks!` macro in `prefix_handler.rs`) keeps one index per property for every vendor prefix. So when a declaration arrives with a different prefix and the value is compatible, it overwrites the earlier one. `backdrop-filter:blur(10px);-webkit-backdrop-filter:blur(10px)` minifies to `-webkit-backdrop-filter:blur(10px)` for every config, and with no targets the reverse order drops the `-webkit-` one. The bug is real. Chromium does not support `-webkit-backdrop-filter` (`CSS.supports('-webkit-backdrop-filter','blur(1px)')` => false), so in Chrome/Edge/Firefox the effect disappears. That is a silent, widespread breakage, and Vite 8 now defaults to lightningcss for CSS minification. The PR makes the parsed-value branch prefix-aware:
- an equal value merges prefixes;
- a different value with overlapping prefixes is split or replaced;
- a different value with a disjoint prefix is pushed as a new declaration.

The parsed-value fix is correct in every case I tried. It does **not** touch the `Property::Unparsed` branch of the same function, which has the identical bug for `var()` values.

## Design
- **Right place, mostly general.** The change is in the shared macro, so it covers every prefixed fallback property: `BackdropFilter(prefix)` and `Filter(prefix)`. `filter`/`-webkit-filter` is fixed too (checked: `filter:blur(10px);-webkit-filter:blur(2px)` went from base `-webkit-filter:blur(2px)` to PR, which keeps both). The logic mirrors `PrefixHandler`: same value → merge prefixes, otherwise track a new entry. That is the established pattern.
- **Incomplete: the `Property::Unparsed` arm** (same macro, a few lines below) still does `dest[index] = Property::Unparsed(unparsed)` regardless of the prefix in `val.property_id`. Any `var()` value still loses the other-prefixed declaration. This is the same bug in the same function, and real-world CSS hits it (Pico, Tailwind-style var-based utilities; see Findings 1). It should be fixed in this PR, with the same prefix comparison applied to the unparsed property id.
- Complexity is small (one index per property, no new data structures). There is no quadratic work: each declaration does O(1) work.
- Philosophy: fine. No non-standard syntax, no hacks.
- Minor: the new code reads `dest.get_mut(index)` twice and calls `context.targets.prefixes` twice. It could be folded into one match, but that is a nit.

## Spec
These are vendor-prefixed and unprefixed properties, which are distinct properties. `-webkit-backdrop-filter` is not a legacy alias in the WHATWG Compat spec (checked https://compat.spec.whatwg.org/: no match for `webkit-backdrop-filter` or `webkit-filter`). So normal cascade applies, and an unprefixed declaration must not be replaced by a prefixed one. The Filter Effects 2 spec defines only `backdrop-filter`. Compat data (`src/prefixes.rs`): Safari/iOS 9–17.x need `-webkit-`, Safari 18+ is unprefixed, and Chrome is unprefixed since 76.

## Findings
1. **Should fix (incomplete fix): `var()` values still drop the other-prefixed declaration.** The `Property::Unparsed` arm ignores the prefix.
   - `.a{backdrop-filter:var(--b);-webkit-backdrop-filter:var(--b)}`, `--minify` (any targets):
     - base: `.a{-webkit-backdrop-filter:var(--b)}`;
     - PR: the same.
     - Chromium: not equivalent, no backdrop filter.
   - `.a{backdrop-filter:blur(10px);-webkit-backdrop-filter:var(--b)}` gives `.a{-webkit-backdrop-filter:var(--b)}` in both.
   - Real world: `pico.css` has `-webkit-backdrop-filter: var(--pico-modal-overlay-backdrop-filter); backdrop-filter: var(...)`. `--minify` without targets keeps only `backdrop-filter:var(...)` in base and PR, so on Safari ≤17 the modal overlay blur is lost. With `--targets 'safari 16'` both are kept, because `get_prefixed` re-adds the prefix.
   - Fix: in the Unparsed arm, compare the incoming `val.property_id` prefix with the tracked entry. Replace only when the prefixes overlap; otherwise push a new entry and update the index. This is the same logic as the parsed arm.
   - Separately, `.a{backdrop-filter:blur(10px);-webkit-backdrop-filter:bananas}` → `-webkit-backdrop-filter:bananas`. That is the known #1392/#1404 issue (an unparsed value treated as valid), made worse here because it also crosses prefixes. It is out of scope, but the prefix check above would at least keep the unprefixed declaration.
2. **Nit / pre-existing: no color fallbacks for the second, differently-prefixed declaration.** Fallbacks are only computed when the handler has no tracked index, so the later declaration never gets them.
   - Input: `.a{backdrop-filter:drop-shadow(0 0 4px oklch(60% .2 30));-webkit-backdrop-filter:<same>}` with `--targets 'safari 15'`.
   - PR output: `backdrop-filter:drop-shadow(… lab(…));-webkit-backdrop-filter:drop-shadow(… oklch(…))`.
   - Base output: `-webkit-backdrop-filter:…oklch…` only.
   - So Safari 15.0 gets no backdrop effect with either build. With only `-webkit-…:oklch` it correctly gets a `lab()` fallback.
   - Not a regression (base is also broken there; Chromium is fixed). Worth a follow-up: treat a disjoint-prefix declaration like a fresh one, including `get_fallbacks`.
3. **Intended behavior change (good): no-target output now keeps `-webkit-` when it was written first.** For example, `-webkit-backdrop-filter:blur(10px);backdrop-filter:blur(10px)` minifies to both instead of `backdrop-filter` only. This matches `PrefixHandler` (`user-select`), which also keeps prefixes when there are no targets, and fixes Safari ≤17 for users who minify without targets. It is the only size change in the corpus (Pico +29 B: `-webkit-backdrop-filter:none` kept).
