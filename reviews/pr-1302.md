# PR #1302: Fix place-self/place-items collapsing non-equal values
**Verdict:** approve with nits. **Confidence:** high.

Author: hdimer. Fixes #1182. Head 3ba4e45, base c6a0c3c; built merged onto current master 574eee2 (clean merge). No CI runs on the head commit (no check runs reported; likely awaiting workflow approval for a first-time contributor). No comments or reviews.

## Summary
`PlaceSelf::to_css` and `PlaceItems::to_css` (src/properties/align.rs) omit the second value when they think justify equals align, but three match arms were wrong: `JustifySelf::Auto => true` (always collapse), and `JustifySelf::Stretch` / `JustifyItems::Stretch` compared against align `Normal` instead of `Stretch`. Since the one-value form copies the first value into justify-*, the minifier silently changed `justify-self`/`justify-items`. The PR fixes the three arms (+3/-3) and adds 6 tests to `test_flex`. Bug confirmed on master:

```
in:     .a{align-self:self-start;justify-self:auto}.b{align-items:normal;justify-items:stretch}.c{align-self:normal;justify-self:stretch}
master: .a{place-self:self-start}.b{place-items:normal}.c{place-self:normal}
PR:     .a{place-self:self-start auto}.b{place-items:normal stretch}.c{place-self:normal stretch}
```
Browser check: master output NOT equivalent in Chromium (grid items shrink instead of stretching); PR output equivalent.

Also a small size win: `align-self:stretch;justify-self:stretch` was `place-self:stretch stretch`, now `place-self:stretch` (same for place-items).

## Design
- The fix is right but local. The root cause is that each serializer re-implements, by hand, the inverse of the "copy from first value" mapping in the matching `Parse` impl, and the two drifted. A more robust shape: factor the parse-side mapping into a helper (e.g. `fn justify_from_align(align: &AlignSelf) -> JustifySelf`, likewise for items/content) and serialize the second value iff `self.justify != justify_from_align(&self.align)`. Parse and serialize then cannot diverge, and the hand-written `is_equal` matches go away. Sketch (not compiled/tested):
  ```rust
  impl PlaceSelf {
    fn default_justify(align: &AlignSelf) -> JustifySelf { /* the match currently in parse */ }
  }
  // parse:  let justify = input.try_parse(JustifySelf::parse).unwrap_or_else(|_| Self::default_justify(&align));
  // to_css: if self.justify != Self::default_justify(&self.align) { dest.write_char(' ')?; self.justify.to_css(dest)?; }
  ```
  For PlaceContent this would also let `align-content:baseline;justify-content:start` serialize as `place-content:baseline` (currently `baseline start`; Chrome's own CSSOM also writes `baseline start`, so that is purely cosmetic). Nit/suggestion, not blocking: the PR's arms are now correct.
- Completeness: checked PlaceContent's `is_equal` (no wrong arms; baseline→start rule respected by emitting both values), `JustifyItems::Legacy`/`left`/`right` and `JustifySelf::Left/Right` (fall through to `false`, so both values kept), overflow (`safe center` vs `center` compared). `Gap` uses `==`. No other affected shorthand found.
- Philosophy: fine. No API/AST change.

## Spec
css-align-3 ED (https://drafts.csswg.org/css-align-3/), fetched:
- place-self: "The first value is assigned to align-self. The second value is assigned to justify-self; if omitted, it is copied from the first value."
- place-items: "The first value is assigned to align-items. The second value is assigned to justify-items; if omitted, it is copied from the first value."
- place-content: "...if omitted, it is copied from the first value, unless that value is a <baseline-position> in which case it is defaulted to start."

So the one-value form is only valid when justify is literally the same keyword; `auto` and `stretch` have no special rule. Chromium probe agrees (`place-content:baseline` → cssText `place-content: baseline start`; `place-self: self-start auto` round-trips).
