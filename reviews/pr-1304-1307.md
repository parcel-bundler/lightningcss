# PR #1304 and #1307: `::search-text:current` rejected since 1.33.0 (#1303)

**Verdict:** merge #1307 (approve with one nit: `cargo fmt`), close #1304. **Confidence:** high on behavior, medium on the policy call about `::search-text:hover`.

Both built with `scripts/build-pr.sh --on-master` on master 574eee24 (both merge cleanly).
Binaries: `target/review/pr-1304-on-574eee24/lightningcss`, `target/review/pr-1307-on-574eee24/lightningcss`, base `target/review/base-574eee24/lightningcss`.

## Summary

#1213 (1.33.0) made `::search-text` a known pseudo-element. Pseudo-classes after a known pseudo-element go through the generic guard in `parse_simple_pseudo_class` (`selectors/parser.rs`), which only allows `is_user_action_state()`. So `::search-text:current` and `::search-text:not(:current)` became hard errors. In 1.32.0 they passed through as an unknown pseudo-element. Confirmed with the published packages: 1.32.0 accepts both, and 1.33.0 throws "Invalid pseudo class after pseudo element". Chromium 153 accepts both selectors.

Both PRs fix this with the same mechanism: a new parser-state bit (1 << 11) set after `::search-text`, plus a trait hook on the pseudo-class.

- **#1304** (rvitaliy, the issue reporter, opened 2026-08-05) adds `is_search_text()` and `is_valid_after_search_text()`. After `::search-text`, *only* `:current` is allowed. The user-action pseudos (`:hover`, `:focus`, `:active`…) become errors, although they have parsed in every release so far.
- **#1307** (rorshopping, 2026-08-12) adds `accepts_current_pseudo_class()` and `is_current()`. `:current` is allowed *in addition to* the user-action pseudos, so it only ever accepts more.

## Design

- **Upstream.** servo/stylo `selectors/parser.rs` (main) has no `::search-text` or `:current` handling. Its model has two parts:
  - each pseudo-element opts into pseudo-classes with `accepts_state_pseudo_classes()`, and if it doesn't, `AFTER_NON_STATEFUL_PSEUDO_ELEMENT` blocks them;
  - an allowlist of pseudo-classes, `is_user_action_state()`. Gecko's list is Hover/Active/Focus, and only pseudos with `SUPPORTS_USER_ACTION_STATE` opt in, so in Firefox `::selection:hover` is invalid.

  Lightning CSS sets `accepts_state_pseudo_classes()` to `true` for every pseudo-element ("Be lenient", `src/selector.rs:1316`). Neither PR ports anything from upstream, because there is nothing to port. Both are small, local extensions in the same style as the existing `is_webkit_scrollbar` and `is_view_transition` flags.
- **Is there a general rule?** css-pseudo-4 lets "other specifications" allow extra pseudo-classes per pseudo-element (selectors-4 §3.6.3). Today the only such case besides `::view-transition-*:only-child` (already special-cased) is `::search-text:current`. A fully general hook, such as `PseudoElement::accepts_pseudo_class(&NonTSPseudoClass)`, would need the parser state to remember *which* pseudo-element it saw. That is more machinery than a single case justifies, so the per-feature bit is fine.
- **What `:hover` after `::search-text` should do.** This is the real difference between the two PRs.
  - Spec text:
    - Selectors-4 §3.6.3: "This specification allows any pseudo-element to be followed by any combination of the logical combination pseudo-classes and the user action pseudo-classes … Combinations that are not explicitly allowed are invalid selectors." This is "At Risk" for non-tree-abiding pseudo-elements, and `::search-text` is a highlight pseudo, so not tree-abiding.
    - css-pseudo-4 `::search-text`: "Any unsupported combination of *these* pseudo-classes with `::search-text` must be treated as invalid". "These" means `:current`/`:past`/`:future`, not `:hover`.
  - WPT: `highlight-pseudos-search-text.tentative.html` asserts `::search-text:hover` is invalid. The non-tentative `highlight-pseudos.html` asserts the same for `::selection:hover`, `::target-text:hover`, `::spelling-error:hover` and `::grammar-error:hover`.
  - Chromium 153 rejects `:hover` after **every** pseudo-element, `::before:hover` and `::first-line:hover` included (table below).
  - Lightning CSS accepts user-action pseudo-classes after all of these, on master and with both PRs.

  So #1304 makes `::search-text` the one highlight pseudo that rejects `:hover`, while `::selection:hover`, `::target-text:hover` and `::highlight(x):hover` still parse. That is a special case rather than a rule. It also turns CSS that every release has accepted into a strict-mode build error, in a PR meant to fix a regression. The philosophy reserves strict errors for "definitely invalid" known syntax, and selectors-4 still lists this combination as valid (at risk). If the project wants WPT/Chromium behavior here, it should be one change for all highlight pseudo-elements: e.g. return `false` from `accepts_state_pseudo_classes()` for highlight pseudos, in upstream style, plus the `:current` exception for `::search-text`. That belongs in a separate change.
- **Complexity and performance.** One bit test per pseudo-class parsed after a pseudo-element, in both PRs. Negligible. There are no AST, serialization or public JS API changes. Both add a defaulted method to the public `parcel_selectors` traits: additive and non-breaking.
- **Interaction with #1308** (rorshopping, open). It renames `AFTER_PSEUDO_ELEMENT` to `AFTER_NON_ELEMENT_BACKED_PSEUDO` and uses bit 11 for `AFTER_ELEMENT_BACKED_PSEUDO_ELEMENT`. Either PR conflicts with it textually (bit number and flag name); the rebase is trivial. With #1307 the same author owns both.

## Spec

- css-pseudo-4 (Bikeshed source, `css-pseudo-4/Overview.bs`, `::search-text`): "The ':current' pseudo-class (but not '::current()') may be combined with '::search-text' to represent the currently focused match instance. The ':past' and ':future' pseudo-classes are reserved for analogous use in the future. Any unsupported combination of these pseudo-classes with '::search-text' must be treated as invalid." https://drafts.csswg.org/css-pseudo-4/#selectordef-search-text
- selectors-4 §3.6.3 "Pseudo-classing Pseudo-elements", quoted above. https://drafts.csswg.org/selectors-4/#pseudo-element-states
- WPT `css/css-pseudo/parsing/highlight-pseudos-search-text.tentative.html` covers valid `::search-text`, `:current` and `:not(:current)` (with `.a`, `div `, `::part(my-part)` prefixes), and invalid `::before…`, `….a`, `… div`, `…::after`, `…:hover`, `…:current(*)`, `…:past`, `…:future` and `:not(…)`. Lightning's WPT harness lists this page as unsupported ("test_valid_selector is not defined"), so CI doesn't cover it.

## Findings

1. **#1304: new strict-mode error for `::search-text:hover` / `:focus` / `:active` / `:not(:hover)`** (should not merge as is). The policy reasoning is under Design.
   - Input: `::search-text:hover{color:red}`.
   - Output: 1.32.0, 1.33.0 and master print `::search-text:hover{color:red}`. #1304 fails with InvalidPseudoClassAfterPseudoElement, and with `--error-recovery` the rule is dropped.
   - In browsers: Chromium ignores this rule either way, so dropping it changes nothing visible in Chromium. The cost is a build break for users.
   - This is inconsistent with `::selection:hover`, which still parses.
2. **#1304 deletes `foo::search-text` and `:current::search-text` from the `parcel_selectors` unit tests** instead of fixing them. They could never pass, because the DummyParser doesn't know `search-text`. `test_parsing` is already broken on master: it fails earlier on `foo::details-content`, and CI doesn't run `-p parcel_selectors`. #1307 teaches the DummyParser `::search-text`/`:current` and adds a passing `test_search_text_current`, which is the better direction.
3. **#1307: `cargo fmt --check` fails** on one `minify_test(...)` in `src/lib.rs` (~7395) that fits on one line (nit; CI runs `cargo fmt`).
4. **#1307 accepts `::search-text:current:hover` and `::search-text:not(:current, :hover)`.** Chromium and WPT reject these. This is consistent with how Lightning treats user-action pseudos after every other pseudo-element. Master errors on them only because of the `:current` bug, and 1.32.0 accepted them. No action needed.
5. **Pre-existing, both PRs unchanged:**
   - Without targets, `::search-text` (without `:current`) merges into neighbor rules: `.b,::search-text{color:red}`. Firefox and Safari would drop the merged rule. This is the existing "no targets = no compat check" behavior.
   - `:current` is marked "no browser support" in `is_compatible`, so `::search-text:current` rules never merge (verified with `--targets 'firefox 120' --targets 'chrome 140'` and without targets).
   - On master, `::search-text:is(:current)` printed `::search-text:is()` (forgiving parse dropped the argument). Both PRs fix that as a side effect: it now prints `::search-text:current`.
