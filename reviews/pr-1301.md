# PR #1301: Strip a leading UTF-8 BOM when parsing a style sheet
**Verdict:** approve with nits (one should-fix: source-map consistency in CLI/napi/C). **Confidence:** high.

Built with `build-pr.sh --on-master 1301` (merged cleanly onto master 574eee24). PR_BIN=target/review/pr-1301-on-574eee24/lightningcss, BASE_BIN=target/review/base-574eee24/lightningcss. No CI check runs exist on the head commit (first-time contributor; workflows not approved yet).

## Summary
Strips one leading U+FEFF in `StyleSheet::parse_with` (covers Rust API, napi/wasm/C, bundler) and again in the bundler before `set_source_content`, so the bundle's `sourcesContent` matches parser positions. Bug is real (#338, open since 2022): on master the BOM is tokenized into the first ident, so `BOM/*! x */html{}`, `BOM@charset ...;` and `BOM@import` (bundle) are hard parse errors, and `BOMhtml{}` becomes the selector `﻿html`, which stops it merging with other `html` rules and breaks it if the output is concatenated (e.g. an imported file).

## Design
- Right place: `parse_with` is the single entry for stylesheets; `StyleAttribute::parse` correctly untouched. Cost is one `strip_prefix` per sheet; outputs on the 16-file real/synthetic corpus are byte-identical.
- Semantics: matches how browsers load *files* (decode strips BOM) — verified in Chromium below. Browsers do *not* strip it from string inputs (`replaceSync`, `<style>` text), so for the "inline `<style>`" use of `StyleSheet::parse` it is a slight deviation, but a leading U+FEFF in inline CSS is pathological and the practical inputs (files, Sass output, Node `readFileSync(...,'utf8')` which keeps the BOM) all want stripping. Fine.
- Only one BOM is stripped and only at offset 0 (matches Encoding "decode").
- Upstream: Stylo strips the BOM during byte decoding (encoding_rs), i.e. before cssparser, same layering as here. Not a selector change.

## Spec
css-syntax-3 (ED, https://drafts.csswg.org/css-syntax/#parse-stylesheet): "If input is a byte stream for a stylesheet, decode bytes from input, and set input to the result." §3.2: "Note: The decode algorithm gives precedence to a byte order mark (BOM), and only uses the fallback when none is found." and "authors should begin the stylesheet with a UTF-8 BOM or the exact characters @charset "utf-8";". So a BOM is an explicitly endorsed way to start a stylesheet file.

Chromium (scripts/probe.mjs):
- `<link href="data:text/css,%EF%BB%BFp{color:rgb(1,2,3)}">` → p color rgb(1, 2, 3) (BOM stripped); `%EF%BB%BF/*!x*/b{...}` → applies too.
- `CSSStyleSheet.replaceSync('﻿p{...}')` and `<style>` textContent → selectorText `"﻿p"` (kept; string input, no decode).

## Findings
1. **Should fix — source maps off by one on line 1 in CLI/napi/C.** `src/main.rs:193`, `napi/src/lib.rs:694`, `c/src/lib.rs:328` still register the unstripped source as `sourcesContent`, while parser columns now exclude the BOM. Input `BOM.a{color:red}.b{color:blue}`, `lightningcss --sourcemap`: base maps `.b` to orig col 14 (counting BOM), PR maps to 13 with sourcesContent `'﻿.a{'`; `--bundle` gives 13 with stripped sourcesContent (consistent). For one-line (minified/Sass-compressed) input every mapping is on line 1. Author already flagged this; suggest stripping at the top of those three entry points (same `strip_prefix`, or make the helper public / move it to a shared util) so all paths agree.
2. Nit/pre-existing: output can start with U+FEFF when the input has a non-leading one that becomes first (` ﻿html{}` or a double BOM) — a browser would then strip it when loading the output file, changing the selector. Same on base; pathological; not for this PR.
3. Nit: CSS-modules content hash now ignores the BOM (`hash(&code)` uses stripped code), so class names for BOM'd files change — they were broken before anyway. No action.
