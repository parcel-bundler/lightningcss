# PR #1245: fix(calc): enhance sum term reduction in calculations to prevent segmentation faults
**Verdict:** request changes (the crash fix works, but the design is heavier than needed and adds cubic work; a one-line fix gives the same output). **Confidence:** medium-high.

Built with `build-pr.sh --on-master 1245`: the PR merged cleanly onto master 574eee2. PR_BIN=target/review/pr-1245-on-574eee2/lightningcss, BASE_BIN=target/review/base-574eee2/lightningcss. No CI check runs exist on the head commit.

## Summary
Adding two `Calc::Sum` nodes on master goes through `V::try_from(a)?.add(V::try_from(b)?)`. When `Length::try_add` / `DimensionPercentage::add_recursive` find no like terms, `Length::add(Calc, Calc)` calls `Calc::add(Sum, Sum)` again, which recurses until the stack overflows. The bug is real: on master, `.a{height:calc((100dvh - 10.5rem) + (4vh + 230px))}` aborts with "thread 'main' has overflowed its stack" (#910, reported by Webflow from production CSS). Random valid sum expressions crash master in about 60% of cases (238 of 400 fuzz inputs). The PR flattens both sums into a term list and combines Value/Value and Number/Number pairs pairwise. That fixes every crash I generated and produced no browser regressions.

## Design
- **Simpler fix available.** The recursion comes only from the `(Sum, Sum)` arm. Adding the right-hand sum's terms one at a time reuses the existing, non-recursing `Sum + Value/Function/Number` arms:
  ```rust
  (a @ Calc::Sum(..), Calc::Sum(b1, b2)) => a.add(*b1)?.add(*b2)?,
  ```
  I prototyped this in the PR worktree (then restored it). Results:
  - All 126 lib tests pass, except the PR's own new `right:` expectation, which differs only in term order.
  - 0 crashes on 400 random inputs.
  - Browser results on 80 fuzz cases match the PR's classification exactly.
  - It needs no `Zero` bound and keeps master's handling of zero terms.
- **Complexity.** `add_sum_terms` re-flattens the *whole accumulated* left-hand sum on every `+ (group)`. `push_reduced_sum_term` then scans every reduced term for each pushed term (O(k²) per add). The result is cubic in the number of parenthesized groups whose terms don't combine. CLI times for `calc((min(Npx,Nvw) + max(Nem,Nvh)) + ...)`:
  | groups | PR | one-line alt | master |
  |---|---|---|---|
  | 400 | 108–133 ms | 6 ms | crash |
  | 800 | 305–474 ms | 20 ms | crash |
  | 1600 | 2.7–3.6 s | 13 ms | crash |

  To be fair, the alternative inherits master's existing cost on deep right-nested sums (`(x) + ((y) + (...))`, depth 200): alt 728 ms, master 373 ms, PR 19 ms. Both cases are pathological; realistic calc() has fewer than 20 terms. So the cubic term is not blocking on realistic input, but the extra machinery doesn't buy anything measurable either. If the maintainer prefers the flattening approach, it should follow the spec algorithm (flatten once, combine identical units in one pass) rather than re-flatten per `+`.
- **Spec fit.** Flattening and combining like units matches css-values-4's simplification. But `is_zero_term` removes zero terms, which the spec says not to do (see Findings 2).
- **API.** Adds a `Zero` bound to the public `impl Parse for Calc<V>` and the inherent `impl Calc<V>`. All in-crate `V` types satisfy it, but it narrows a public generic impl.

## Spec
css-values-4, [simplify a calculation tree](https://drafts.csswg.org/css-values-4/#calc-simplification), "If root is a Sum node":
> For each of root's children that are Sum nodes, replace them with their children. For each set of root's children that are numeric values with identical units, remove those children and replace them with a single numeric value containing the sum of the removed nodes, and with the same unit.
>
> Note: Zero-valued terms cannot be simply removed from a Sum; they can only be combined with other values that have identical units. (This is because the mere presence of a unit, even with a zero value, can sometimes imply a change in behavior.)

## Findings
1. **should fix (design/perf): cubic re-flattening and reduction, plus a much simpler fix exists.** See Design. Suggestion: the one-line `(Sum, Sum)` arm above, or a single-pass spec-style combine.
2. **nit: dropping zero `Number` terms turns invalid calc into valid calc.**
   - Input: `.a{width:10px;width:calc((1 + 2px) + (-1 + 3px))}`.
   - Base output: `width:calc(0 + 5px)`. PR output: `width:5px`.
   - Chrome rejects number + length, so the declaration is dropped. Both builds are already wrong here: master also discards the `10px` fallback, and Chrome computes 10px for the input. The PR makes the invalid value apply as 5px.
   - This contradicts the spec note. Master already drops zero *dimension* terms (`calc(100px + 0%)` → `100px`, which the browser check flags: 0% changes percentage-height behavior). That is pre-existing, not this PR.
3. **nit: the new `right:` test enshrines rounding.** The expected output `calc(min(100vw,1724px)/12 + 50vw - 6.66667px + min(100vw - 112px,1612px)/-2)` folds 32px − 464px/12 into `-6.66667px`. Chrome then lays out 14.0156px instead of 14px at an 80px viewport (equivalence: NOT EQUIV, 1/64 px). This is the pre-existing #949 number precision issue (master emits the same `- 6.66667px` for `calc(32px + (min(100vw,1724px) - 464px) / 12)`), so it isn't caused by this PR. The test pins it, though. `/-2` is valid but longer than `- min(...)/2`.
4. **nit: unrelated churn.** Formatting-only changes in `src/selector.rs` (a re-wrapped `let` and a removed blank line). Both versions pass rustfmt with the repo config.

## Edge cases checked
25 hand cases × 3 configs (`--minify`; `--minify --targets 'safari 12' --targets 'chrome 90'`; `--targets 'chrome 60'`): 3 fixed (the #910 crash), 48 ok, 9 changed and equivalent (term order only), 15 still-broken, all pre-existing:
- the `right:` rounding;
- `calc(100px + 0%)` and `(100px + 1%) + (-1% + 0px)` with percentage height;
- invalid number + length.

| case | config | result |
|---|---|---|
| #910 `calc((100dvh - 10.5rem) + (4vh + 230px))` | all 3 | fixed: crash → `calc(100dvh + 4vh + 230px - 10.5rem)`, equivalent |
| PR `right:` test | all 3 | base crash; PR NOT EQUIV by 1/64 px (rounding, pre-existing) |
| `(1em + 2px) + (3% + 4em)` | all 3 | changed order only (`calc(3% + 5em + 2px)` → `calc(2px + 3% + 5em)`), equivalent |
| nested groups, 4 groups, negative sums, var() neighbour, angle, time, clamp, font-size %, background-position %, !important, @media | all 3 | ok/changed-equivalent |
| `(1 + 2px) + (-1 + 3px)` (invalid) | all 3 | still broken; output changes `calc(0 + 5px)` → `5px` |

Fuzz (80 random valid sums with min/max, division and nesting; % replaced by vmin to avoid oracle noise), PR vs master: 35 fixed, 25 ok, 12 changed, 8 still-broken (all 6-digit rounding, e.g. 588.694px → 588.695px), 0 regressions. The one-line alternative gave the same classification.
