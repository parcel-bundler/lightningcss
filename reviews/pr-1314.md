# PR #1314: Error on nested @property and @position-try rules
**Verdict:** request changes (small). **Confidence:** high.

## Summary
`NestedRuleParser::parse_prelude` (src/parser.rs) returned early for `@property` and `@position-try`, skipping the `is_in_style_rule && !allowed_in_style_rule()` check that `@keyframes`, `@font-face`, etc. go through. Nested `@property` was therefore silently accepted and, with targets that keep nesting (no targets, chrome >= 120), emitted as invalid nested CSS that Chromium drops (#962). The PR removes the early returns so both rules fall through to the check: error in strict mode, warning in errorRecovery. This is exactly what the maintainer asked for in #962 ("they should probably both error unless errorRecovery is enabled in which case they should both warn"). The core change is correct, but in errorRecovery mode it newly routes these rules into a pre-existing bug that drops the declarations *before* the invalid rule.

Built with `build-pr.sh --on-master 1314` (merged cleanly onto 574eee24). No CI check runs exist on the PR head (fork PR, not yet approved to run).

## Design
- Right place: the shared `allowed_in_style_rule()` check, and `AtRulePrelude::Property`/`PositionTry` were already listed as `false` there; the early `return Ok(..)` was the only thing bypassing it. No other prelude arm in `NestedRuleParser::parse_prelude` has an early return any more. Covers nesting through `@media`/`@supports`/`@container`/`@layer`/`@scope`/`@starting-style` inside a style rule, since `is_in_style_rule` propagates (parser.rs `parse_nested`, `is_in_style_rule: self.is_in_style_rule || is_style_rule`). Verified by cases.
- Top-level conditional/layer/scope wrappers (`@media{@property}`, `@scope(.a){@property}`) are unaffected, matching Chromium, which applies `@property` in both.
- Behavior change to call out: with older targets (nesting lowered), base *hoisted* nested `@property` to the top level and it worked; now strict mode errors. That is the maintainer's stated policy for #962, but it will break builds that relied on it (e.g. next-yak users migrating from emotion, per the issue).
- Philosophy: fits "strict by default"; recovery drops the invalid rule as a browser does.

## Spec
- css-nesting-1 §3.3 (https://drafts.csswg.org/css-nesting-1/#nested-group-rules): "this specification allows nested group rules inside of style rules: any at-rule whose body contains style rules can be nested inside of a style rule as well, unless otherwise specified. ... Specifically, these rules are capable of being nested group rules: all the conditional group rules (@container, @media, @supports) @layer @scope". `@property` and `@position-try` bodies are declaration lists, so they are not nested group rules.
- css-anchor-position-1 §6.4: "The syntax of the @position-try rule is: @position-try <dashed-ident> { <declaration-list> }".
- css-properties-values-api-1 (Bikeshed source) has no explicit placement sentence; the nesting spec decides it.
- Chromium 153 (probe): `.foo{ @property --a{..} @position-try --b{..} @media all{ @property --c{..} } color:red }` serializes as `.foo { @media all { } color: red; }`; `--a`/`--c` unregistered; top-level `@media all{@property --d}` and `@scope(.foo){@property --e}` apply.

## Findings
1. **Should fix (blocking-ish for errorRecovery users): declarations before the nested rule are lost in errorRecovery mode.**
   Input: `.foo{ color:blue; @property --a { syntax:"<length>"; inherits:false; initial-value:5px } background:green }` with `--minify --error-recovery`
   - base: `.foo{color:#00f;@property --a{...}background:green}` (Chromium: color blue; the nested rule is ignored)
   - PR: `.foo{background:green}` + warning (Chromium: color lost)
   - Chromium on the input: `.foo { color: blue; background: green; }`.
   Same for `@position-try`. cases.mjs: 3 regressions (`--minify --error-recovery`, `--error-recovery --targets 'chrome 120'`), NOT EQUIV.
   Root cause is pre-existing in `NestedRuleParser::parse_nested`: on any error while `parse_declarations` is true it does `iter.parser.declarations.clear(); iter.parser.important_declarations.clear();`, wiping the declarations parsed so far (already happens for nested `@keyframes`, `@font-face`, invalid nested selectors like `&:::bad{}`). The PR newly routes `@property`/`@position-try` into it. Prototype: deleting those two `clear()` lines makes all 126 lib tests pass (`cargo test --lib` on the PR-on-master tree); not further validated (CLI not rebuilt with it). Suggest including that change plus a test asserting the recovered output (`.foo{color:blue;background:green}` style), not only the warning count.
2. **Nit:** the recovery test only asserts `warnings.len() == 1`; it should also assert the output CSS, which would have caught (1).
3. **Note (pre-existing, not this PR):** the warning text for `AtRuleInvalid` reads "Unknown at rule: @property", which is misleading for a known rule in the wrong place. Also nested `@import` in a style rule is warned yet kept in output in recovery mode (base and PR). Out of scope.

## Edge cases checked
22 cases x 3 configs (`--minify`, `--minify --error-recovery`, `--targets 'chrome 100'`) plus per-case configs: 21 fixed, 15 ok, 9 changed, 14 still-broken, 3 regression.

| case | config | result |
|---|---|---|
| #962 nested @property / nested @position-try | --minify, chrome 100 | fixed (now errors) |
| @property in @media/@supports/@layer/@scope/@starting-style inside style rule; @position-try in @container | strict | fixed (errors; base emitted nested or hoisted) |
| `@PROPERTY` uppercase | strict | fixed |
| same, `--error-recovery` | recovery | equivalent, rule dropped with warning ("still-broken" rows are an artifact of `expect: error` under the recovery config) |
| top-level @property, @media/@supports/@layer/@scope wrappers | all | ok, unchanged |
| nested @keyframes / @font-palette-values, invalid @property prelude, block-less @property | all | unchanged errors (message change only) |
| declaration before nested @property / @position-try | --error-recovery | **regression**: preceding declaration dropped |

## Tests & performance
- PR's tests: `test_property`, `test_position_try` pass; full `cargo test --lib` 126/126 pass on PR merged onto master.
- Tests would fail on base (base accepts the nested rule; `error_test` expects an error).
- size-check.sh: 0 bytes change on every synthetic and real-world corpus entry, with and without older targets; no corpus file newly errors. No perf concern (removes an early return).
