# PR #1311: Fix panic when generating color fallbacks for gradients using currentColor
**Verdict:** request changes (correct, but incomplete; the general fix is a few more lines in the same function). **Confidence:** high.

## Summary
`CssColor::get_fallback` calls `to_rgb()/to_p3()/to_lab().unwrap()`, which return `Err` for `currentColor`, system colors and `light-dark()` containing either. Any list value whose fallbacks are driven by one oklch/lab/p3 color and which also contains such a color panics with targets that need fallbacks. The PR adds `CurrentColor | System` to the early return in `get_fallback`. Bug is real: master 574eee2 `--targets 'chrome 90'` panics at color.rs:517 on the PR's example, and also on `linear-gradient(oklch(..), Canvas)`, `filter: drop-shadow(.. oklch) drop-shadow(.. currentcolor)`, `border-color: oklch(..) currentcolor`, `background: currentcolor linear-gradient(oklch(..), red)` and `mask-image`. The PR fixes all of these (built on current master; merges cleanly).

## Design
Same root cause in four places, three of which the PR does not touch:
1. `CssColor::get_fallback` (fixed by PR for bare currentColor/system colors; **still panics for `light-dark(currentcolor, …)`/`light-dark(Canvas, …)`**, because the LightDark arm falls through to `to_rgb()`, which is all-or-nothing over both sides).
2. `impl FallbackValues for CssColor` (color.rs ~585) calls `to_rgb().unwrap()` directly: `color: light-dark(currentcolor, oklch(50% .2 30))` panics on master and PR.
3. `impl FallbackValues for SmallVec<[TextShadow; 1]>` (text.rs:1502/1513/1522) calls `to_*().unwrap()` directly: `text-shadow: 1px 1px oklch(50% .2 30), 1px 1px currentcolor` panics on master and PR (the "separate PR" mentioned in the description does not exist).
4. `BoxShadowHandler` (box_shadow.rs, #722/#801) uses `to_*().unwrap_or_else(|_| clone)`. No panic, but for `box-shadow: 1px 1px light-dark(currentcolor, oklch(..))` the whole light-dark is kept, so Chrome 90 output still contains an unlowered `oklch()` (two identical declarations, both invalid in Chrome 90): a silent wrong fallback.

**Text-shadow answer:** yes, same root cause (direct `to_*().unwrap()` on a color that has no fixed color space). The fix belongs in one shared place: `CssColor::get_fallback`, made total (keep currentColor/RGBA/System as written, recurse into each side of `LightDark`), and every per-property fallback path (`FallbackValues for CssColor`, text-shadow, box-shadow) should call it instead of `to_*()` directly. Then any future color-bearing property only has to call `get_fallback`.

Prototype (applied to the PR tree, then reverted), `r1311/proto.diff`:
```rust
pub fn get_fallback(&self, kind: ColorFallbackKind) -> CssColor {
  match self {
    CssColor::CurrentColor | CssColor::RGBA(_) | CssColor::System(_) => self.clone(),
    CssColor::LightDark(light, dark) =>
      CssColor::LightDark(Box::new(light.get_fallback(kind)), Box::new(dark.get_fallback(kind))),
    _ => match kind { RGB => self.to_rgb().unwrap(), P3 => self.to_p3().unwrap(), LAB => self.to_lab().unwrap(), _ => unreachable!() },
  }
}
```
plus `FallbackValues for CssColor`, text-shadow and box-shadow switched to `color.get_fallback(kind)`. No public API change (`to_rgb` etc. keep their `Err` semantics; `get_fallback` only stops panicking).

Fits philosophy: no hacks, purely a crash fix; nothing is newly parsed.

## Spec
css-color-4 (Overview.bs l.1011): `<color> = <color-base> | currentColor | <system-color>`; l.2157: "The keyword currentcolor represents value of the 'color' property on the same element." css-color-5 (l.2854): `light-dark() = light-dark( [<color>, <color>] | [<image>, <image>])`. So currentColor/system colors are valid anywhere `<color>` is, including gradient stops, shadows and both light-dark arguments; they have no color space to convert, so they must pass through unchanged.

## Findings
1. **should fix (panic remains): light-dark with currentColor/system color.** `.a{background-image:linear-gradient(oklch(50% .2 30),light-dark(currentcolor,red))}`, `--targets 'chrome 90'`: base panics, PR panics (color.rs:517). Same for `border-color: light-dark(currentcolor, oklch(..))` and `color: light-dark(currentcolor, oklch(..))` (color.rs:585). Prototype output: `linear-gradient(#ba0d01, var(--lightningcss-light, currentColor) var(--lightningcss-dark, red))` + lab version; browser-equivalent.
2. **should fix (same root cause, out of PR scope but trivially covered): text-shadow.** `.a{text-shadow:1px 1px oklch(50% .2 30),1px 1px currentcolor}` chrome 90: base and PR panic at text.rs:1502. Prototype: `text-shadow: 1px 1px #ba0d01, 1px 1px; text-shadow: 1px 1px lab(40.0416% 62.4616 55.0184), 1px 1px;`.
3. **nit/related:** box-shadow with `light-dark(currentcolor, oklch(..))` silently keeps oklch for Chrome 90 (see Design 4); fixed by the same refactor.
4. **aside, unrelated pre-existing bug (not filed, no existing issue found):** `.a{border:3px solid;border-color:oklch(50% .2 30)}` with `--targets 'chrome 90'` outputs `border-color: oklch(50% .2 30)` with no fallback at all (oklch needs Chrome 111). Only when the `border` shorthand precedes the longhand.
