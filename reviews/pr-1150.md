# PR #1150: Fix source location of list-style-image url location
**Verdict:** approve with nits (still a draft; author asks a design question). **Confidence:** high.

## Summary
Adds `input.skip_whitespace()` at the start of `Url::parse` (src/values/url.rs) before recording `current_source_location()`, and adds column assertions to `test_dependencies`. Fixes #1149. The bug is real and much broader than `list-style-image`: on base (master 574eee24), any `url()` that is parsed by `Url::parse` when whitespace/comments precede it records the location of the whitespace, so the dependency column is one short (or, after a newline, on the wrong line). Only contexts where a caller already skipped whitespace (comma-separated lists, custom-property token lists) were right. The PR fixes every `Url::parse` context I tested; two pre-existing location bugs remain that it doesn't touch (image-set strings, whitespace inside `url( x )`).

## Design
- **Right place.** cssparser's `expect_url()` (like every `expect_*`/`next()`) skips leading whitespace itself, so normal `Parse` impls never need to. `Url` is special only because it captures the location *before* calling `expect_url`. Skipping whitespace there makes the recorded position match the token `expect_url` actually consumes, for every caller, including future properties. Fixing in the callers (e.g. skipping whitespace after the declaration colon) would only cover the first value in a declaration and miss `filter: blur(1px) url(#f)`, `background: red url(x)`, `mask: no-repeat url(x)`, etc. Answer to the author's question: whitespace is the parser's job; the one thing that must consume it explicitly is code that records a location before the token.
- `skip_whitespace` also skips comments (`list-style-image: /*c*/ url(x)` now correct).
- Inside `try_parse`, the skip is rolled back on failure, so no behavior change for enum alternatives. Cost: negligible (whitespace would be skipped by `expect_url` anyway).
- No serialization change: `Url.loc` is only used for `UrlDependency` and the `AmbiguousUrlInCustomProperty` printer error. The serialized AST shape (JS visitors see `url.loc`) is unchanged; only the values become correct.

## Findings
1. **should fix (test):** the new `image-set('./img12x.png', ...)` assertions enshrine a known-wrong column (`30 + 4` with a `// TODO wrong`). Cause: `ImageSetOption::parse` (src/values/image.rs ~420) builds `Url { loc }` for a bare string, and `UrlDependency::new` (src/dependencies.rs:115) always adds 4 for `url(`. Input `.a { background: image-set( "x.png" 1x) }` reports column 33 (points at `ng"`), expected 30 (the opening quote, matching how quoted `url("x")` is reported). Either fix it (e.g. a flag/offset on the location for string sources) or drop those two column assertions rather than encode the wrong value.
2. **nit (pre-existing):** `url(  x.png  )` start points at the inner whitespace (fixed +4 offset); end column also off. Not caused by the PR.
3. **nit:** the new tests cover only `background-image` and `list-style-image`. Worth adding one non-list case that was broken on base, e.g. `filter: blur(1px) url(#f)` or `fill: url(#g)`, and a newline case (`list-style-image:\n  url(x)` reported line 1 on base).
