# PR #1354: Fix UTF-16 column tracking in source maps
**Verdict:** approve (merge). **Confidence:** high.

Author: SegaraRai. Fixes #780. One file (`src/printer.rs`, +116/-14), one commit, based on cbeaf83 (master is 8 commits ahead, none touching `src/printer.rs`). The PR text says GPT-6 Astra wrote it.

## Summary
`Printer` advanced its generated column `col` by UTF-8 **bytes** (`s.len()`). Source map columns are UTF-16 code units, so every mapping after a non-ASCII character on an output line drifted right. In minified output, which is one line, browsers then resolved later rules to an earlier rule's original line. That is #780. The PR counts UTF-16 units in `write_str`, `write_str_with_newlines`, `write_char` and `fmt::Write for Printer`.

It also fixes a second bug in CSS-modules identifiers. `write_ident` and `write_dashed_ident` added the length of each pattern segment *before* `serialize_identifier`/`serialize_name` escaped it. So escaped names drifted the column even in pure ASCII (`.\31 a`, `.\#x`). The new `IdentifierWriter` wraps `dest` and counts the bytes as they are actually written, after escaping.

The bug is real and the base build reproduces it (below). The PR's output CSS is byte-identical to base on every corpus file tested.

## Design
- **General and in the right place.** All column bookkeeping lives in `Printer` (grep: no other file touches `col` or writes past the printer's `dest`), and the PR covers every write path into it. Future printing code inherits the fix automatically.
- **Consistent with the original side.** cssparser 0.37 already reports *original* columns in UTF-16 units (`tokenizer.rs`: "Column numbers are counted in UTF-16 code units"; it adjusts `current_line_start_position` for multi-byte chars). Before this PR, generated and original columns used different units. `find_closest_mapping` lookups into input source maps (e.g. from Sass) already use UTF-16 original columns, so nothing else needs to change.
- **Cost.** `utf16_len` makes the column update O(len) instead of O(1). It is a branch-free byte count that the compiler can vectorize. No measurable time change (see below).
- **No API or AST change.** `Printer.col` is private. The only extra change is removing an unused `'b` lifetime on an impl.

## Spec
ECMA-426 (Source Map), "column" definition (https://tc39.es/ecma426/, source `spec.emu`):
> zero-based indexed offset within a line of the generated code, computed as UTF-16 code units for JavaScript and CSS source maps, and as byte indices in the binary content (represented as a single line) for WebAssembly source maps.
> That means that "A" (LATIN CAPITAL LETTER A) measures as 1 code unit, and "🔥" (FIRE) measures as 2 code units.

## Findings
No blocking or should-fix findings.

1. nit: `utf16_len` could be written as `s.encode_utf16().count()`, which is simpler. The bit trick is correct (one unit per non-continuation byte, plus one for each 4-byte lead byte `>= 0xF0`; valid `&str` never has 0xF8+) and has a comment. Not worth a round trip.

## Edge cases checked
Oracle: `sm/check.cjs` in the scratchpad. It runs the CLI with `--sourcemap`, decodes every mapping with source-map-js, and checks that the text at the generated position (indexed in UTF-16, i.e. a JS string index) starts with the same character as the original text at the mapped position.

| input | config | base mismatched / total | PR mismatched / total |
|---|---|---|---|
| ascii.css (control) | `--minify` / pretty | 0/3 / 0/3 | 0/3 / 0/3 |
| unicode.css (é ❯ 😀, 日本 class names, `/*!` comment with newlines and ©, url with ä, escaped `\2192`, `@media`) | `--minify` | **10/11** | 0/11 |
| unicode.css | pretty | 0/11 | 0/11 |
| modules.css (`.\31 é😀`, `--\+❯😀`, unicode keyframes) | `--minify --css-modules` | **4/5** | 0/5 |
| esc.css (ASCII-only escaped idents `.\31 a`, `.\#x`, `--\@y`) | `--minify --css-modules` | **1/4** | 0/4 |
| esc.css | `--minify` | 0/4 | 0/4 |
| big.css (400 random-unicode rules, nesting, `@media`, logical props) | `--minify` | **563/586** | 0/586 |
| big.css | `--minify --targets 'safari 12'` | 551/565 | 58/565* |
| big.css | `--targets 'chrome 80'` | 58/639* | 58/639* |

\* The 58 remaining mismatches come from the oracle, not the PR. Lowered nesting rules (`.n0 .k`) map to the original nested selector position (`& .k`), so their first characters differ by design. The count is identical on base wherever the drift doesn't also apply.

Output CSS is identical between base and PR: md5 of minified bootstrap+bulma+fontawesome ×2, and of big40 with safari 12 targets; size-check shows 0 bytes delta on all 16 corpus entries.

## Tests & performance
- `cargo test --lib printer::` in the PR worktree: 3/3 new tests pass. `cargo test --lib source_map`: 4/4 pass. The new source-map test asserts UTF-16 mapping columns, which base's byte counting cannot produce. The base failure is inferred from the oracle results above, not run.
- `scripts/size-check.sh`: 0 bytes delta on every entry (synthetic and real-world). Times within noise, e.g. react-spectrum S2 52→53 ms, primer 56→38 ms, on a loaded machine with parallel builds.
- CLI with `--sourcemap`, best of 7: 2.3 MB real-world concat 130→121 ms minified and 130→140 ms pretty; 840 KB unicode-heavy file 114→77 ms. This is noise from the shared machine; there is no sign of a regression.
- The PR's tests cover `write_str`, `write_char`, `fmt::Write`, `write_str_with_newlines` and two end-to-end source-map cases (plain and CSS modules with escapes).
