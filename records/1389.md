# #1389: Parsing nested `calc()` that contains a `var()` takes exponential time

**bug / confirmed / medium / action: queue-fix**

When a nested math function fails to parse as Calc<V> (here because of var()), Calc::parse_value falls through to V::parse, which parses the same function again as Calc<V> and fails the same way. Each level doubles the work, so nesting depth d costs ~2^d. The declaration then falls back to unparsed tokens, so the output is correct, only slow.

Real, old (>= 1.14.0), output correct but exponential. Rated medium only for the DoS angle; hand-written CSS won't hit it. PR #1390 is a plausible root-cause fix (review first). ## Draft reply

Thanks, confirmed. On 1.33.0, `width: calc(calc(... var(--x) - 1px ...) - 1px)` takes 2.6 ms at 10 levels, 150 ms at 15 and 4.5 s at 20; it has behaved this way since at least 1.14.0. The cause is in math-function parsing: when a nested function can't be fully parsed because of `var()`, the same function is parsed a second time through another path, so the work doubles at each level. The output is still correct, only slow. Without `var()`, or in a custom property, the same nesting is instant.

There's an open PR, #1390, that addresses this. Until it's released, the workaround is to avoid feeding deeply nested generated `calc()`/`min()` around `var()` into typed properties.
