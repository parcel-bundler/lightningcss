A known property whose value fails its grammar becomes Property::Unparsed and is printed as written, in strict mode too, with no warning. This is deliberate: Lightning CSS cannot tell a typo from a value it does not parse yet (new keywords/functions), and keeping it is meaning-preserving because the browser drops it at the same place. It matches the CLAUDE.md errorRecovery contract (recover like a browser, keep CSS as written); only the website docs sentence 'omitting them in the output' (which describes declarations that fail to tokenize/parse at all, e.g. `width: 10px )`, which ARE dropped with a warning) is imprecise. The visitor point (Unparsed for both var() and invalid values) is by design; visitors can inspect the tokens.

## Draft reply

Thanks for the detailed report. Keeping these declarations is intentional: when a value doesn't match a property's grammar, Lightning CSS can't tell a typo from a newer value it doesn't parse yet, so it keeps the declaration as written rather than dropping it, in strict mode too. A browser ignores it at the same point, so the result doesn't change. The docs sentence you quoted is about declarations that can't be parsed at all (e.g. `width: 10px )`), which are dropped with a warning. It should say that more clearly.

While checking this we found a related bug: for `color`, `fill`, `filter`, `text-shadow` and a few others, such a value replaces an earlier valid fallback (`color:red;color:bananas` becomes `color:bananas`). That's the same cause as #1392 and will be tracked there.
