# #1283 `animation-timeline: view()` added to `animation` shorthand

**bug / confirmed / high / action: queue-fix**

When animation and a non-auto animation-timeline are on the same rule, AnimationHandler folds the timeline into the shorthand whenever targets are absent or are Chromium-only >= 115. BCD marks timeline-in-shorthand as partial ('reset-only') for Chrome 115+, and build-prefixes.js treats that as full support. Chromium 153 rejects `animation: ... view()` as invalid, so the whole animation declaration is dropped. The timeline should stay a separate longhand after the shorthand.

**Impact:** Scroll-driven animations silently stop working in production builds. 11 reactions on #1283, 4 on #1342; duplicates #1342, #1369 (open) and #815, #1115 (closed earlier as 'set your targets'); also the animation-timeline sub-case of umbrella #572. Reporters hit it through Astro 7 / Vite 8, which use Lightning CSS for CSS by default; workarounds in comments are switching cssMinify to esbuild or passing browserslist targets that include a non-Chromium browser.

**Repro:** 1283-repro.mjs. `img{animation:parallax 1ms linear both;animation-timeline:view()}` with targets chrome 115 -> `img{animation:1ms linear both parallax view();...}`. Same with no targets. Controls: chrome 114, or chrome 130 + safari 18 -> `animation:1ms linear both parallax;animation-timeline:view()` (correct).

**Evidence:** repro.mjs: identical wrong output on local master, 1.33.0, 1.32.0, 1.31.1 (behavior dates from f4408c7, which added the timeline to the shorthand). probe.mjs in Chrome/153: el.style.cssText='animation:1ms linear both parallax view()' leaves style.animation empty; CSS.supports('animation','x 1s view()') = false; plain shorthand resets animationTimeline to 'auto' (reset-only). Spec: css-animations-2 ED grammar does include <single-animation-timeline> in <single-animation>, so the parser keeping it is fine; the problem is emitting it for engines that only reset it. Maintainer's own comment on #1283 points at build-prefixes.js line 337.

**Fix:** Filter partial_implementation entries for animationTimelineShorthand in build-prefixes.js and regenerate compat.rs (as PR #1306 does, per the maintainer's review). Separately decide the no-targets case: with no targets is_compatible() is true, so the fold still happens; #1306 always emits the longhand when targets are None.

**PR #1306:** Reworked per maintainer feedback: filters BCD partial entries in build-prefixes.js (same approach as statePseudoClass), compat.rs shown as regenerated (Feature moves to the always-false group, which will revert to a version check once BCD drops the partial flag), shorthand struct/parsing untouched. Adds tests for chrome 115 and no targets, updates existing expectations (e.g. `animation: foo 3s scroll()` input now splits into a longhand, matching browsers). Extra change in flush: targets=None never folds. That deviates from the 'no targets = future perfect browser' convention the maintainer stated on #815/#1115, so it needs an explicit maintainer call; given no engine supports it and correctness > size, keeping it seems right. ## Draft reply

Thanks for the report, and for the workarounds in the thread. Confirmed on 1.33.0 and current master: with Chrome 115+ targets (or no targets) `animation-timeline` is merged into `animation`, which Chrome (tested 153) rejects as invalid, so the whole animation is dropped.

The cause is the compatibility data: MDN marks timeline-in-shorthand support in Chrome 115+ as partial ("reset-only"), and that flag was being treated as full support. There's an open PR, #1306, that addresses this. Until it lands, setting targets that include Safari or Firefox (e.g. via `browserslistToTargets`) keeps `animation-timeline` as a separate declaration.

#1342 and #1369 report the same problem.
