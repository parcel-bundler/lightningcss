# #1319: two-value `overflow` emitted for Safari 14

**Status:** works-as-intended · **Severity:** low · **Action:** close (with reply)

- The reporter's support numbers are wrong. MDN `overflow.multiple_keywords`: Chrome 68, Firefox 61, Safari 13.1 / iOS 13.4. The "Chrome 90 / Safari 16" figures are for `overflow: clip`.
- `OverflowHandler::finalize` (src/properties/overflow.rs) gates on `Feature::OverflowShorthand`, and src/compat.rs matches MDN (safari >= 13.1).
- `1319-repro-boundary.mjs`: Safari 13 / Chrome 67 / Firefox 60 split both merged and hand-written input into `overflow-x`/`overflow-y`; Safari 13.1 / Chrome 68 keep the shorthand. Both the data and the logic are correct.

## Draft reply

Thanks for the detailed report! I think the support versions here are off. Per MDN's compatibility data, the two-value `overflow` syntax shipped in Chrome 68, Firefox 61 and Safari 13.1 (iOS 13.4) ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/overflow#browser_compatibility), "Multiple keywords" row). Chrome 90 / Safari 16 is when `overflow: clip` shipped. So `overflow: hidden scroll` is valid for Safari 14.

Lightning CSS uses that data for exactly the behavior you describe. Below the cut-off it splits the shorthand. For example, with `targets: { safari: 13 << 16 }`, both of your inputs become `.a{overflow-x:hidden;overflow-y:scroll}`, and the same happens for Chrome 67 or Firefox 60.

If you've seen Safari 14 actually fail to apply `overflow: hidden scroll`, please share the details and we can recheck the data. Otherwise I think this is working as intended.
