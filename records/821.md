# #821 `light-dark` is broken when children have different `color-scheme`'s

**bug / confirmed / high / action: needs-maintainer-decision**

The light-dark() polyfill rewrites it as var(--lightningcss-light,a) var(--lightningcss-dark,b), with the toggles set next to color-scheme. In a custom property the var() toggles are substituted where the custom property is declared (e.g. :root), so the inherited token value is fixed there; a descendant that changes color-scheme flips the toggles but not the already-computed token. Native light-dark() in a custom property stays unresolved until it is used, so it follows the using element's color-scheme. This is inherent to the polyfill technique; it can only be fixed for browsers that support light-dark() natively.

## Draft reply

Thanks all for the detailed reports. To summarize where this stands: the light-dark() fallback relies on CSS variables, and a custom property's value is computed on the element that declares it. So when tokens like `--background: light-dark(...)` are defined on `:root` and `color-scheme` changes on a descendant, the token has already been resolved and doesn't follow the descendant's scheme. It works when the tokens are declared on the same element that sets `color-scheme`. This can't be fixed for browsers without native support, but there's an open PR, #1287, that keeps the fallback and adds a native `light-dark()` override for browsers that support it.

Until then, you can disable the transform with `exclude: Features.LightDark` (in Vite: `css.lightningcss.exclude`) or raise targets to Chrome 123 / Safari 17.5 / Firefox 120.

The `color-scheme: inherit` -> `normal` problem mentioned above was fixed in 1.32.0 (#1152).
