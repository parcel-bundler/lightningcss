# #137 Non-deterministic ordering of `@supports` conditions

**Status:** confirmed, still present on master and every release checked (1.14.0 to 1.33.0). **Severity:** medium. **Action:** queue-fix (medium size).

`Bundler::load_file` loads a file's `@import`s in parallel (rayon). When the same file is imported again, its conditions are OR-ed into the existing entry in whatever order the threads arrive. That affects `@media` too (`print,screen` vs `screen,print`).

- Bundling the same entry 200 times on master gave 140 distinct outputs.
- The issue's exact 2-import case flipped order in 1 of 20 processes.
- Worse: for `@import "b.css"; @import "b.css" supports(color:red); @import "b.css" print;`, the media/supports compatibility check depends on that order, so the bundle sometimes fails with "Unsupported import condition" (27/300 on master, 2/300 on 1.33.0).

In the plain OR case the output is semantically equivalent, but it is not byte-stable, which breaks content hashing and makes `bundler::tests::test_bundle` flaky.

Fix: fold repeated-import conditions in deterministic import order after the parallel load (sorting would fix the ordering but not the flaky error).

Repros: `137-repro.mjs`, `137-repro-error.mjs`, fixtures in `137-fixture/`.

No reply drafted: this is a maintainer-filed issue, and the maintainer already diagnosed it.
