# #1403: A three-value `transform-origin` loses its z when its y is a near side: `left top 30px` minifies to `0 30px`

**bug / confirmed / severity medium / action queue-fix**

transform-origin is typed as <position>, but its grammar is different: an optional third <length> z, no side offsets, and no four-value form. A z offset after a side keyword is therefore parsed as that side's offset and printed as a different origin, or as invalid syntax when the y keyword comes first. It needs its own type (x, y, optional z) with the transform-origin grammar.

**Impact:** No reactions (batch report). transform-origin is parsed as a CSS <position> (src/properties/mod.rs:1474 has `// TODO: handle z offset syntax`), so a z offset after `<x-keyword> <top|bottom>` or `<y-keyword> <left|right>` is read as a side offset. Two effects: (1) the z is moved into x/y (`left top 30px` -> `0 30px`, `center left 10px` -> `10px`); (2) worse, which the report doesn't mention: y-keyword-first forms print as INVALID transform-origin, so the browser drops the declaration: `bottom left 0` -> `left 0 bottom`, `top right 20px` -> `right 20px top` (Chromium parse() returns ''). Three-value keyword origins are uncommon (none in the real corpus; two-value keyword forms like `center bottom` dominate, and those are fine), mostly in 3D transform CSS. `left top 0` -> `0 0` is harmless since z=0 is the default. Also, invalid values such as `left 10px center` and the four-value `left 10px top 5px` are accepted in strict mode. A user commented with a fix branch on a fork (not reviewed or run; no PR).

**Repro:** 1403-repro.mjs, 1403-repro-invalid.mjs. `left top 30px` -> `0 30px` (Chromium: 0 0 30px vs 0 30px); `center left 10px` -> `10px`; `bottom left 0` -> `left 0 bottom` (invalid, dropped: computed 50px 50px instead of 0 100px); `top right 20px` -> `right 20px top` (invalid). `right bottom 30px` and `0% 0% 30px` survive.

**Evidence:** repro.mjs --all: wrong on every release from 1.14.0 to 1.33.0 and on master (1.31.0+ prints `center left 10px` as `10px` instead of `10px 50%`, same bug). Chromium 153 probe: computed `left top 30px` = `0px 0px 30px`; `parse('transform-origin','left 0 bottom')` = '' (invalid), `bottom left 0` = 'left bottom 0px', `left 10px center` = '' and `left 10px top 5px` = '' (both invalid). equivalence.mjs on 1403-in.css: NOT EQUIVALENT (transform-origin differs on all three rules). Spec: css-transforms-1 transform-origin value is `[ left | center | right | top | bottom | <length-percentage> ] | [ left | center | right | <length-percentage> ] [ top | center | bottom | <length-percentage> ] <length>? | [ [ center | left | right ] && [ center | top | bottom ] ] <length>?`. No side offsets and no four-value form.

**Fix (medium):** Add a TransformOrigin value type {x: HorizontalPosition-like, y, z: Option<Length>} parsed with the transform-origin grammar (keywords in either order for the && form, no side offsets), and print it in a canonical x y [z] order, dropping z when it is 0. Changes the serialized AST shape for transform-origin (Position -> new struct), so it has to be called out as a breaking change for JS visitors (node/ast.d.ts regenerated). Also touches prefix handling for -webkit-/-moz- variants.

## Draft reply

Thanks, confirmed on 1.33.0 and master. `transform-origin` is parsed as a `<position>`, so a z offset after a side keyword is read as that side's offset. When the vertical keyword comes first, the output is also invalid, and the browser drops it:

```css
.a { transform-origin: bottom left 0 }     /* -> left 0 bottom   (invalid) */
.b { transform-origin: top right 20px }    /* -> right 20px top  (invalid) */
.c { transform-origin: left top 30px }     /* -> 0 30px */
```

The fix is to give `transform-origin` its own type with the [css-transforms-1 grammar](https://drafts.csswg.org/css-transforms-1/#transform-origin-property). That changes the AST shape seen by JS visitors. Until then, writing the x value first with lengths or percentages (`0 0 30px`, `100% 0 20px`) is preserved correctly.
