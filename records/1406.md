# #1406: calc() in a resolution media feature is a parse error

**bug · confirmed · low · queue-fix (good first issue)**

`Resolution::parse_with_range` (src/values/resolution.rs, `// TODO: calc?`) accepts only a dimension token. As a result `(resolution: calc(2 * 1x))`, `(min-resolution: calc(1dppx + 1x))` and `(resolution >= calc(96dpi * 2))` all fail to parse on master and on 1.31–1.33. Chromium 153 parses all three and serializes them as `calc(2dppx)`. MQ4 gives `resolution` the value `<resolution>`, and css-values-4 allows math functions wherever their type is allowed. With `errorRecovery` the rule is kept as written, with a warning. This is valid CSS rejected in strict mode, not corrupted output. It's rare in real CSS.

Fix (small): copy the approach in `src/values/time.rs`. All resolution units are absolute, so calc always folds to a value and the AST doesn't change. A commenter says they have a fix on a fork branch, but they opened no PR and I couldn't read the branch.

Repro: 1406-repro.mjs (3 failing cases; controls are plain resolution and image-set calc pass-through).

## Draft reply
Thanks, confirmed: Lightning CSS doesn't accept math functions in `<resolution>` values yet, so `(resolution: calc(2 * 1x))` is rejected even though it's valid per Media Queries 4 / CSS Values 4 and Chromium parses it. This reproduces on master and on 1.31-1.33. With `errorRecovery: true` the rule is kept as written with a warning, so that's a workaround for now. Since all resolution units are convertible, the fix should be able to resolve the calc() at build time (e.g. to `2x`), the same way `<time>` values are handled.
