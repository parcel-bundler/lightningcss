# #660 — CSS Modules `[hash]` to include class name

**Type:** feature (with a confirmed silent-output bug) · **Status:** confirmed · **Severity:** medium · **Action:** needs-maintainer-decision

`[hash]` hashes only the file path. Any pattern without `[local]` (`[hash]`, `[name]-[hash]`, `[content-hash]`) maps *every* local in the file to one name: `.a{} .b{} @keyframes k{}` with `[hash]` → `{a,b,k}` all `_9b48uG`. No error/warning; same on master, 1.33.0, 1.32.0, 1.31.1 (`660-repro.mjs`).

Fix options (small): (A) when the pattern lacks `[local]`, hash path + local (css-loader semantics; only already-broken output changes; closes the issue), or (B) error on such patterns. Open PR #1237 (large webpack-parity PR, maintainer skeptical) has an opt-in `hashLocalName`; opt-in keeps the broken default, so A or B is preferable.

## Draft reply

Thanks! Confirmed on 1.33.0 and master: `[hash]` is a hash of the file path only, so a pattern without `[local]` (e.g. `[hash]`, `[name]-[hash]` or `[content-hash]`) currently gives every class and keyframes name in a file the same scoped name. For example, `.a {} .b {}` with `pattern: '[hash]'` exports `{a: '_9b48uG', b: '_9b48uG'}`. That silently merges styles, so it needs fixing either way: by including the local name in the hash when the pattern has no `[local]` (what css-loader does), or by rejecting such patterns. There's also an open PR, #1237, that adds an opt-in option for this.

Until then, keep `[local]` in the pattern (e.g. `[hash]_[local]`).
