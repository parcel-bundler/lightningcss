# #1400 `none` beside other entries of `transition-property` or of a `transition` list parses as a valid value

- **Type/status:** bug / confirmed
- **Severity:** low
- **Action:** needs-maintainer-decision
- **Code:** src/properties/mod.rs: transition-property is SmallVec<[PropertyId; 1]>, PropertyId parse accepts `none` as a custom name; src/properties/transition.rs: Transition::parse (no list-level check for `none`)

css-transitions-1 excludes `none` from the <custom-ident> in <single-transition-property> and makes a multi-item `transition` with a `none` item invalid. Lightning CSS parses both as typed values, so instead of falling back to Unparsed (as `transition-property:5px` does, which is then preserved correctly) the TransitionHandler merges and overrides with them. Not shared with #1401: that regression (33265a2) is in TransitionHandler's merging of repeated properties; this is in parsing.

Spec and Chromium confirm the claim, and the typed parse lets the handler merge/override it with valid declarations, changing meaning. Not shared with #1401 (33265a2 is TransitionHandler merging; this is parsing).

**Repro:** 1400-repro.mjs. `.a{transition:opacity 1s;transition-property:none,width}` -> `.a{transition:none 1s,width 1s}` (all releases); expected both kept as written, as `transition-property:5px` is.

**Evidence:** Spec (css-transitions-1 Overview.bs): 'The <<custom-ident>> production in <<single-transition-property>> also excludes the keyword none' and 'If there is more than one <<single-transition>> in the shorthand, and any of the transitions has none as the <<single-transition-property>>, then the declaration is invalid.' Chromium probe: CSS.supports('transition-property','none, width') = false, computed transition-property `all` for both invalid declarations. Equivalence on 1400-fixture/in.css --minify: NOT EQUIVALENT (opacity/width 1s transitions lost). repro.mjs --range 1.14.0..1.33.0: bug cases wrong in all releases, controls correct.

**Fix:** small: Parse transition-property with a custom list parser that fails when the list has more than one item and any is `none` (ASCII case-insensitive); in the `transition` shorthand list parse, fail when len > 1 and any item's property is `none`. The failure then falls back to Unparsed, which the handler already preserves correctly. Tests in src/lib.rs next to the transition tests.

## Draft reply

Thanks, confirmed. Per CSS Transitions, `none` is only valid as the whole `transition-property` value, and a `transition` list with more than one item is invalid if any of them is `none`. Lightning CSS accepts both, so they aren't kept as written the way `transition-property: 5px` is. That can also change output: `transition: opacity 1s; transition-property: none, width` becomes `transition: none 1s, width 1s`, which browsers reject, so the opacity transition is lost. This has been the case in all recent releases. The fix is small: reject these lists while parsing.
