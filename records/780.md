# #780 Line numbers in source map incorrect

**bug / confirmed / high / queue-fix**

The printer advances its generated column by UTF-8 byte length (`s.len()`), but Source Map v3 columns are UTF-16 code units, and the original-side columns from cssparser are already UTF-16. After any non-ASCII output character, later generated columns are overcounted, so a consumer looking up a position finds an earlier mapping. With minified (single-line) output this shows as wrong original lines, as reported.

**Evidence:** repro.mjs: local (master c6a0c3c), 1.33.0, 1.32.0, 1.31.1 all WRONG on the 4 non-ASCII cases, ASCII control correct; --range 1.14.0..1.33.0 WRONG on every release (never worked). cssparser 0.37 documents `Column numbers are counted in UTF-16 code units` (tokenizer.rs), confirming the original side is UTF-16 and only the generated side is wrong.

**Fix:** Count UTF-16 code units for every col increment in Printer (5 sites). Prefer a fast path (`s.is_ascii()` -> s.len()) or skip counting when no source map is requested, since write_str is hot.

**Open PRs:** #1354: Fixes the root cause at all five col-increment sites in src/printer.rs, including the CSS-modules ident path via an IdentifierWriter wrapper; adds unit tests for utf16_len, printer positions and a source-map lookup after non-ASCII. Recommend reviewing it. Note for review: utf16_len scans every byte on every write even without a source map; consider an is_ascii fast path. Branch is behind master. Author discloses AI assistance.

## Draft reply

Thanks for narrowing this down. Confirmed: the generated columns in the source map are counted in UTF-8 bytes instead of UTF-16 code units, which is what the source map format uses. After the first non-ASCII character on an output line (e.g. `content: 'é'` or an icon glyph), every later mapping is shifted. Minified output is a single line, so rules end up pointing at an earlier rule's original line. A minimal case is `.a { content: 'é' }\n.b { color: red }` minified with `sourceMap: true`: `.b` maps to line 1 instead of line 2. It reproduces on every release back to at least 1.14.

There's an open PR, #1354, that addresses this.
