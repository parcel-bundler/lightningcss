# #436 Duplicate image-set with '>=0.0%' targets: confirmed bug, low

**Status:** confirmed on master and all releases 1.14.0-1.33.0 (never worked). **Action:** queue fix (small, good first issue).

Root cause: `get_fallbacks` in `src/values/image.rs` pushes a legacy `-webkit-gradient` fallback whenever the targets include Chrome 4-9, Safari <5.1, iOS <=6 or Android 2.x and a WebKit prefix is needed. `Image::get_legacy_webkit` returns a plain clone for non-gradients, so with an `image-set()`-only value that fallback equals the final unprefixed declaration.

Minimal: `.a{background-image:image-set(url(a.jpg) 1x, url(b.jpg) 2x)}` with targets `{chrome: 9<<16, safari: 6<<16}` gives three declarations, and the first and last are identical. The duplicate is harmless (byte-identical, so no change in behavior), only extra bytes, and only with unrealistic targets.

Fix: skip the legacy list unless it contains a gradient, or return Err for non-gradient prefixed images. Add a prefix_test.

Thanks for the clear repro! This still happens on the latest release (1.33.0). It only shows up when the targets include very old WebKit browsers that need the legacy `-webkit-gradient()` syntax (Chrome 4-9, Safari before 5.1), which `>=0.0%` pulls in: Lightning CSS builds a legacy fallback for those, and for an `image-set()` that isn't a gradient the fallback ends up identical to the final declaration. The duplicate is harmless (same value, so browsers behave the same), just extra bytes. A minimal case is `background-image: image-set(url(a.jpg) 1x, url(b.jpg) 2x)` with targets Chrome 9 and Safari 6. Using a more realistic query, such as `defaults`, avoids it.
