# #404 `:export` ICSS rule: feature, needs maintainer decision (medium)

- **What happens:** with `cssModules`, `:export { rowCount: 4 }` is copied verbatim into the output CSS and nothing is added to `exports`. The only signal is a misleading warning ("Did you mean '::export'"), and there is no error even in strict mode. Same in 1.27.0 through master. See `404-repro.mjs` (feature case WRONG, controls correct).
- **Demand:** the strongest of the CSS modules gaps. 8+8 reactions and about 10 users. The usual case is Sass `$vars` exposed to JS, hit through Vite (`css.transformer: 'lightningcss'`, Vite 8) and Next.js/Turbopack.
- **Philosophy fit:** a non-standard convention, but `:export` is valid CSS syntax and lives inside the cssModules option that already exists. It needs no tokenizer changes and no per-property substitution (unlike `@value`).
- **Fix (medium):** in cssModules mode, drop a top-level `:export` rule and add each `name: value` to `exports`. API question: putting the value in the existing `name` field would work in Vite/Parcel/Turbopack with no changes there but overloads `name`. A new field changes the exports shape.
- **Cheap interim step:** a specific "`:export` is not supported" warning or error instead of the `::export` hint.
- No open PRs. No draft reply until the maintainer decides.
