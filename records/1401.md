# #1401: A `transition` list keeps the first of a repeated property, where the last one applies

**regression / confirmed / severity medium / action queue-fix** (regression 1.28.1 -> 1.28.2, 33265a2 Fix duplicate `-webkit-backdrop-filter` output (#850))

Since 1.28.2, merge_properties() collapses repeated entries of transition-property (ignoring vendor prefix) into the first occurrence, but leaves the duration/delay/timing-function lists untouched. Per css-transitions-1 the LAST occurrence's timing applies, and because the lists are index-aligned, every entry after the removed one shifts to the wrong timing. Lists should be kept as written (as in 1.28.1), only avoiding the duplicate prefixed entries that #850 was about.

**Impact:** No reactions (batch report). The reporter's exact cases (`width 1s, width 2s`, `all, all`) are rare in real CSS. But the same root cause has a worse, more plausible form the issue doesn't mention: merging a prefixed/unprefixed pair drops a list entry without dropping its duration/delay/easing, so every LATER entry gets the wrong timing. `.a{transition:-webkit-transform .3s, transform .3s, opacity .5s}` -> `...,opacity .3s` (Chromium confirms opacity runs 300ms instead of 500ms). Hand-written legacy CSS with -webkit-transform listed before transform and a different later timing hits this; autoprefixer's own output (prefixed entry appended last) happens to survive. No hits in the real-world corpus (pico uses var(), which is unparsed and unaffected). Silent wrong output, with or without minify, no targets needed.

**Repro:** 1401-repro.mjs (reporter cases), 1401-repro-shift.mjs (index shift). `.a{transition:width 1s, width 2s}` -> `.a{transition:width 1s}` (1.28.1: kept as written). `.a{transition:width 1s, width 2s, height 3s}` -> `.a{transition:width 1s,height 2s}`. `.a{transition:-webkit-transform .3s, transform .3s, opacity .5s}` -> `.a{transition:-webkit-transform .3s,transform .3s,opacity .3s}`. `transition-property:all,all;transition-duration:1s,2s` -> `transition-property:all;transition-duration:1s,2s`.

**Evidence:** repro.mjs --all --bisect: correct in 1.14.0..1.28.1, wrong in 1.28.2..1.33.0 and local master. Only transition change between v1.28.0 and v1.28.2 is 33265a2 (#850, introduced merge_properties). Chromium 153 via getAnimations(): `transition:width 1s, width 2s` -> width transition 2000ms vs 1000ms after LC; `-webkit-transform .3s, transform .3s, opacity .5s` -> opacity 500ms vs 300ms; `all,all;1s,2s` -> 2000ms vs 1000ms. equivalence.mjs also reports transition-duration differences. Spec (css-transitions-1 Overview.bs): "If a property is specified multiple times in the value of 'transition-property' (either on its own, via a shorthand that contains it, or via the 'all' value), then the transition that starts uses the duration, delay, and timing function at the index corresponding to the last item in the value of 'transition-property' that calls for animating that property."

**Fix (small):** Stop removing entries in merge_properties; keep the list (and its indexes) as written, and when adding vendor-prefixed variants in flush() skip a prefix that the list already contains for that property, which is what #850 needed. Keep the #850 test and add tests for `width 1s, width 2s`, `-webkit-transform .3s, transform .3s, opacity .5s` and `all, all` with two durations. Deduplicating is only safe in the shorthand with all four lists expanded to the same length, and then must keep the last occurrence; not worth it.

**Not verified:** Behavior only checked in Chromium. Did not check other handlers that might use merge_properties-like logic (animation lists). Didn't check behavior with targets that add prefixes, beyond reading the code.

## Draft reply

Thanks for the report, confirmed. This is a regression from 1.28.2: lists were kept as written up to 1.28.1. The change that dedupes prefixed entries in `transition-property` also collapses exact repeats into the first occurrence, but leaves the duration/delay/easing lists as they were. Per [css-transitions-1](https://drafts.csswg.org/css-transitions-1/#transition-property-property) the last occurrence's timing applies. Because the lists are matched by index, it can also shift the timing of later entries:

```css
.a { transition: -webkit-transform .3s, transform .3s, opacity .5s }
/* 1.28.2 to 1.33.0: */
.a { transition: -webkit-transform .3s, transform .3s, opacity .3s }
```

In Chromium, opacity then animates for 300ms instead of 500ms. Until it's fixed, avoid repeating a property (prefixed or not) ahead of other entries in the same list.
