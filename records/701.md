# #701 Missing ../pkg when bundling lightningcss

**bug, fixed-in-release (1.32.0), low (historically high: 23 reactions), action: close**

`node/index.js` up to 1.31.1 had a static `require(`../pkg`)` behind `CSS_TRANSFORMER_WASM`; esbuild-based bundlers (serverless-esbuild, Bun.build, Vite dep optimizer, Next server bundling) tried to resolve it and failed. Commit 96c5c6d (#1170) removed the branch; first released in v1.32.0. Repro (`701-repro.mjs`): esbuild bundle of the loader errors on 1.30.0..1.31.1, succeeds with a warning on 1.32.0/1.33.0. Control: `external: ['lightningcss']` works on all versions.

Note: in a source checkout, esbuild's glob for `../lightningcss.*.node` matches the locally built addon and errors with "No loader for .node"; published packages don't ship that file, so this doesn't affect users.

## Draft reply

This should be fixed as of **lightningcss 1.32.0**. Older versions had a fallback `require('../pkg')` (for a local WASM build) in `node/index.js`; because it was a static path, bundlers like esbuild, `serverless-esbuild` and `Bun.build` tried to resolve it and failed with `Could not resolve "../pkg"`. That branch was removed in 1.32.0, so bundling `node/index.js` now only produces a warning about the optional `.node` glob.

If you still see this, please check which version is actually installed (`npm ls lightningcss`), since Vite or Tailwind may pull in an older one. Either way, we'd recommend keeping `lightningcss` external (e.g. `external: ['lightningcss']`, or `serverExternalPackages` in Next.js): it loads a native binary per platform, so it works best loaded from `node_modules` rather than bundled.

Closing for now; happy to reopen with a repro on 1.32.0 or later.
