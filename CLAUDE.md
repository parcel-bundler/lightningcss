# Lightning CSS

A CSS parser, transformer, bundler and minifier in Rust, published as the `lightningcss` crate and the `lightningcss` npm package (200M+ weekly downloads). Correctness matters more than output size: a minifier bug silently changes the look of a huge number of production sites. When unsure whether a transform preserves meaning, it must not be applied.

## Project philosophy

These come from the maintainer. Apply them when reviewing PRs, triaging issues and writing fixes:

- **Fully parse all syntax.** Every property, value and rule gets a typed representation, rather than raw tokens in the AST like other CSS parsers store. It's more work, but it is what makes the performance, minification and correctness possible. A PR that stores something as unparsed tokens to avoid writing a parser is usually the wrong approach.
- **Strict by default.** Lightning CSS errors in more cases than browsers and other CSS parsers, on purpose. It's a build tool, and developers should learn about broken CSS before it ships, not have it silently ignored. Because third-party packages often contain invalid CSS unknowingly, the `errorRecovery` option exists: errors become warnings and parsing recovers exactly like a browser would, keeping the CSS as written rather than "repairing" it. So:
  - **Strict mode:** errors are for definitely invalid input involving *known* syntax, e.g. `(min-width)` in a boolean context. Unknown-but-valid syntax passes through, e.g. `(min-foo)`.
  - **Error recovery mode:** the same input produces a warning and is preserved as written.
- **No non-standard features.** Non-standard rules and properties can pass through in `errorRecovery` mode if they are valid CSS syntax. Other syntax extensions are not supported, because they complicate the tokenizer and parser; external tools should process them first.
- **Limit hacks for very old browsers.** Target browsers people actually use. The CSS specification is the source of truth, not implementation bugs; don't add workarounds for bugs in browsers nobody uses.
- **Put experimental and draft features behind flags.** Draft syntax (e.g. only in Chrome, without other browsers committed) may change. It goes behind draft feature flags so a later spec change isn't a breaking change for users.

## Layout

- `src/lib.rs`: crate root. Also holds most of the test suite (~30k lines, the `tests` module).
- `src/stylesheet.rs`: `StyleSheet` parse → `minify` → `to_css`.
- `src/rules/`: one file per at-rule type, plus `style.rs` for style rules.
  - `CssRuleList::minify` in `rules/mod.rs` does all rule-level optimization: merging adjacent rules, removing duplicate rules (`StyleRuleKey`, `is_duplicate`), `@layer` merging and hoisting, and inserting fallback rules.
- `src/declaration.rs`: `DeclarationBlock` and `DeclarationHandler`, which dispatch to property handlers. Handlers buffer declarations and emit them in `finalize`; this is where shorthands get combined, duplicates removed and fallbacks/prefixes added.
- `src/properties/`: property definitions (`mod.rs` macro lists every property) and their handlers (one file per family: `background.rs`, `border.rs`, `font.rs`, …). `custom.rs` holds unparsed/custom property token lists.
- `src/values/`: value types (`length.rs`, `calc.rs`, `color.rs`, …).
- `src/selector.rs` plus the forked `selectors/` crate (`parcel_selectors`): selector parsing, serialization, compatibility checks, nesting.
- `src/media_query.rs`: media queries, including range syntax lowering.
- `src/targets.rs`, `src/compat.rs`, `src/prefixes.rs`: browser targets. **`compat.rs` and `prefixes.rs` (and `node/targets.d.ts`, `node/flags.js`) are generated** by `scripts/build-prefixes.js` from caniuse-lite, @mdn/browser-compat-data and autoprefixer. Never hand-edit them; change the script.
- `src/css_modules.rs`, `src/bundler.rs`, `src/dependencies.rs`: CSS modules, `@import` bundling, url/import extraction.
- `src/visitor.rs`, `derive/`, `static-self*`: the visitor API and its derive macros.
- `node/`: napi bindings (`node/src`), JS entry points and TypeScript types. `node/ast.d.ts` is generated by `yarn build-ast`; `node/index.d.ts` is hand-written.
- `napi/`, `wasm/`, `c/`: other bindings. `cli/`: npm CLI wrapper; `src/main.rs`: the Rust CLI (`--features cli`).
- `wpt/`: Web Platform Tests diagnostic harness with a reviewed failure baseline (see `wpt/README.md`).
- `scripts/equivalence.mjs`, `scripts/cases.mjs`, `scripts/probe.mjs`, `scripts/build-pr.sh`, `scripts/size-check.sh`: verification tools (below).

## Building and testing

```sh
cargo build --release --features cli --bin lightningcss   # CLI at target/release/lightningcss
cargo test --lib <name>          # e.g. cargo test --lib test_merge_layers
cargo test --all-features        # what CI runs (plus cargo fmt)
yarn build && yarn test          # node binding + JS tests (node/test)
yarn tsc                         # type-check node/index.d.ts
yarn test:wpt:baseline           # WPT regression check (needs fixtures; see wpt/README.md)
```

Tests in `src/lib.rs` use helpers such as `test` (pretty printed), `minify_test`, `prefix_test(source, expected, Browsers)`, `nesting_test`, `css_modules_test` and `error_test`. A new behavior needs tests there, next to the existing tests for that property or rule. Format with `cargo fmt` (config in `rustfmt.toml`).

The CLI: `target/release/lightningcss --minify --targets 'safari 12' file.css` (browserslist query; repeat `--targets` or use `--browserslist`).

## Verifying CSS behavior: use a browser, not intuition

CSS has many non-obvious rules, so reasoning alone is not evidence that a transform is safe. Check claims about behavior:

- `node scripts/equivalence.mjs in.css [-- cli args]` renders the input and Lightning CSS's output in Chromium against generated DOM trees (or `--html`). It compares computed styles of every element and pseudo-element across:
  - viewports either side of each breakpoint;
  - dark mode, print and reduced motion (when the CSS mentions them);
  - forced `:hover`/`:focus`/`:active` states;
  - sampled animation and transition times.

  Exit 1 means the output changes behavior. Color-space conversions and added prefixed fallbacks are reported but don't fail.
- `node scripts/cases.mjs cases.css [--base-bin A] [--bin B] [--config "--minify"]... [--repeat N]` runs many `/* case: name */` blocks through one or two builds under several option sets. It browser-checks every output and classifies each run as regression, fixed, still-broken, changed or ok.
- `node scripts/probe.mjs "matchMedia('(min-width)').media" ...` evaluates expressions in Chromium (with optional `--css-text`/`--html`/`--media`) to see how a real browser parses or computes something.
- `scripts/build-pr.sh [--on-master] <pr-number>` builds the PR and its merge base (or the PR merged onto master, and master) into `target/review/` and prints `PR_BIN=` / `BASE_BIN=`.
- `scripts/size-check.sh BASE_BIN NEW_BIN [files...]` compares minified output size and time on two corpora:
  - a synthetic one (`scripts/size-corpus.py`): Tailwind-style, component bundles and atomic CSS;
  - a pinned real-world one (`scripts/real-corpus.json`, fetched from npm by `scripts/fetch-corpus.mjs`): react-spectrum S2's atomic CSS, Radix Themes, Bootstrap, Bulma, Primer, Pico, animate.css, Open Props and Font Awesome.
- Chromium is at `/opt/pw-browsers/chromium` in cloud sessions (`CHROME_PATH` overrides). Puppeteer is a dev dependency.

Limits: only one engine (Chromium), and only meaning in a *modern* browser is checked. Whether lowered output works in an old target browser comes from compat data and specs, not this tool. A pass means "no difference observed", so pair it with deliberately adversarial fixtures and cases.

For spec questions, read the current Editor's Draft at drafts.csswg.org and quote it. If that host is unreachable, use the Bikeshed source at `raw.githubusercontent.com/w3c/csswg-drafts/main/<spec>/Overview.bs`. Check MDN/caniuse for support data, and the CSSWG issue tracker (w3c/csswg-drafts) for recent resolutions. Browser behavior can lag or deviate from the spec; note it when it does.

See `.claude/knowledge/css-pitfalls.md` before changing or reviewing minification, lowering or serialization code. Most past regressions fall into categories listed there.

## Conventions

- Do not change public Rust APIs, the JS API, or the serialized AST shape (`node/ast.d.ts`, serde output used by JS visitors) without calling it out: those are breaking changes for users.
- Generated files (`src/compat.rs`, `src/prefixes.rs`, `node/ast.d.ts`, `node/targets.d.ts`, `node/flags.js`) are regenerated, never hand-edited.
- Tests that change an existing expected output need a justification (spec text or browser evidence). Several past bugs were enshrined in wrong expectations.
- Performance: avoid quadratic work over rule lists or token lists, needless cloning in hot paths, and re-parsing. Benchmarks: `cargo bench --bench transform` (CodSpeed runs in CI).
